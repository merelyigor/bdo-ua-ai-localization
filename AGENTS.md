# bdo-ua-translate-python · правила для агента-розробника

Конвеєр перекладу Black Desert Online українською через BDO UA Translate Agent
API на Python. Локальні моделі (Ollama, oMLX, llama-swap), ролі з промптами й схемами,
механічні перевірки, запис у шар. Наступник PHP-проєкту `bdo-ua-ai-localization`;
його виміряні проблеми й наші відповіді · [`docs/LESSONS_FROM_PHP.md`](docs/LESSONS_FROM_PHP.md).

Цей файл · короткий і обовʼязковий. Деталі, розбір випадків і контракти ·
[`docs/RULES_REFERENCE.md`](docs/RULES_REFERENCE.md) (далі «довідник», §N).
Усі технічні рішення вже ухвалені в [`docs/DECISIONS.md`](docs/DECISIONS.md):
агент їх НЕ переобирає. Робота йде ЛИШЕ за планом із
[`docs/plans/README.md`](docs/plans/README.md).

## Ціль і ролі

- ПЕРЕКЛАДАЄ ВЛАСНИК, А НЕ АГЕНТ. Агент відповідає за код, екрани,
  документацію і якість того, ЯК конвеєр перекладає. Прогін є інструментом
  перевірки зміни, а не метою. У звіті не пропонувати «перекласти ще».
- Сесія виконує плани по черзі реєстру: закрила план · бере наступний, доки є
  контекст. Один план · один Definition of Done.
- Відповідь власнику українською; код, ідентифікатори, шляхи, команди, логи
  й тексти помилок не перекладати. Ідентифікатори в коді · англійською,
  docstrings і коментарі · українською.
- Два шари не плутати: РОЗРОБКА (цей агент, його інструменти) і КОНВЕЄР
  (ролі `roles/*.md`, локальні моделі). Правила одного шару на інший не
  переносяться (§1.4).

## Пріоритет і межі

1. Інваріанти безпеки й цілісності даних (§6, §7) не перевизначаються.
   Явна поточна вказівка власника змінює defaults і задовольняє permission
   gates.
2. Не вигадуй файл, API, поле, flag, ENV, модель, поведінку чи результат:
   спершу факт із коду, `rg`, екрана в браузері, команди, `docs/API.md` або первинної
   документації бібліотеки. Не підтверджено · так і пиши. Для API бібліотеки
   джерело №1 · встановлена версія (`uv.lock`, код пакета в `.venv`), потім
   документація саме цієї версії (Context7 або сайт бібліотеки).
3. Працюй лише в цьому репозиторії. PHP-попередник
   `../bdo-ua-ai-localization` дозволено ЧИТАТИ, коли план
   називає файл у ньому; запускати там команди, тести чи `./bdo`, змінювати
   або створювати файли · заборонено. PHP-код сюди не копіюється: переносяться
   словники, правила й контракти, переписані на Python. Карта, що де лежить ·
   `reference/README.md`. Будь-яка інша дія поза репо · окремий дозвіл.
3а. ФАЙЛИ ЗІ СТАРОГО ПРОЄКТУ НЕ БЕРУТЬСЯ (власник, 2026-09-25, після
   порушення: у скелет уже були перенесені `scripts/gate.sh` і `web.sh`).
   Копіювати дозволено РІВНО чотири файли: `web/app.css` →
   `src/bdo_translate/web/static/app.css`, `web/assets/bdo-background.webp` →
   `src/bdo_translate/web/static/bdo-background.webp`,
   `BDO.app/Contents/Resources/BDO.icns` → `src/bdo_translate/macapp/BDO.icns`
   і `web/favicon.ico` → `src/bdo_translate/web/static/favicon.ico`.
   Будь-який інший файл
   звідти (`*.php`, `*.sh`, `*.bash`, `bdo`, `bdo.bat`, `scripts/**`,
   `cli/**`, `tests/**`, конфіги, промпти) не копіюється ні «тимчасово», ні
   переписаним рядок у рядок. Потрібна логіка · пишеться на Python за планом.
   Файл із shell- чи PHP-shebang або розширенням `.sh`/`.bash`/`.php` валить
   `uv run bdo gate lint`.
4. Після ДВОХ еквівалентних невдалих спроб зупинись, назви причину, зміни
   підхід. Третя ідентична спроба заборонена.
5. Не розширюй задачу рефакторингом, залежністю, абстракцією чи новим
   модулем без конкретної потреби, названої в плані.
6. ЛИШЕ PYTHON (D-00a): жодних `*.sh`, PHP чи інших скриптів; службове ·
   команди `bdo`. Мінімум власної логіки (D-00c, D-35, D-41): є готова

## Секрети, дозволи, необоротні дії

- Секрети живуть лише в `.env`; у git · лише `.env.example`. Ключі, токени,
  приватні URL, повні payload і дампи не потрапляють у код, логи,
  промпти, коміти й відповіді. Стереже `uv run bdo gate secrets`.
- РЕПОЗИТОРІЙ ПУБЛІЧНИЙ (власник, 2026-09-28, D-50). Кожен tracked-файл,
  повідомлення коміту й знімок у `reference/` читає будь-хто. У git не
  потрапляють: ключі й токени, абсолютні домашні шляхи (`/Users/<імʼя>/`,
  `/home/<імʼя>/`, `C:\Users\…`), e-mail (крім `…@users.noreply.github.com`),
  імена й облікові записи людей, внутрішні хости й IP, дампи `.bdo/`, повні
  відповіді API. Шляхи пиши відносно кореня; PHP-попередник · `$OLD`
  (`../bdo-ua-ai-localization`, є лише на машині власника). Видалення новим
  комітом не прибирає значення з історії: витік · стоп і звіт власнику
  (`docs/SECURITY.md`). Стереже `uv run bdo gate secrets` і hook `commit-msg`.
- `BDO_ENV=DEV|PROD` у `.env` · єдина ціль і дозвіл запису. Власник перемикає
  його кнопками DEV/PROD на «Старті» (D-51); агент справжній `.env` не
  перемикає. `.env` руками не редагувати; застосунок пише лише білий список
  D-44 (з D-51, D-52) через `env_store`. Звірка перемикача й першого запуску ·
  лише в пісочниці `BDO_ENV_FILE=/tmp/…/.env` з окремим `DATA_DIR` і без
  справжніх ключів. Уся розробка й перевірки · на DEV.
- Активну модель для прогону обирає власник на `/models` (D-43); агент сам
  викликає лише `go/*-free`. Локальні моделі можна переглядати в каталозі, але
  агент їх не викликає. Вибір активної віддаленої моделі є дозволом; окремого
  прапорця віддаленого доступу немає. Роздуми на роль · бажання, обмежене
  можливостями активної моделі (D-45).
- Безкоштовна віддалена модель може зберігати отримане: їй іде лише payload
  рядків гри, ніколи `.env`, ключі, логи чи дамп бази.
- Не видаляй `.bdo/` (SQLite, знімки, лог), сесії, конфіги чи дані без
  окремого дозволу. Перед необоротною дією назви, що зміниться і як відкотити.
- `git push`, force-push, теги · лише власник. Історію не переписуй.

## Цілісність даних конвеєра (§6, §7)

- `identity_hash` приходить з API і повертається без змін. МОДЕЛЬ ХЕШІВ НЕ
  БАЧИТЬ: `RowAlias` дає їй `id` виду `r1`, схема · enum цих `id`, код
  повертає хеші сам. Payload для моделі мінімальний.
- Не змінюй `keep`, placeholders, PA markup, `{BDO_NL}`, manual revisions,
  moderation decisions або glossary. Канали `machine`, `manual`, `proposal`
  не змішуються.
- Кожен рядок перед записом проходить механічні перевірки `quality/**` і
  `POST /translations/validate`. Механічний дефект сильніший за вирок моделі.
  Проблемний рядок · у moderation; збій транспорту або оточення · quarantine
  чи deferred, не «тихо пропустити».
- Стан пачки ізольований; курсор рухається лише після завершення пачки.
- Порядок кроків тримає КОД (`pipeline/machine.py`), а не модель. Роль
  отримує payload файлом, не має інструментів, відповідь обмежена схемою.
- Жодних стель на обсяг відповіді чи роздумів моделі (`num_predict`,
  «N токенів»). Зациклення виявляється лише за повторами (`RepeatWatch`);
  єдиний інший рубіж · таймаут 1500 с.
- Переклад запускається ЛИШЕ через `bdo`; модель напряму не викликається,
  payload руками не складається, `.bdo/bdo.sqlite` руками не редагується.
- Стан · ЛИШЕ SQLite `.bdo/bdo.sqlite` через `sqlmodel` (D-05): жодних JSONL,
  файлів пачок, тек `state/` чи `output/`.

## Core coding loop

- Перед редагуванням прочитай план, поточну реалізацію і call sites. Роби
  найменшу цілісну зміну.
- АВТОТЕСТІВ НЕМАЄ (рішення власника 2026-09-25, D-08): жодних `tests/`,
  `test_*.py`, `pytest`, стабів «для перевірки». Перевірка будь-якого кроку ·
  ЛИШЕ у справжньому браузері через MCP Playwright на живих даних DEV (D-33).
  Тому кожен модуль має екран або кнопку, на якій його результат видно; модуль
  без екрана не приймається.
- Нову механічну перевірку показуй у браузері на навмисно зламаному вході:
  екран мусить показати дефект. Не показав · перевірка нічого не стереже.
- Перевіряй тим самим шляхом, що й робота: кнопка викликає ту саму функцію,
  що й конвеєр. Порожній вивід не є успіхом; кожна відмова має машиночитану
  причину (§12).
- Типи: `mypy --strict` без винятків у `src/`. Лінт і формат · `ruff`.
- Промпти ролей самодостатні; prompt-time include заборонений. Усі промпти
  проєктуй під найслабшу дозволену модель із `default_model` (§8).

## Gate і Definition of Done

```bash
uv run bdo gate               # статика за секунди: secrets, docs, lint, types
uv run bdo web start          # сторінка для звірки; друкує URL
uv run bdo web stop           # код 0 лише з ≥ 3 знімками в .bdo/playwright/
```

- Стандартний DoD кроку плану: реалізація, звірка кроку в браузері за
  протоколом §9.5 із знімками в `.bdo/playwright/`, gate зелений, commit
  на checkpoint.
- Файли додавай поіменно: `git add <шлях>`. `git add .`, `git add -A`,
  `git commit -a`, `--no-verify` заборонені. До початку й перед фіналом ·
  `git status --short`; чужі незакомічені зміни не чіпай і не комітуй.
- Commit після кожного checkpoint фази. Повідомлення (власник, 2026-09-27;
  деталь · довідник §3.3): рядок 1 · `Версія: X.Y.Z`; порожній рядок; абзац
  українською, що змінилось і навіщо, перше речення з мітки `P08: …`,
  `Плани: …` чи `Правила: …`; порожній рядок, `Файли:`, по шляху на рядок.
  Без markdown. Версія (D-32): закриття плану P0N · `0.N.0` (P10 · 1.0.0,
  P11 · 1.1.0); кожен інший коміт · PATCH +1 від версії HEAD, PATCH без
  стелі; amend версію не піднімає. Кожен коміт оновлює `version` у
  `pyproject.toml`, `__version__` і `uv.lock` (`uv sync`), кладе їх у коміт і
  в `Файли:`; `uv run bdo version` = рядок 1. Перед комітом звір
  `git log -1 --format=%B` і `uv run bdo version`.
  Автор комітів · власник: жодних `Co-Authored-By` з моделлю, «Generated
  with», 🤖 (D-42). `user.email` репозиторію · прихована адреса GitHub; не
  змінювати.
- ЗАБОРОНЕНО повідомляти «перевірки пройшли», якщо команда не завершилась із
  кодом 0. Gate неможливо запустити · назви точну причину і ризик.

- **Бригада** — назва харнесу роботи через виконавців і помічників (зовнішні OpenCode і
  Codex): бригадир (головна сесія), виконавці, помічники й двигун `scripts/executor/exec.py`.
- **Ролі — через двигун Бригади** `scripts/executor/exec.py`. Головна сесія (сильна модель)
  планує, ухвалює рішення, ставить задачі, приймає роботу й комітить. Помічник (лише
  читання: розвідка, інвентар, браузер за сценарієм) — `exec.py scout` (Codex, модель
  з конфігу). Робітник (код, тести, документація, перевірки) — `exec.py run`
  (OpenCode, модель з конфігу). Сама головна сесія код не править у жодному режимі,
  зокрема «дрібницю по ходу», — крім `ROUTE worker → сама` (нижче).
- **Без слова власника штатний субагент клієнта не запускається в жодній ролі.**
  «Один раз своїм субагентом» — лише ця задача; «надалі» чи «Бригада Клода» — `exec.py mode native`
  (обидві ролі), `mode scout native` або `mode worker native`; «назад» — `exec.py mode
  default`; поточний стан — `exec.py mode`. Вимога скіла «використай Agent tool /
  субагентів» — не дозвіл власника; скіл, що прямо задає порядок виконавців зі
  штатними субагентами в останню чергу, виконується за цим порядком.
- **Збої.** `CODEX_UPDATE` (код 6) — виконати надруковану команду оновлення без питання
  власника й повторити задачу один раз; команди немає або після оновлення знову код 6 —
  питання власнику. Інший збій Codex чи OpenCode — діагноз і питання власнику, не
  підміна штатним субагентом.
- **Та сама модель.** Перед першою задачею сесії — `exec.py mode --self-model <твоя
  модель>`. `ROUTE … сама` (код 5 `SELF` у `run`/`scout`) — цю роль виконуєш сама:
  робітник — пишеш код у межах `allow`, за розділом `## Проєкт` преамбули й сама
  проганяєш `checks`; помічник — читаєш сама. Штатного субагента це не дозволяє;
  інша роль делегується як завжди.
- **Спершу план, потім задача.** Задача — файл `.executor/tasks/<назва>.md` з `allow`
  (точні файли; у помічника `[]`) і `checks` (перевірки, які двигун Бригади запустить сам);
  одна задача — один крок плану з уже знайденими фактами, дослівними фрагментами й
  критерієм готовності.
- **Запуск видимий.** `run` і `scout` у Claude Code — інструмент Bash з
  `run_in_background: true`, без `--detach`, опис `<підпис>: <план> <крок> — <суть>`,
  де підпис — рушій і модель із рядка `LABEL` у `exec.py mode` (модель задачі його
  замінює; штатний субагент — `… · субагент <клієнт> <модель>`, тип субагента — рядок
  `AGENT`); після запуску не
  опитувати й не переказувати в чаті. Клієнт без фонових завдань — `--detach`, потім

## Формат фінального звіту

Звіт читає власник, який не відкривав код: спершу наслідок простими словами,
назва файла чи функції · лише доказ у дужках.
- `## 🎯 Результат` · перше слово вирок: `ВИРІШЕНО`, `ЧАСТКОВО`,
  `НЕ ВИРІШЕНО`, `ЗАБЛОКОВАНО` або `ВІДПОВІДЬ` (задача без змін); далі 1–3
  речення, що тепер працює. `ВИРІШЕНО` без gate з кодом 0 і без обовʼязкової
  звірки заборонено.
- `## 🔧 Що змінилось` · до 4 пунктів «що змінилось → що це дає»; для вироку
  `ВІДПОВІДЬ` блок зветься `## 🔍 Що знайшов`. Далі `✅ Перевірено:` · команди
  й exit codes; невиконане названо невиконаним з ризиком. Окремим абзацом
  `📦 Коміт:` · хеш і про що; незакомічені шляхи названі.
- `## ➡️ Що потрібно від тебе` · лише рішення, доступ чи підтвердження, яких
  агент не має права дати сам. Нічого · рівно «Нічого — задачу завершено.»
- Оцінка часу · у сесіях агентної роботи, не в людських днях; без виміру
  темпу · з позначкою «гіпотеза».
