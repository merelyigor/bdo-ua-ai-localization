# Як перекладати цим набором

Переклад виконують СКРИПТИ й локальні моделі Ollama. Порядок кроків тримає код,
а не модель: це головна відмінність від попередньої версії набору, де конвеєр
вела модель-диригент у OpenCode (законсервована тегом `v3.0.6-opencode`).

Канонічний перелік команд · [`cli/command-registry.json`](cli/command-registry.json),
згенерований довідник · [`docs/COMMANDS.md`](docs/COMMANDS.md).

## Для власника: один вхід

```bash
./bdo
```

У Windows той самий запуск · подвійний клік по `bdo.bat` (він піднімає набір у
WSL2 і друкує посилання). З IDE або файлового менеджера · `make web`.

Команда бере вільний порт і друкує посилання · відкривається сторінка, де
прогін видно як чат із конвеєром: запит і відповідь кожної ролі, генерація
токен за токеном, черга до людини, історія сесій. Кнопки «почати прогін»,
«зупинити», «нова сесія», «схвалити» виконують рівно ті самі команди набору,
які нижче описані для розробника. Запис у PROD вимагає підтвердження.

Сторінку можна закрити й відкрити знову · робота триває: прогін живе окремим
процесом, а сервер лише читає стан. Тому й прогін, запущений у терміналі,
видно в браузері так само.

## Без браузера: вікно в терміналі

```bash
./bdo tui
```

Відкриється меню:

| Пункт | Що робить |
|---|---|
| `патч` | бере рядки патча й доводить їх до запису в шар `machine` |
| `покращення-ші` | повторний прохід по вже машинних рядках |
| `пропозиції` | той самий конвеєр, але запис у канал пропозицій |
| `ручний` | вузький набір під підтвердження людини |
| `продовжити` | доводить незавершену пачку до кінця |
| `стан` | ціль, поточна пачка, останні виклики моделі |
| `журнал` | скільки разів і за скільки працювала кожна роль |

Далі набір питає патч, категорію й кількість пачок · і працює сам. `Ctrl-C`
зупиняє між кроками; стан лежить на диску, тому продовження починається з того
самого місця.

## Що відбувається всередині однієї пачки

```
mode start          вибірка рядків з API у теку пачки
   ↓
run drive           рушій каже, який КРОК наступний
   ↓
run-loop.sh         драйвер виконує цей крок і питає рушій знову
   ↓
client.php          роль виконує локальна модель під strict-схемою
```

Порядок ролей: `terminology` → `worker` → механічні перевірки → `qa` →
`repair` → `judge` → запис. Кожен перехід дозволений
[`lib/Pipeline/StateMachine.php`](lib/Pipeline/StateMachine.php); драйвер не
вигадує кроків і не пропускає їх.

Ключова межа: **payload роль отримує файлом**. Ніхто його не переказує, не
скорочує й не відновлює по памʼяті. У версії з диригентом саме переказ дав 174
порушення контракту й чотири окремі дефекти.

## Для розробника: ручний CLI

Це не основний користувацький workflow · він потрібен для діагностики.

```bash
./bdo env                    # яка ціль стоїть у .env (PROD або DEV)
./bdo runtime                # чи готова локальна модель до пачки
./bdo mode start patch 50 7  # почати пачку патча 7 (ключ англійський!)
./bdo loop --batches 1       # провести рівно одну пачку до кінця
./bdo run drive              # один крок рушія, JSON-конверт
./bdo audit                  # що робили моделі цього прогону
./bdo review                 # стан проєкту одним екраном
./bdo gate full              # повний quality gate
```

## Де що налаштовується

| Файл | Що задає |
|---|---|
| `.env` | ціль прогону (`BDO_ENV`), ключі API, розміри payload |
| `config/roles.json` | модель, схема й температура кожної ролі, endpoint Ollama |
| `roles/<роль>.md` | промпт ролі · самодостатній, без include |
| `state/model-calls.jsonl` | журнал КОЖНОГО виклику моделі: роль, час, токени, вирок |

Модель для всіх ролей задає `default_model`; окремій ролі можна дати свою
`model`. Роль без промпта або з моделлю, якої немає в `ollama list`, зупиняє
`./bdo runtime` · до пачки, а не посеред неї.

## Межі, які набір тримає кодом

- Порожній `content`, обрив на стелі, чужа схема, переповнене вікно · це
  ПОМИЛКА з машинно-читаною причиною, а не привід мовчки повторити.
- Драйвер зупиняється, якщо стан не рухається; нескінченного циклу немає.
- Ціль прогону не «забувається»: доки в патчі лишаються рядки, наступну пачку
  драйвер відкриває сам.
- Валідація тексту повторюється ПЕРЕД записом, уже після repair і судді.
