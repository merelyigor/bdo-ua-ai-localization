# Нормативний довідник AI-агента

Це повний контракт `bdo-ua-ai-localization`. Коротка карта в root rule-файлах
маршрутизує сюди за категорією задачі. Номери `§N.M` сталі: нові правила отримують
нові номери, чинні не перенумеровуються.

## §1 Пріоритет, факти і межі задачі

- §1.1 Поточна вказівка власника має пріоритет, крім безпекових і юридичних
  заборон. Конфлікт правил зупиняє роботу до рішення власника.
- §1.2 Не вигадувати файли, API, поля, flags, ENV, модель, поведінку або результат.
  Джерела факту: код, targeted read, `rg`, лог, тест, реальна команда, серверна
  документація через `TRANSLATE_PROJECT_ROOT`.
- §1.3 Після двох еквівалентних невдач встановити причину й змінити підхід;
  третя ідентична спроба заборонена.
- §1.4 Одна сесія має одну ціль і явний Definition of Done. Не додавати
  рефакторинг, dependency, abstraction або compatibility layer без потреби.
- §1.5 Перед редагуванням знайти реалізацію, call sites, конфіг і перевірки.
  Серверний проєкт read-only: його код звідси не змінювати й не дублювати.
- §1.6 Операційні факти про патчі, рядки, шари, квоти й модерацію отримувати
  тільки через `./bdo`/Agent API. `TRANSLATE_PROJECT_ROOT` дозволяє лише targeted
  read/rg серверного контракту; shell, Docker, Artisan, SQL/БД, тести, запуск
  коду й будь-яка зміна зовнішнього проєкту заборонені. Потребу змінити API
  передавати власнику окремим промптом за `docs/API_CHANGE_HANDOFF.md`.

## §2 Публічний репозиторій і класи даних

- §2.1 Репозиторій та історія публічні. Заборонені у tracked/staged content,
  commit messages, prompts, відповідях і логах: API keys, tokens, passwords,
  private keys, cookies, session identifiers, credential/password/token/session
  hashes, private URLs, private hostnames, database dumps і персональні дані.
- §2.2 Усі чутливі значення зберігаються лише в локальному `.env` або у файлі,
  явно заданому `TRANSLATE_ENV_FILE`; обидва мають бути поза Git. У репозиторії
  дозволений лише `.env.example` з порожніми або безпечними публічними defaults.
- §2.3 `.env`, state, output, API responses, журнал викликів моделі і
  runtime logs не передавати remote/free моделям та не вставляти в issue/PR/chat.
- §2.4 `identity_hash`, `source_hash`, schema fingerprint і artifact checksum є
  технічними ідентифікаторами, а не credentials. Вони дозволені у мінімальному
  API/batch payload, але повний payload чи state dump публікувати заборонено.
- §2.5 Домашні абсолютні шляхи, приватна топологія, локальні usernames, e-mail та
  внутрішні URL не документувати. Публічні repo/domain URLs і нейтральні
  placeholders дозволені.
- §2.6 Якщо секрет потрапив у Git або зовнішній канал: зупинити роботу, не
  повторювати значення, повідомити власника, відкликати/перегенерувати credential,
  оцінити історію та логи. Видалення рядка новим комітом не скасовує витік.

## §3 Механічні security controls

- §3.1 `.gitignore` мусить ігнорувати root і nested `.env`, крім безпечного
  `.env.example`, а також `output/`, runtime dependencies та IDE metadata.
- §3.2 `.githooks/pre-commit` перевіряє staged snapshot, а не лише worktree:
  забороняє `.env*`, значення з локального env і відомі credential patterns.
- §3.3 Security hook не пропонує `--no-verify` як нормальний recovery path.
  Хибне спрацювання виправляється мінімальним уточненням pattern/test після review.
- §3.4 Docs gate сканує tracked files і нові файли поточної зміни, але не читає
  вміст `.env`, `state*` або `output/`. Значення env порівнює лише pre-commit hook.
- §3.5 Заборонено виводити знайдений секрет повністю. Повідомлення називає файл,
  line/type або ім'я ENV, достатні для локального виправлення.

## §4 Робоче дерево, Git і необоротні дії

- §4.1 До роботи й перед фіналом виконати `git status --short`, переглянути власний
  diff і не змінювати чужі незакомічені правки.
- §4.2 `git push` виконує ВИКЛЮЧНО власник. Агент не пушить ніколи · ні за
  дозволом, ні за проханням, ні «щоб завершити задачу». Те саме стосується всього,
  що змінює remote: force-push, `push --tags`, видалення чи перейменування
  віддалених гілок, зміна remote. Агент може лише сказати, що готове до push, і
  назвати гілку.
- §4.3 `git commit` агент виконує у двох випадках: власник попросив прямо, або
  агент спитав згоду й отримав її в цьому ж діалозі. Без цього коміту немає, навіть
  коли робота завершена й перевірки зелені. Дозвіл на один коміт не переноситься
  на наступні.
- §4.4 Заборонені без одноразового явного дозволу: force, rebase, tag, amend,
  зміна історії або remote state. Не використовувати `git add -A`, `git add .`,
  `git commit -a`; файли додавати переліком.
- §4.5 Commit message після дозволу строго відповідає
  `.codex/prompts/commit-message-ua.txt`, має зростаючу версію та не містить
  trailers, AI attribution або generated-by text. Backticks навколо
  ідентифікаторів дозволені; markdown-розмітка · ні.
- §4.6 Перед видаленням state/output, переписуванням історії, production write чи
  іншою необоротною дією назвати, що зникне, як відновити і що перевірити після.
- §4.7 `output/` і `state/` містять audit/cursors/quarantine. `./bdo clean` без
  `--apply` є preview; автоматично ці теки не видаляти.
- §4.8 `./bdo quarantine --clear` агент виконує САМ · дозвіл власника
  2026-09-04. Підстава не в тому, що дія дешева, а в тому, що вона не втрачає
  роботи: карантин є ДІАГНОСТИЧНИМ слідом, а не чергою. Перевірено
  2026-09-04 · жоден крок конвеєра не читає `state/quarantine.jsonl` (дві
  згадки в коді є коментарями), а самі рядки сервер віддає у вибірку доти,
  доки вони не записані й не стали пропозицією. Виключає рядок із вибірки
  окремий механізм · `state/row-attempts.jsonl` зі стелею
  `BDO_ROW_MAX_ATTEMPTS`, і `--clear` обнуляє його разом зі слідом; саме це й
  потрібно після виправлення причини. Слід при цьому не зникає: `--clear`
  доповнює ним `quarantine.jsonl.archived`, бо рівно цим слідом доведені D53,
  D56 і D58. Архів старіє за `BDO_KEEP_DAYS` і прибирається `./bdo clean`.

## §5 Реалізація, shell і PHP

- §5.1 Стек: Bash orchestration/HTTP transport, frameworkless PHP 8.3+ для
  identity/quality/batch logic, jq/curl і локальна Ollama.
- §5.2 Новий shell helper має `set -euo pipefail` де сумісно, usage, явні exit
  codes, quoted expansions і пояснення причини нетривіального guard.
- §5.3 Новий PHP код використовує `Bdo\Translate\`, наявний autoloader,
  typed contracts і `php -l`; framework або Composer dependency без потреби не
  додавати.
- §5.4 HTTP виконувати лише через штатні helpers/select-env flow. Не створювати
  ad-hoc `curl` write, alternate API client або model runner.
- §5.5 Поведінковий bug отримує regression test. Спершу вузький доказ, потім
  профіль `shell`, потім ширший gate.
- §5.6 Коментарі пояснюють причину й invariant. Не видаляти дороге обґрунтування;
  якщо причина змінилась, оновити її разом із кодом.
- §5.7 `cli/command-registry.json` є єдиним джерелом дерева команд, описів і
  execution guard. `docs/COMMANDS.md` генерується `php
  scripts/generate-command-docs.php`, не редагується вручну, а gate перевіряє
  його актуальність.

## §6 Translation identity, quality і state

- §6.1 Stable identity = `source_language + key0 + record_id + key1`.
  `identity_hash` повертається API без вигадування або зміни; candidate не може
  містити foreign, duplicate чи missing identity.
- §6.2 PA markup, placeholders і newlines копіюються байт у байт. Так само все,
  що API віддав у `tokens.must_preserve` (`keep`): це єдиний авторитетний перелік
  недоторканого, і рівно його перевіряє `Row::tokenViolations()`.
- §6.3 Manual, machine і proposal є різними шарами. Manual revisions, glossary,
  moderation decisions і audit history не стирати й не перезаписувати.
- §6.4 Підстановка згадок дозволена лише для предметів. NPC, location, lore та
  інші типи не розширювати без окремого game-tested contract: це валило гру.
- §6.5 Видимий український текст не містить російської, латинських гомогліфів у
  кириличних словах або `—`; використовувати `·` чи дефіс.
- §6.6 Batch state ізольований manifest-ом. Cursor рухається лише після завершення
  batch; dry run його не рухає. Audit receipts і quarantine append-only.
- §6.7 Робочий flow один · скриптовий драйвер `cli/run/run-loop.sh` і ролі на
  локальних моделях. Версія на оркестрації OpenCode законсервована 2026-09-04
  тегом `v3.0.6-opencode` і не є альтернативним entrypoint. Власний
  orchestrator замість цього flow не створювати.
- §6.8 Квадратні дужки зберігаються за структурою (кількість, позиція), а вміст
  усередині перекладається, якщо теґа немає в `keep`: у корпусі усталене
  `[Титул]`, не `[Title]`. Вимога «квадратні теґи байт у байт» механічної
  перевірки не мала й дала на прод-прогоні 2026-08-17 три розбіжності, усі гірші
  за наявний текст.

## §7 Agent API і production

- §7.1 Ціль прогону задає одна константа `BDO_ENV=PROD|DEV` у локальному `.env` і
  керує читанням та записом разом. Агент її читає (`./bdo env`), не обирає й не
  перемикає прапорцем. `BDO_ENV` є одночасно ціллю й дозволом: окремого
  підтвердження на прод-запис агент не запитує, бо свідомою дією власника є
  правка `.env`. Перед першою пачкою ціль оголошується одним рядком. Запис
  виконується лише коли запит означає переклад; запит-перевірка запису не дає.
- §7.2 Перед write виконується `/me`; capability/role не обходяться зміною layer.
  `machine+direct`, `manual+proposal` та `auto_approve` використовуються лише за
  чинним `API_WRITE_CONTRACT.md` і серверним контрактом.
- §7.3 Кожен write row проходить deterministic local gates і API validate.
  Problematic row іде в moderation, а transport/environment failure · у quarantine.
- §7.4 External/API calls мають bounded timeout/retry й не логують headers,
  credentials або повні sensitive payloads. Error schema/status трактуються за
  серверною документацією, не вгадуються.
- §7.5 Прогін pin-иться до одного environment. Зміна target посеред run
  відхиляється; префікс `BDO_API_ENV=`, що суперечить `.env`, валить скрипт замість
  тихого перемикання. Один `.env` містить ключ рівно одного середовища.

- §7.6 Коли потрібна зміна саме в API на серверному боці, агент каже це прямо
  («потрібна правка API на серверному боці») і дає ГОТОВИЙ промпт повним текстом
  у відповіді, а не посиланням на файл. У промпті: що зламано, доказ фактом
  (відповідь API, коди помилок, приклади рядків), потрібний контракт і що не можна
  зламати. Файл плану лишається записом, але він копія, а не заміна відповіді
  (рішення власника 2026-09-04: посилання на файл змусило власника шукати блок і
  питати, кому його віддати).
## §8 Ролі, драйвер і моделі

- §8.1 Порядок кроків тримає КОД. `cli/run/run-loop.sh` виконує конверт
  `./bdo run drive`; модель не вирішує, що робити далі, і не бачить стану пачки.
  Рішення власника 2026-09-04; причина · 14 із 45 записаних дефектів і 89%
  витрачених токенів припадали на LLM-диригента.
- §8.2 Роль отримує payload ФАЙЛОМ, який приготував рушій. Переказувати,
  скорочувати чи відновлювати його вміст заборонено: саме переказ дав 174
  порушення контракту й дефекти D16, D17, D36, D39.
- §8.3 Роль не має інструментів. `cli/model/client.php` шле повідомлення й читає
  відповідь; ні shell, ні API, ні вкладених викликів у неї немає за побудовою.
- §8.4 Модель ролі задає `config/roles.json` · єдине джерело. Роль без промпта
  або з моделлю, якої немає в `ollama list`, зупиняє `./bdo runtime` ДО пачки.
  Джерело правди після прогону · `state/model-calls.jsonl` і `./bdo audit`, а не
  самозвіт моделі.
- §8.5 Думання вимикається ЯВНО (`think: false`). «Не сказано» для думальної
  моделі означає ДУМАТИ: відповідь піде в `thinking`, а `content` лишиться
  порожній. Формат відповіді тримає `format` (constrained decoding).
- §8.6 Кожна відмова моделі має власну машинно-читану причину:
  `model_unreachable`, `model_error`, `truncated`, `context_overflow`,
  `empty_content`, `not_json`. Мовчазного повтору немає.
- §8.7 Staged schema не замінює детерміновані gates. Вона фіксує довжину й enum
  identity; `./bdo items`, перевірки якості й серверна валідація лишаються
  обовʼязковими.
- §8.8 Нову модель кваліфікувати кількома прогрітими прогонами, дотриманням
  формату, `./bdo runtime` і реальним аудитом. Один sample не є доказом якості.
- §8.9 Не створювати альтернативний спосіб виклику моделі. Санкціонований
  entrypoint один · `cli/model/client.php`.
- §8.10 Windows підтримується через WSL2 тим самим Bash/PHP flow. Окремий native
  PowerShell flow не створювати.
- §8.11 Prompts ролей розраховувати на найслабшу дозволену локальну модель.
  Вимоги: самодостатність; короткі наказові речення; один стабільний термін на
  поняття; нумеровані кроки без вкладеної прози; точні input/output JSON schema;
  явні stop-стани; приклад лише для усунення реальної неоднозначності. Identity,
  маршрут, повнота й безпека запису мають бути gates у коді, а не проханням у
  prompt.
- §8.12 Кожен `roles/<роль>.md` є повним і самодостатнім. Заборонені
  prompt-time `include`, вказівка моделі прочитати спільний файл або інша
  runtime-композиція: роль не має інструментів, а слабка модель пропустить
  залежність. Повторення дозволене заради надійності.
- §8.13 Еталонна «найслабша модель» названа: `qwen3.6:35b-a3b-mtp-q4_K_M`
  (курс власника на локальні моделі, 2026-08-27; повний перехід 2026-09-04).
  Правило промпта без механічної перевірки для локальної моделі є побажанням,
  тому кожне нове правило закривається grep-перевіркою в
  `scripts/agent-check.sh` або окремим тестом. Мовний зрив (чужа писемність,
  русизм, гомогліф) ловиться детектором у `lib/Quality/**`, бо промпт лише
  просить.
- §8.14 Prompt ролі задає рамку задачі: офіційна українська локалізація Black
  Desert Online, а рядок · назва предмета, опис, квест, вміння, інтерфейс або
  системне повідомлення. Межа обовʼязкова разом із рамкою: знання гри пояснює
  СЕНС, відповідник дають `glossary`, `terms`, `examples`, а спогад про чужу
  локалізацію (насамперед російську) не переноситься · саме звідти беруться
  русизми. Наявність рамки перевіряє `scripts/agent-check.sh`.
- §8.15 Драйвер не виконує рядків із конверта. Поле `command` ігнорується;
  наступна пачка відкривається з ПЕРЕВІРЕНИХ полів `goal` (режим зі списку,
  патч числом, категорія літерами). Невідоме значення зупиняє прогін.

## §9 Документація і плани

- §9.1 `docs/*.md` описують фактичний поточний стан. Плани живуть лише в
  `docs/plans/{backlog,active,done}` і синхронізуються з `README.md` та `BACKLOG.md`.
- §9.2 Новий план має status/date/registry header, scope, етапи й Definition of
  Done. `active -> done` лише з доказами або явною передачею залишку.
- §9.3 Зміна flow оновлює `docs/FLOW_STATE.md`; зміна API boundary ·
  `API_WRITE_CONTRACT.md`; зміна security · `docs/SECURITY.md`; навігація ·
  `docs/README.md`.
- §9.4 Документувати лише підтверджену поведінку. Неперевірений runtime/API факт
  позначити з причиною й ризиком, не перетворювати на твердження.
- §9.5 Публічна документація не містить приватних шляхів, host topology, ключів,
  state/API dumps або персональних даних.

## §10 Перевірки, завершення і формат звіту

- §10.1 Primary сам виконує `./bdo gate preflight` перед роботою і після зміни
  профілю/категорії. Перед завершенням він сам виконує
  `./bdo gate full && ./bdo api`. `full` охоплює локальні deterministic gates,
  але не викликає модель або API; API перевіряється окремо. Власник змінює лише
  `.env` і працює через меню `./bdo`; ці команди вручну не запускає.
- §10.2 Gate недеструктивний: не пише в API/production, не деплоїть, не видаляє
  state, не змінює Git. Профіль без реальної перевірки заборонений.
- §10.3 Не заявляти успіх без exit 0. Пропущена команда має точну причину,
  неперевірений аспект і ризик.
- §10.4 Фінальний diff перевірити на secrets, state/output/tmp, generated files,
  чужі зміни, scope drift і whitespace.
- §10.5 Фінал має рівно три блоки в цьому порядку: `## Підсумок` → `## Що зробив`
  → `## Що далі`, разом ≤ 20 рядків. Власник читає це між справами: за пʼять
  секунд він мусить зрозуміти стан, не читаючи весь звіт.
- §10.6 ПЕРШЕ слово `## Підсумок` · вирок, і лише один із цих: `ВИРІШЕНО`,
  `ЧАСТКОВО`, `НЕ ВИРІШЕНО`, `ЗАБЛОКОВАНО` (потрібне рішення власника),
  `ВІДПОВІДЬ` (задача без змін: аналіз, розвідка, питання). Далі одне речення що
  саме, а другим рядком обовʼязковий `Причина:` · корінь проблеми з доказом у
  дужках (`файл:рядок`, вивід команди або рядок логу). Причину не встановлено ·
  писати рівно `Причина: не встановлена` і що саме лишилось невідомим; здогад
  подавати лише зі словом `гіпотеза`. Рядок `Ризик:` · лише коли ризик реальний.
  Виправлення власної хибної заяви · окремий рядок тут же.
- §10.7 `## Що зробив` · до 5 пунктів, кожен один рядок: зміна і навіщо вона. Далі
  три рядки, присутні ЗАВЖДИ: `Перевірка:` (команда → результат; не виконана ·
  так і написати, з ризиком), `SEO-check:`, `OSM-check:`. Для цього CLI/docs repo
  два останні зазвичай `не застосовно`, але рядок лишається: власник переглядає
  їх окремо від решти. Фінал фіксує результат, а не переказує процес.
- §10.8 `## Що далі` при повністю досягнутій меті · рівно один рядок «Мету
  досягнуто, додаткова робота не потрібна.» Інакше · що лишилось, наступний крок,
  потреба від власника й Done criteria, кожен пункт із маркером `[потрібно]` або
  `[опційно]`. Вигадані варіанти й перенесення роботи з поточної задачі заборонені.
  Вирок `ВИРІШЕНО` заборонений, якщо релевантний gate не завершився з exit 0.

## §11 Еволюція правил

- §11.1 `AGENTS.md`, `.cursorrules`, `CLAUDE.md`, `QWEN.md` дослівно однакові.
  Зміна одного без трьох інших є gate failure.
- §11.2 Коротка карта не перевищує механічний line limit і не дублює цей довідник.
- §11.3 Нова норма не дублює чинну, має чітку область і, де можливо, механічний
  check у `scripts/agent-check.sh` (`./bdo gate`) або hook.
- §11.4 Номер правила сталий. Дублікат, номер чужої секції або посилання на
  неіснуюче `§N.M` є помилкою.

## §12 Клас відмови: тихий збій і фіктивна перевірка

Ця секція народжена з двох діб розбору 2026-08-25…27. Кожне правило тут має за
собою вимір, а не гадку; хронологію див. `docs/FLOW_STATE.md`.

- §12.1 Перевірка мусить проходити ТИМ САМИМ шляхом і тим самим артефактом, що й
  робота. `translation-smoke` півтора місяця мав власну спрощену схему, тому
  показував зелений маршрут на конфігурації, де жодна реальна роль не
  працювала: маршрут мав 0 успішних викликів із 3. Перевірка, яка не
  торкається того, що ламається, гірша за її відсутність · вона дає хибний
  спокій.
- §12.2 Порожній вивід не є відповіддю. Кожен вихід дає машиночитану причину.
  `mode start` і `run drive` вмирали під `set -e` мовчки, бо повідомлення про
  помилку осідало у змінній; за це згоріла сесія з двох десятків команд. Голе
  `x="$(cmd)"` там, де помилка можлива, є дефектом: або `if ! x="$(cmd)"`, або
  явний вивід причини.
- §12.3 Тест виконується на МЕЖІ дозволеного, а не на зручному розмірі. Схема з
  полем на рядок була бездоганною на двох рядках і ламала ліміт провайдера на
  ста, тобто дефект переїхав би з малих пачок на великі й проявився найпізніше.
- §12.4 Стан, який код пише, мусить хтось читати. `state/quarantine.jsonl`
  наповнювався з першого дня і не читався ніким: 18% рядків пачки осідали там
  мовчки. Лічильник `window_rollovers` писався і не використовувався. Або
  зʼявляється команда, що це показує, або запис прибирається.
- §12.5 Один вимір не робить правила, яке тихо викидає дані. `source_equivalent`
  оголосили невиправним за одним випадком (`AMD FidelityFX`), і на цьому втрачали
  18% пачки, бо в решті випадків воркер просто не переклав. Правило, наслідком
  якого є втрата рядка, вимагає вибірки, а не прикладу.
- §12.6 Виправлення мусить доходити до вже запущеної роботи. Раніше промпти й
  плагіни вантажились один раз на старті чужого застосунку, тому виправлений
  формат не діяв ні в старій сесії, ні в пачці, що вже висіла. Тепер промпт
  ролі читається з диска на КОЖНОМУ виклику, і цей клас зник; але правило
  лишається для будь-якого артефакту, який будується один раз на пачку ·
  staged-схема мусить перебудовуватись перед використанням.
- §12.7 Симптом «модель падає» вимагає розрізнення в коді, а не в чаті. Кожна
  відмова виклику має власну причину (`model_unreachable`, `empty_content`,
  `truncated`, `context_overflow`, `not_json`), і саме вона потрапляє в
  `state/model-calls.jsonl`. «Модель мовчить» без причини з журналу не є
  діагнозом.
- §12.8 Джерело правди про факт роботи · сервер, а не звіт агента. Після пачки
  перевіряти залишок через `./bdo patch <N>`, а поведінку ролей · через
  `./bdo audit`. Формулювання «пачка успішна» без цифри з API не приймається.

## §13 Термінал як робочий інструмент: PTY, видимість, запис екрана

- §13.1 Вікно перевіряється в справжньому PTY, і в цьому проєкті це `tmux`.
  Текстовий тест (`tests/tui.sh`) подає stdin каналом і читає stdout каналом ·
  він перевіряє ВМІСТ, але не термінал. Поза PTY не виконується `clear`, не
  вмикаються кольори (`[ -t 1 ]` хибний), невідомий розмір екрана й не працює
  `read` на клавіатурі. 2026-09-04 саме в цій щілині жив D62: екран «стан»
  малювався повністю, а вікно вилітало в оболонку з кодом 255. Живий тест ·
  `tests/tui-live.sh`; без `tmux` він пропускається ГОЛОСНО, а
  `BDO_REQUIRE_TMUX=1` робить його обовʼязковим.
- §13.2 MCP для термінала не потрібен і не існує. Пошук у реєстрі конекторів за
  `terminal`, `iterm2`, `tmux`, `tty` дав нуль результатів (перевірено
  2026-09-04), а доступний `read_terminal` лише ЧИТАЄ панель і не вміє
  надсилати клавіші. `tmux` умів обидва напрямки ще до появи MCP: `send-keys`
  пише, `capture-pane` читає. Тому шукати конектор під цю задачу не треба.
- §13.3 Довга робота йде у ВИДИМУ сесію. `./bdo watch loop|tui` запускає
  роботу в tmux-сесії `bdo`; агент читає екран через `./bdo watch --show`,
  власник підключається одною командою `tmux attach -t bdo` і відключається
  `Ctrl-b d`, не зупиняючи роботу. Прогін на десять хвилин у невидимому фоні
  залишає власника з німим екраном · він не бачить, на якому кроці пачка.
  Фон дозволений лише там, де видимість неможлива. Видимість має ДВІ частини:
  сесія (де дивитись) і зміст кроку (що саме дивитись). Другу дає
  `cli/run/step-report.sh` · запит і відповідь кожної ролі у її власній формі,
  з дублюванням у `state/run-transcript.log`. Рядок «роль X працює» видимістю
  не є.
- §13.4 Межа `watch` стоїть у КОДІ. Дозволено рівно `loop` (із `--once` або
  `--batches N`) і `tui`, будь-що інше падає з названою причиною. Без цієї межі
  один запис у allowlist guard відкривав би через `watch` усе дерево команд.
  Pane після завершення не закривається: останній екран і код виходу мусять
  лишитись видимими, інакше успіх і аварія виглядають однаково.
- §13.5 Запис екрана для документації · `./bdo gif` (`vhs`). Сценарій
  генерується з коду, а не лежить окремим файлом: інакше він розійдеться з
  меню тихо, як ручна копія дерева команд. Натискаються лише безпечні пункти
  (`6`, `7`, `q`); пункти, що запускають прогін, у записі не використовуються
  ніколи. Вихід · `docs/assets/*.gif`.
- §13.6 GIF є документацією, а не доказом. Красивий запис зробити легко й на
  зламаному вікні, тому «на GIF усе працює» вироком не є: працездатність
  доводить тест, який перевіряє коди виходу. `vhs` не є залежністю набору ·
  без нього `./bdo gif` падає з інструкцією `brew install vhs`, а не малює
  порожній файл.
- §13.7 `$VAR` перед багатобайтовим символом під `set -u` є дефектом:
  `«$SESSION»` bash читає як імʼя змінної разом із лапкою й падає
  `unbound variable`. Пишеться `«${SESSION}»`. Той самий клас уже ловив хук
  `commit-msg`, і він повторився в `watch.sh` 2026-09-04.
