# Нормативний довідник AI-агента

Це детальний контракт проєкту. Короткі правила в `AGENTS.md`, `.cursorrules`,
`CLAUDE.md` і `QWEN.md` маршрутизують сюди за категорією задачі; ці чотири
файли мають бути дослівно однакові.

## §1 Пріоритет, факти і межі задачі

- Вказівка власника має пріоритет, крім безпекових і юридичних обмежень.
- Не вигадувати файли, API, поля, flags, ENV, моделі, поведінку чи результати.
  Факт береться з коду, targeted read, `rg`, логу, тесту, команди або
  read-only документації серверного проєкту.
- Після двох еквівалентних невдалих спроб встановити причину й змінити підхід;
  третя ідентична спроба заборонена.
- Одна сесія має одну ціль і явний Definition of Done. Не додавати рефакторинг,
  dependency чи abstraction без конкретної потреби.
- Перед редагуванням прочитати реалізацію, call sites, конфіг і перевірки.
  Зовнішній серверний проєкт — лише read-only довідник; його shell, Docker,
  Artisan, SQL/БД, тести й записи заборонені.

## §2 Публічний репозиторій і класи даних

- У tracked/staged content, commit messages, prompts, відповідях і логах не
  потрапляють API keys, tokens, passwords, private keys, cookies, session
  identifiers, private URLs, private hostnames, dumps і персональні дані.
- Секрети живуть лише в локальному `.env` або файлі, заданому
  `TRANSLATE_ENV_FILE`; у Git дозволений лише безпечний `.env.example`.
- `.env`, `state`, `output`, API responses, журнали викликів і runtime logs не
  передаються remote/free моделям і не вставляються в issue, PR або чат.
- `identity_hash`, `source_hash`, schema fingerprint і artifact checksum —
  технічні ідентифікатори, не credentials; повний payload чи state dump не
  публікуються.
- Домашні абсолютні шляхи, приватну топологію, usernames, e-mail і внутрішні
  URL у публічній документації не фіксувати.

## §3 Механічні security controls

- `.gitignore` і hook захищають root/nested `.env`, `output/`, runtime
  dependencies та IDE metadata; pre-commit перевіряє staged snapshot.
- Docs gate сканує tracked/new content, але не читає `.env`, `state` або
  `output`; значення env порівнює лише pre-commit hook.
- Знайдений секрет не виводити повністю: назвати файл, рядок/тип або ENV.
  Якщо секрет уже витік, зупинити роботу і повідомити власника без повторення
  значення.

## §4 Робоче дерево, Git і необоротні дії

- До роботи й перед фіналом виконати `git status --short`, переглянути власний
  diff і не змінювати чужі незакомічені правки.
- §4.2 `git push` агенту НЕ дозволений: відправляє власник, а агент — лише за
  разовим явним дозволом у поточній задачі. Force-push, tags, rebase, amend,
  зміна remote state і переписування історії також потребують явного дозволу.
- `git commit` є частиною роботи. Файли додаються поіменно; `git add .`,
  `git add -A`, `git commit -a` і `--no-verify` заборонені.
- Commit message відповідає локальним правилам проєкту й не містить секретів,
  AI attribution або generated-by text.
- Перед видаленням state/output, production write або іншою необоротною дією
  назвати, що зникне, як відновити і що перевірити після.
- `./bdo clean` без `--apply` — preview. Налаштування Ollama, `keep_alive`,
  паралелізм і кількість резидентних моделей належать власнику; набір їх не
  перекриває.

## §5 Реалізація, shell і PHP

- Продукт — frameworkless PHP 8.3+ з наявним autoloader і typed contracts;
  shell лишається в development-оснастці.
- Новий shell helper має `set -euo pipefail` де сумісно, usage, явні exit codes
  і quoted expansions. Новий PHP код проходить `php -l` і не додає dependency
  без потреби.
- HTTP, модель і середовища використовують штатні helpers; ad-hoc write через
  `curl` або alternate model runner заборонені.
- Поведінковий bug отримує regression test: спершу вузький доказ, потім
  `./bdo gate touched`, потім ширша перевірка за картою.
- `cli/command-registry.json` — єдине джерело дерева команд, описів і guard;
  `docs/COMMANDS.md` генерується, вручну його не редагують.

## §6 Translation identity, quality і state

- Stable identity = `source_language + key0 + record_id + key1`. `identity_hash`
  повертається API без вигадування, зміни, duplicate чи missing identity.
- PA markup, placeholders, newlines і `tokens.must_preserve` (`keep`) копіюються
  за контрактом; перевіряє їх `Row::tokenViolations()`.
- `manual`, `machine` і `proposal` — окремі шари. Manual revisions, glossary,
  moderation decisions і audit history не стирати та не перезаписувати.
- Видимий український текст не містить російської, латинських гомогліфів у
  кириличних словах або `—`; використовувати `·` чи дефіс.
- Batch state ізольований manifest-ом. Cursor рухається лише після завершення
  batch; dry run його не рухає; audit receipts і quarantine append-only.
- Робочий flow один: PHP-драйвер `RunLoopCommand` і локальні моделі. Старий
  OpenCode flow не є альтернативним entrypoint.
- Квадратні дужки зберігаються за структурою, але їхній вміст перекладається,
  якщо теґа не входить до `keep`; у корпусі усталене `[Титул]`.

## §7 Agent API і production

- Одна константа `BDO_ENV=PROD|DEV` у `.env` керує читанням і записом. Агент
  читає її через `./bdo env`, не перемикає прапорцем і не змінює `.env` сам.
- Перед write виконується `/me`; layer, capability і `auto_approve` не обходять
  `API_WRITE_CONTRACT.md` або серверний контракт.
- Кожен write row проходить локальні gates і API validate. Problematic row іде
  у moderation, transport/environment failure — у quarantine.
- API calls мають bounded timeout/retry й не логують headers, credentials або
  повні sensitive payloads. Error schema/status не вгадуються.
- Прогін pin-иться до одного environment; суперечливий `BDO_API_ENV=` валить
  запуск замість тихого перемикання.
- §7.6 Коли потрібна зміна саме в API на серверному боці, агент каже прямо
  «потрібна правка API на серверному боці» і дає готовий промпт повним текстом.
  У ньому мають бути причина, фактичний доказ (відповідь API, коди, приклади),
  потрібний контракт і те, що не можна зламати. Формат —
  [`API_CHANGE_HANDOFF.md`](API_CHANGE_HANDOFF.md).

## §8 Ролі, драйвер і моделі

- Порядок кроків тримає код. `RunLoopCommand` виконує конверт `./bdo run drive`;
  модель не вирішує, що робити далі, і не бачить стану пачки.
- Роль отримує payload ФАЙЛОМ, який приготував рушій. Переказ, скорочення чи
  відновлення вмісту по памʼяті заборонені.
- Роль не має shell, API чи вкладених викликів; санкціонований entrypoint —
  `cli/model/client.php`.
- `config/roles.json` — єдине джерело моделі, схеми й температури. Джерело
  правди після прогону — `state/model-calls.jsonl` і `./bdo audit`.
- Думання передається явно (`think: false` або ввімкнений стан); `format`
  тримає constrained decoding. Кожна відмова має машиночитану причину:
  `model_unreachable`, `model_error`, `truncated`, `context_overflow`,
  `empty_content`, `thinking_loop` або `not_json`.
- Нову модель кваліфікувати прогрітими прогонами, strict format, `./bdo runtime`
  і аудитом; один sample не є доказом.
- §8.11 Prompts ролей розраховувати на найслабшу дозволену локальну модель:
  самодостатність, короткі наказові речення, стабільні терміни, нумеровані
  кроки, точні input/output JSON schema і явні stop-стани. Identity, маршрут,
  повнота й безпека запису мають бути gates у коді.
- §8.12 Кожен `roles/<роль>.md` є повним і самодостатнім. Prompt-time include,
  спільний файл, який модель мусить окремо прочитати, та інша runtime-композиція
  заборонені.
- §8.13 Еталонна «найслабша модель» названа: `huihui_ai/Qwen3.6-abliterated:35b-Claude-4.7-q4_K`;
  актуальне значення береться з `default_model` у `config/roles.json`.
- §8.14 Prompt ролі задає рамку задачі: офіційна українська локалізація Black
  Desert Online. Знання гри допомагає зрозуміти сенс, але не є джерелом
  українського відповідника; джерело — payload, glossary, terms і examples.

## §9 Документація і плани

- `README.md` — публічний quick start; `WORKFLOW.md` — користувацький flow;
  `docs/PROJECT_OVERVIEW.md`, `FLOW_STATE.md`, `API.md`, `SECURITY.md` і
  `CHECKLIST.md` — канонічні документи своїх тем.
- `docs/plans/README.md` — реєстр; `active/` — робота, `backlog/` — узгоджені
  незавершені рішення. Виконаний план видаляється після доказу; закриті
  дефекти не дублюються архівом.
- `docs/plans/DEFECTS.md` містить відкриті дефекти й прийняті ризики. Закритий
  дефект має regression test або gate до видалення з активного реєстру.
- Дзеркала правил не редагуються окремо: після зміни `AGENTS.md` всі чотири
  файли мають лишитися ідентичними.

## §10 Перевірки, завершення і звіт

- Мінімум перед завершенням зміни: `./bdo gate touched && ./bdo api`.
- §10.9 Пропорційна локальна перевірка й CI: `touched` — єдиний дефолт;
  невідомий шлях валить gate, доки для нього не визначено перевірку.
- Після власного дозволеного push чекати `gh run watch <id> --exit-status`.
- Фінальна відповідь українською має заголовки `## 🎯 Результат`,
  `## 🔧 Що змінилось`, `## ➡️ Що потрібно від тебе`; назви файлів, команди,
  ідентифікатори й логи не перекладати.

## §11 Еволюція правил

Правило, яке змінює поведінку агента, оновлюється в каноні разом із механічною
перевіркою. Не додавати разові симптоми, приватні дані або швидкозмінні версії.

## §12 Клас відмови: тихий збій і фіктивна перевірка

- Перевірка мусить проходити тим самим шляхом і тим самим артефактом, що й робота.
- Порожній вивід не є відповіддю; кожна команда повертає машиночитану причину.
- Тестують межу дозволеного і навмисно ламають властивість, яку gate стереже.
- Стан, який код пише, мусить хтось читати; один вимір не стає правилом, що
  тихо викидає дані.

## §13 Термінал як робочий інструмент

- §13.1 Вікно перевіряється в справжньому PTY через `tmux`; pipe не доводить
  кольори, розмір екрана, `clear` чи keyboard input.
- Довгу роботу запускати у видимій власникові сесії; `./bdo watch --show` читає
  те саме, що власник у `tmux attach -t bdo`.
- §13.6 GIF є документацією, а не доказом; доказ дає test або live-сесія.

## §14 Браузерний інтерфейс як основна поверхня власника

- `./bdo` без аргументів відкриває браузерний flow; сторінка лише перетворює
  кнопку на команду з `cli/command-registry.json`.
- Сервер читає `state/**`; дія виконується через POST і штатну команду.
  Запис у PROD захищений кодом, не checkbox у markup.
- `web/**` не містить другої бізнес-логіки: порядок і guards живуть у PHP.

## §15 Цілісність дизайну: система, а не набір випадкових стилів

- Кольори — токени `var(--…)` із `:root` в `web/app.css`, в обох темах.
- Розміри тексту — шкала 11/12/13; кнопки використовують наявні класи
  (`button`, `.btn-primary`, `.btn-danger`, `.chip`, `a.as-button`).
- Новий колір, розмір або стиль спочатку стає токеном/класом із причиною;
  перевірка — `./bdo gate shell`.

## §16 Браузер власника як обовʼязкова поверхня перевірки

- Браузерна перевірка бере вкладку власника через `./bdo browser` і
  `chrome-devtools` з `--autoConnect`; чистий профіль не є доказом.
- Якщо вкладку власника не вдалося підʼєднати, сказати це прямо і не підміняти
  її іншим браузером.
- `ЗАБОРОНЕНО без окремого слова власника`: видалення сесій/журналів, зміна
  `.env` і цілі прогону, а також будь-яка дія поза поточною задачею.
- §16.7 ОБОВʼЯЗКОВИЙ ПОРЯДОК ЗАКРИТТЯ ЗМІНИ В `web/**`: `./bdo browser`,
  `list_pages`/`select_page`, DOM snapshot, дія у вкладці власника, 3–5 live
  screenshots із паузою 1–2 секунди, console і network logs.
- Тест і gate не замінюють live browser: вони не бачать token, `localStorage`,
  темп показу й фактичну композицію екрана.

## §17 Одна сесія й делегування частин роботи

- §17.1 Робота ведеться однією локальною сесією; адресат — власник.
- §17.2 Process rules і плани агент править сам за погодженим рішенням і з
  перевіркою, яка це рішення тримає.
- §17.3 Приймання роботи — gate з кодом 0 і CI на точному SHA; слово агента не
  є доказом.
- §17.4 СПРОБА ЗЛАМАТИ НАВМИСНЕ обовʼязкова для кожної нової перевірки.
  Перевірка, яку не вдалося змусити впасти, нічого не стереже.
- §17.7 ДУМАННЯ НЕ ДЕЛЕГУЄТЬСЯ: рішення, пороги, приймання, коміт і push
  лишаються в головній сесії.
- §17.8 Шар РОЗРОБКИ і шар ПЕРЕКЛАДУ (`roles/*.md`, локальна Ollama) не
  плутаються.
- §17.9 ХТО ВИКОНАВ — умовний рядок лише коли власник просив делегування; без
  делегування його у звіті немає.
- §17.10 Маршрут делегування залежить від клієнта: спочатку перевірити доступні
  інструменти поточної сесії; у Codex використовувати нативний механізм
  сабагентів і не запускати вкладений `codex exec`; поза Codex викликати
  Codex-виконавця через `scripts/delegate-codex.sh`.

## §18 Мова реалізації: продукт проти оснастки

- Продукт — `./bdo`, `bdo.bat`, браузер, `cli/**` у шляху прогону, `lib/**`,
  model client і Agent API. Продукт працює на PHP без bash у робочому flow.
- Оснастка — `scripts/**`, `tests/**`, git hooks і діагностика; вона може лишатися
  на Bash.
- Межа визначається call site: якщо команду кличе сторінка, драйвер або
  `flow_commands`, це продукт; решта — оснастка.
- Підетап 9 етапу (перенос тестів у PHP) СКАСОВАНО: тести лишаються незалежним
  доказом, написаним іншою мовою.
