# Бригада: двигун виконавця й помічника

Двигун Бригади запускає дешевих агентів на вузьких задачах у двох ролях: помічник (лише
читання) — Codex через `exec.py scout`, робітник (код, тести, документація) — OpenCode
через `exec.py run`. Змінені файли й перевірки двигун Бригади збирає сам. Штатний субагент
клієнта головної сесії — лише за словом власника (розділ 12); процес і приймання
однакові. Мета — щоб токени сильної моделі йшли на план, рішення, діагноз і
приймання, а не на просту й середню роботу. Загальна частина цього
документа однакова в усіх проєктах і оновлюється скілом `brygada`;
проєктні прив'язки — у розділі «Цей проєкт» у кінці.

## 1. Ролі

| Роль | Хто | Робить | Не робить |
|---|---|---|---|
| Головна сесія | сильна модель у будь-якому клієнті (Claude Code, Codex, OpenCode…) | план, рішення (свої й власника), діагноз невдач, задачі виконавцю, приймання, жива перевірка, коміт; секрети, прод, дані, історія git | не пише код, тести й документацію сама, зокрема «дрібницю по ходу» |
| Робітник (виконавець) | типово OpenCode через `exec.py run` з моделлю `EXECUTOR_MODEL` (`opencode-go/deepseek-v4.1-flash`); штатний субагент — лише за словом власника (розділ 12) | код, тести, документація за готовим текстом, перевірки задачі, розвідка, дрібні технічні рішення (у `РІШЕННЯ` звіту) | не комітить, не пушить, не бере інших кроків, не вирішує питань цілі й архітектури |
| Помічник для розвідки | типово Codex через `exec.py scout` з `EXECUTOR_SCOUT_MODEL`/`EXECUTOR_SCOUT_EFFORT` (`gpt-6-luna`, `high`); штатний субагент — лише за словом власника | широкий пошук і читання з висновком, інвентар, браузерна перевірка за сценарієм | файлів не змінює |

Розвідку, яку не можна віддати робітнику (лише читання, багато файлів, потрібен
висновок), головна сесія віддає помічнику через `exec.py scout`, а не читає сама.
Без слова власника штатний субагент клієнта не запускається в жодній ролі. Збій
Codex чи OpenCode — діагноз і питання власнику, а не підміна субагентом (оновлення
Codex за `CODEX_UPDATE` — розділ 12). Субагент, що змінює файли, — це вже робітник:
лише через `prepare`/`finish` (розділ 12.1).

## 2. Файли двигуна Бригади

У репозиторії (git):

- `scripts/executor/exec.py` — двигун (стандартна бібліотека Python 3); керує скіл,
  вручну не правити;
- `scripts/executor/preamble.md` — правила й формат звіту для робітника: блоки між
  маркерами `executor-harness` керує скіл, між ними — проєктний розділ;
- `scripts/executor/scout.md` — межі й формат звіту помічника; керує скіл цілком,
  вручну не правити;
- `docs/EXECUTOR_HARNESS.md` — цей документ: блок між маркерами керує скіл, розділ
  «Цей проєкт» після нього — проєкт.

Поза git (`/.executor/` у `.gitignore`):

- `.executor/config.env` — необов'язкові налаштування (перекривають типові з коду);
- `.executor/mode.env` — вибір виконавців ролей власником; пише лише `exec.py mode` (розділ 12);
- `.executor/tasks/<назва>.md` — файли задач; `.executor/specs/<назва>.md` — довга
  специфікація, на яку посилаються кілька задач;
- `.executor/runs/<run-id>/` — теки прогонів (промпт, події, звіт, підсумок, логи перевірок).

## 3. Налаштування

Типові значення — у коді. Файл `.executor/config.env` (KEY=VALUE) їх перекриває,
`.executor/mode.env` (вибір власника, пише `exec.py mode`) — його, а змінні середовища
з тими самими іменами — обидва файли.

| Ключ | Типово | Значення |
|---|---|---|
| `EXECUTOR_MODE` | `opencode` | робітник: `opencode` або `native` (штатний субагент), розділ 12 |
| `EXECUTOR_MODEL` | `opencode-go/deepseek-v4.1-flash` | модель робітника |
| `EXECUTOR_SCOUT_MODE` | `codex` | помічник: `codex` або `native` (штатний субагент), розділ 12 |
| `EXECUTOR_SCOUT_MODEL` | `gpt-6-luna` | модель помічника |
| `EXECUTOR_SCOUT_EFFORT` | `high` | рівень міркувань помічника (`model_reasoning_effort`) |
| `EXECUTOR_SCOUT_TIMEOUT` | `900` | загальний ліміт прогону помічника, с |
| `EXECUTOR_SCOUT_MCP` | `playwright,context7` | сервери Codex, що лишаються ввімкненими й отримують дозвіл на інструменти; решта вимикається на прогін (розділ 9) |

| `EXECUTOR_TIMEOUT` | `1800` | загальний ліміт прогону, с |
| `EXECUTOR_IDLE_TIMEOUT` | `600` | секунд без росту логу = зависання |

| `EXECUTOR_CHECK_TIMEOUT` | `900` | ліміт однієї перевірки, с |

## 4. Формат задачі

Заголовок між `---`, тіло — вільний markdown:

```markdown
---
title: example-task
allow:
  - docs/example-output.md
checks:
  - test -f docs/example-output.md
model: opencode-go/deepseek-v4.1-flash   # необов'язково
timeout: 900                             # необов'язково
---
# Задача: <план> <крок> — <суть>

Створи `docs/example-output.md` з коротким описом того, що ти зробив.

- Один файл, кілька рядків.
- Наприкінці запусти перевірку із заголовка й запиши результат у звіт.
```

`allow` — glob-и дозволених файлів (`*`, `?`, `**`); `checks` — команди приймання,
які двигун Бригади запускає сам після прогону. Усе, що змінилося поза `allow`, двигун Бригади
позначить `OUT-OF-SCOPE`; зміни в межах `allow` іншого активного прогону — окремим
рядком `PARALLEL`.

Задача помічника (`scout`) — той самий заголовок, але `allow: []` (помічник нічого не
змінює), `checks` не запускаються. `output: raw` — відповідь рівно у форматі, який
просить тіло задачі (наприклад, лише JSON), без звіту; файл відповіді — у рядку
`output:` підсумку. Типово `output: report`.

## 5. Формат звіту

`report.md` (≤ 30 рядків) має п'ять блоків: `STATUS` (`done|partial|blocked`),
`ЗМІНИ`, `ПЕРЕВІРКИ`, `РІШЕННЯ`, `ПИТАННЯ`. Той самий текст виконавець повторює
наприкінці своєї відповіді — двигун Бригади бере з нього рядки від `STATUS:`, а `report.md`
лише як запасний шлях.

Звіт помічника (`scout.md`, ≤ 40 рядків) — останнє повідомлення з блоками `STATUS`,
`ВИСНОВОК`, `ДОКАЗИ` (`шлях:рядок` або команда), `НЕВІДОМО`.

## 6. Як запускати: власник має бачити, що працює виконавець

Запуск виконавця — видимий процес, а не мовчазна робота головної сесії.

- **Claude Code (CLI, десктоп):** КОЖЕН `run` — інструментом Bash з
  `run_in_background: true`, ніколи звичайною командою. Команда
  `python3 scripts/executor/exec.py run <task.md>` (без `--detach`), опис дії —
  мовою власника: `<підпис>: <план> <крок> — <суть>` (задача поза планом — просто
  `<підпис>: <суть>`). Завдання видно в панелі фонових завдань, поки виконавець
  працює; про завершення клієнт сповістить сам. Не опитувати, не читати лог під час
  роботи, не писати в чат «що передав / що він зробить».
- **Помічник** — так само: у Claude Code Bash з `run_in_background: true`, команда
  `python3 scripts/executor/exec.py scout <task.md>`, опис `<підпис>: <суть>`.
- **Підпис** — хто саме працює, рушій і модель, щоб власник бачив це в чаті. Готовий
  підпис дає `exec.py mode` рядками `LABEL worker …` і `LABEL scout …`, наприклад
  `Виконавець · OpenCode opencode-go/deepseek-v4.1-flash` або
  `Помічник · Codex gpt-6-luna high`. Модель задачі (`model:` у заголовку, `--model`)
  замінює модель у підписі. Штатний субагент — напр. `Виконавець · субагент Claude sonnet medium`:
  у Claude Code модель і рівень двигун бере з налаштувань клієнта й агента Бригади
  (розділ 12); `<модель>` лишається в підписі, лише коли модель не видно, — тоді
  підставити фактичну модель субагента. Так само для помічника. Той самий рушій
  із моделлю двигун друкує першим рядком живого виводу (`exec.py: <run-id> · …`).
- **Клієнт без фонових завдань** (Codex, OpenCode, Cursor): `run <task.md> --detach`
  або `scout <task.md> --detach`, далі `wait last` (або `wait <run-id>`) до коду не 4.
  Тільки тут `--detach` доречний.
- `--detach` у Claude Code заборонений: процес від'єднується від клієнта, і в панелі
  фонових завдань виконавця не видно.
- **Штатний субагент** (лише за словом власника): робітник — `prepare` → субагент →
  `finish`, розділ 12.1; видимість та сама — фоновий субагент з описом
  `Виконавець · субагент <клієнт> <модель>: …`; помічник — субагент лише для читання
  з описом `Помічник · субагент <клієнт> <модель>: …`.
- Поки прогін іде, головна сесія робить інше: наступну задачу, приймання попередньої,
  рішення, план.

## 7. Команди й коди виходу

```bash
python3 scripts/executor/exec.py run <task.md> [--model M] [--timeout S] [--keep] [--detach] [--self-model M]
python3 scripts/executor/exec.py scout <task.md> [--timeout S] [--detach] [--self-model M]
python3 scripts/executor/exec.py wait <run-id|last> [--max 540]
python3 scripts/executor/exec.py show <run-id|last> [--log|--diff|--check N]
python3 scripts/executor/exec.py clean [<run-id>|--all|--sessions]
python3 scripts/executor/exec.py mode [default|native|worker opencode|worker native|scout codex|scout native] [--model M] [--effort E] [--self-model M]
python3 scripts/executor/exec.py prepare <task.md>
python3 scripts/executor/exec.py finish <run-id|last>
python3 scripts/executor/exec.py --version
```

- `mode` — друкує по рядку на роль: `MODE worker opencode · <модель> · <джерело>`
  (або `MODE worker native · …`) і `MODE scout codex · <модель> <рівень> · <джерело>`
  (або `MODE scout native · …`), далі `CLIENT`, `LABEL`, у Claude Code `AGENT` (тип
  субагента ролі) і `ROUTE` для кожної ролі; з аргументами
  записує вибір власника (розділ 12).
- `scout` — прогін помічника: `codex exec` у sandbox `read-only`, без збереження сесії,
  MCP поза `EXECUTOR_SCOUT_MCP` вимкнено (розділ 9). Підсумок — рядок `SCOUT`, `report:`
  (звіт від `STATUS:`) або `output:` (для `output: raw`), `CHANGED` (файли, що змінились під час прогону: помічник у read-only їх не пише — це правки головної сесії чи інших; звір зі своїми, на код виходу не впливає),
  `PARALLEL` (зміни в межах `allow` паралельного робітника — не запис помічника), `artifacts` (знімки Playwright MCP, перенесені в
  теку прогону), `CODEX_UPDATE` (якщо треба), `tokens`, `details`.
- `prepare` / `finish` — прогін штатного субагента (розділ 12): `prepare` пише промпт
  і знімок стану, друкує `PREPARED <run-id>` і рядок для субагента; `finish` після
  субагента дає той самий підсумок, що й `run`, з міткою `native` замість моделі.

- `run` — прогін; `--keep` не видаляє сесію OpenCode; `--detach` запускає прогін у
  фоні й друкує один рядок `STARTED <run-id>`.
- `wait` — тихо чекає завершення (опитування раз на 5 с); не встиг за `--max` —
  друкує `RUNNING <run-id> <секунд>s`; фоновий процес помер без підсумку —
  `DIED <run-id>: <причина>`.
- `show` — підсумок; `--log` (хвіст подій), `--diff` (git diff змінених), `--check N`
  (лог перевірки).
- `clean` — прибрати теку прогону (`run`, `scout` чи `prepare`) і файл його задачі; `--all` — усі неактивні
  і задачі без прогону, старші за добу;
  `--sessions` — усі сесії OpenCode з назвою `exec-*`.

| Команда | Код | Значення |
|---|---|---|
| `run` | 0 | процес завершився (`done`) і всі `checks` дали 0 |
| `run` | 1 | інакше (не `done`, `no-status` — звіт без `STATUS:`, є check ≠ 0) |
| `run` | 2 | погана задача (заголовок не розібрано тощо) |
| `run` | 3 | `BUSY` — досягнуто ліміт паралельності |
| `run` | 5 | `SELF` — головна сесія на моделі робітника (розділ 12) |
| `scout` | 0 | `done` (є рядок `STATUS:` у звіті) |
| `scout` | 1 | інакше (помилка Codex, timeout, немає звіту, `no-status` — звіт без `STATUS:`) |
| `scout` | 2 | погана задача (зокрема непорожній `allow`) |
| `scout` | 3 | `BUSY` — досягнуто `EXECUTOR_MAX_PARALLEL_SCOUT` |
| `scout` | 5 | `SELF` — головна сесія на моделі помічника (розділ 12) |
| `scout` | 6 | `CODEX_UPDATE` — Codex застарів або модель не прийнята (розділ 12) |
| `run --detach`, `scout --detach` | 0 | друкує `STARTED <run-id>`; результат згодом дає `wait`; до старту — ті самі коди 2, 3, 5, 6 |
| `wait` | 0/1/6 | код завершеного прогону; `DIED` — 1 |
| `wait` | 2 | немає такого прогону |
| `wait` | 4 | ще триває (`RUNNING <run-id> <секунд>s`) |
| `show`, `clean`, `mode`, `prepare` | 0 | успіх |
| `finish` | 0 | є звіт зі `STATUS:` і всі `checks` дали 0 |
| `finish` | 1 | інакше (`no-report` — субагент не записав звіт, або check ≠ 0) |
| `finish` | 2 | прогін не з `prepare` або немає такого прогону |

Підсумок `run` — рядок `EXECUTOR`, звіт, `changed`, `OUT-OF-SCOPE`, `PARALLEL` (якщо
є), `checks rc` (для впалої перевірки — до 10 останніх рядків її виводу), `tokens`,
`details`. Для приймання його зазвичай досить.

## 8. Прибирання

Двигун Бригади сам видаляє сесію OpenCode після прогону; помічник сесій не лишає (`--ephemeral`). Тека `.executor/runs/<run-id>`
лишається, доки її не приберуть: `clean <run-id>` або `clean --all` (активні
прогони, зокрема ті, що ще проганяють перевірки, не чіпаються). Разом з останнім
прогоном задачі видаляється і її файл, якщо він лежить у `.executor/` (зокрема в
`.executor/tasks/`); `config.env` не чіпається ніколи. Специфікацію з
`.executor/specs/` головна сесія прибирає сама, коли прийнято останню задачу, що
на неї посилається. `clean --sessions` прибирає сесії OpenCode, якщо лишились.

`clean <run-id>` головна сесія робить одразу, щойно прогін більше не потрібен: після
коміту, після прочитаного звіту помічника, після відкинутого чи покинутого прогону.
Забуте двигун Бригади прибирає сам перед кожним новим `run`, `scout` чи `prepare`: неактивні
прогони, старші за добу (за часом останньої зміни теки), і файли `.executor/tasks/*.md`
без жодного прогону, теж старші за добу: черга задач, яку паралельна сесія ще не
запустила, так не зникає. Активні прогони не чіпаються; про прибране
двигун Бригади пише рядок `авто-прибирання .executor/: …` у stderr.

## 9. Які MCP вимкнено на прогін

Глобальний MCP `figma-desktop` у `~/.config/opencode/opencode.jsonc` має timeout
400000 мс: `opencode run` «висить» після init, бо чекає MCP і не звертається до
моделі (сесія `created`, `loop step=0`, але немає `stream`). `EXECUTOR_DISABLE_MCP`
вимикає такі MCP **лише на прогін** через `OPENCODE_CONFIG_CONTENT`, не змінюючи
глобальний конфіг. Кожен прогін піднімає власні MCP-процеси; двигун Бригади запускає
OpenCode у власній групі процесів і після завершення вбиває всю групу (`killpg`),
тож після прогону його MCP-процесів не лишається, а сторонні — не чіпаються.

Помічник так само: сервери з `~/.codex/config.toml` поза `EXECUTOR_SCOUT_MCP`
вимикаються на прогін (`-c mcp_servers.<назва>.enabled=false`), бо MCP-процеси пишуть
поза sandbox (Serena — `.serena/` у репозиторії). Сервери зі списку отримують
`default_tools_approval_mode="approve"`: підтвердити виклик без людини нікому.

## 10. Як головна сесія ставить задачі

Розділ однаковий для всіх проєктів. Що саме кожен проєкт визначає сам — у розділі
«Цей проєкт».

### 10.1 Куди йдуть токени сильної моделі

Сильна модель коштує в рази дорожче за виконавця, тож головна сесія витрачає її лише
на те, що виконавець зробить гірше або не має права робити:

| Головна сесія (сильна модель) | Робітник (`exec.py run`, OpenCode) | Помічник (`exec.py scout`, Codex, лише читання) |
|---|---|---|
| діагноз, вибір підходу, архітектура | код за описаним кроком | широкий пошук і читання багатьох файлів із висновком |
| рішення власника й запис у журнал | тести за переліком випадків | інвентар call sites, конвенцій, донора |
| план і файл задачі з уже знайденими фактами | документація за готовим змістом | браузерна перевірка за сценарієм |
| приймання: підсумок, вибірковий diff, жива перевірка | перевірки задачі (`checks`) | |
| коміт, прод, дані, секрети | розвідка в межах задачі | |

Правила економії:

- Не читати файл цілком, якщо досить місця з `rg` або кількох рядків навколо.
- Не читати лог прогону й повний diff за звичкою: підсумок `run` — основний доказ;
  `show --diff` — вибірково, за ризиком (нова логіка, безпека, дані), `show --log` —
  лише при невдачі.
- Не переказувати виконавцю те, що він прочитає сам у файлі: давати шлях і рядок-орієнтир.
  Не повторювати довгу специфікацію в кількох задачах: один файл `.executor/specs/…`
  і посилання на потрібні розділи.
- Не робити за виконавця «дрібницю по ходу»: це зсуває межу, і наступна сесія
  перестане її бачити. Дрібниця — окремий рядок наступної задачі або окрема мала задача.
- Не чекати без діла: поки йде прогін, готувати наступну задачу чи приймати попередню.

### 10.2 План чи задача без плану

- Типово — спершу план, потім виконавець. До першої задачі зміна записується в план
  проєкту: новий план або новий крок чинного. Чат не є планом: чого немає у файлі
  плану, того наступна сесія не побачить.
- Головна сесія ПЛАНУЄ, а не лише пише промпт: діагноз, межі й перевірка з'являються
  в плані до запуску, а не в голові сильної моделі.
- Задача без плану — лише коли вся зміна вміщається в один файл задачі й не
  потребує докладного опису (перейменування, одна правка тексту, одна функція з
  відомим місцем). Сумнів — значить, план.
- Одна задача — рівно один крок плану або етап, який план прямо називає однією
  задачею. Не два кроки разом і не половина кроку.

### 10.3 Крок, який можна віддати

Слабка модель погано шукає й погано вибирає, тому крок робить пошук і вибір
заздалегідь. Крок має:

- **Files** — точний перелік файлів; нові файли — поіменно.
- **Do** — чекліст дій: файл, функція чи рядок-орієнтир і що саме змінити. Для
  заміни — дослівний старий і новий фрагмент. Формули й алгоритми — словами або
  псевдокодом, без «як у попереднику».
- **Context** — уже знайдені факти: назви функцій, наявні класи, змінні, call sites,
  точні назви enum-ів і констант. Виконавець не має відкривати їх наново.
- **Verify** — що побачить головна сесія, коли крок зроблено (не «працює», а
  «у рядку X видно Y», «тест Z перевіряє W»).
- **If it fails** — як відкотити.
- **Notes** — рішення головної сесії й відкинуті варіанти, щоб виконавець їх не
  переобирав.

### 10.4 Розмір задачі

- Задача, яку виконавець робить за 5–15 хвилин, приймається найдешевше. Орієнтир:
  до ~8 файлів і однієї нової сутності з тестами до неї.
- Прогін, що вичерпав час без коду або з `partial`, — майже завжди завелика чи
  розмита задача. Не повторювати ту саму: розбити на кроки й дати зібрані факти.
- Велика специфікація — у `.executor/specs/`, а задачі посилаються на її розділи й
  перелічують, що вже зроблено попередньою задачею й на чому будувати.

### 10.5 Файл задачі

- `allow` — рівно `Files` кроку. Спільні файли, які одночасно правлять інші сесії, —
  з приміткою «лише новий блок у кінці, наявних рядків не змінювати».
- `checks` — базова статична перевірка проєкту плюс вузькі перевірки кроку, які
  можна запустити без браузера й без людини. Повний повільний набір тестів — не в
  `checks`: він запускається головною сесією послідовно перед комітом (два прогони
  одночасно ділять тимчасові ресурси тестів і дають хибні падіння).
- Тіло — посилання на крок плану і коротке повторення лише потрібного з нього:
  нумеровані дії з дослівними фрагментами. Виконавець читає план як контекст, а не
  як чергу.
- Явно — чого не робити: план, статуси, журнали, реєстри рішень, інші кроки, файли
  інших прогонів.

### 10.6 Запуск і паралельність

- Паралельно — лише незалежні кроки з `allow`, що не перетинаються, і не більше
  `EXECUTOR_MAX_PARALLEL`. Файли сусіда двигун Бригади покаже рядком `PARALLEL`, а не
  `OUT-OF-SCOPE`.
- Файли, які головна сесія правила під час прогону (журнал, план), теж потраплять у
  `changed` прогону: це не порушення виконавця.
- Помічників одночасно — не більше `EXECUTOR_MAX_PARALLEL_SCOUT`; вони нічого не
  змінюють, тож із прогонами робітника не конфліктують.
- Опис фонового завдання — `<підпис>: <план> <крок> — <суть>`, підпис із рушієм і моделлю (розділ 6).

### 10.7 Приймання

1. Підсумок `run`: код виходу, `STATUS`, `checks rc`, `OUT-OF-SCOPE`. Зміни поза
   `allow` спершу звірити з паралельними сесіями й прогонами, не відкочувати наосліп.
2. `show --diff` — вибірково: що зміна відповідає кроку й не зачепила зайвого.
3. `РІШЕННЯ` звіту — у журнал рішень проєкту й `Notes` кроку. `ПИТАННЯ` — головна
   сесія вирішує сама за порядком джерел проєкту; власнику — лише те, що необоротне,
   небезпечне або змінює ціль.
4. Жива перевірка тим самим шляхом, що й робота (браузер, команда, прогін на
   справжніх даних), до наступної задачі. Статична перевірка шаблонів, стилів і
   розмітки не бачить: зміна екрана без живої звірки не прийнята.
5. Перевірки, яких виконавець не має (інспекції IDE, повний набір тестів, живі
   дані), — головна сесія.
6. Знайдене на прийманні виправляє наступна задача (вужча, з дослівним фрагментом),
   а не головна сесія власноруч.
7. Коміт робить головна сесія, поіменно файлами кроку; потім `clean <run-id>`.
   Статус кроку `done` — лише після побаченого доказу.

### 10.8 Невдача

- `partial`, `blocked` або впала перевірка — `show --check N` чи `show --log`,
  діагноз, потім виправлений крок: вужчий, з доданим контекстом або дослівним
  фрагментом, і повторний прогін.
- Після двох однакових невдач — інший підхід: розбити крок, дати інший контекст,
  іншу модель (`--model`) або переглянути план. Третя ідентична спроба заборонена.
  Мовчки доробити код самій головна сесія не має.
- Дефект, знайдений на прийманні, — у реєстр дефектів проєкту одразу, виправлення —
  окремим кроком. Якщо дефект могла зловити машина, у тій самій задачі додати
  перевірку в гейт або CI.

### 10.9 Що визначає проєкт

У розділі «Цей проєкт» нижче, у правилах проєкту й у проєктному розділі
`preamble.md`:

- базову перевірку для `checks` і повний набір, який запускає головна сесія;
- де лежать плани, реєстр, журнал рішень і дефектів, і формат кроку;
- протокол живої звірки (браузер, прогін) і перевірки, яких виконавець не має;
- порядок джерел для самостійних рішень і перелік необоротних дій, перед якими
  треба зупинитись;
- формат коміту й версій;
- заборони для виконавця: секрети, прод, сервери, дані, git, мова коду й стиль.

## 12. Хто виконує: помічник, робітник і штатний субагент

Типова схема:

| Роль | Виконавець | Команда |
|---|---|---|
| Помічник (лише читання) | Codex, `EXECUTOR_SCOUT_MODEL` з `EXECUTOR_SCOUT_EFFORT` | `exec.py scout` |
| Робітник (код, тести, документація) | OpenCode, `EXECUTOR_MODEL` | `exec.py run` |

Інший виконавець обирає лише власник у чаті; головна сесія сама не перемикається,
навіть коли Codex чи OpenCode недоступний (тоді — діагноз і питання власнику).
Виняток — `CODEX_UPDATE` (код 6): виконати надруковану команду оновлення Codex без
питання власника й повторити задачу один раз; команди немає або після оновлення
знову код 6 — питання власнику.

Поточний стан — `python3 scripts/executor/exec.py mode`: перед першою задачею сесії
й після кожного перемикання. Вибір лежить у `.executor/mode.env` (поза git) і діє для
всіх сесій цього клону, доки власник не змінить його.

| Власник каже | Дія |
|---|---|
| «цю задачу / один раз — своїм субагентом» | режим не змінювати; ця одна задача — штатним субагентом тієї ролі, про яку йдеться |
| «надалі своїми субагентами» (роль не названо), «Бригада Клода» | `exec.py mode native` — обидві ролі |
| «надалі своїми субагентами для розвідки» | `exec.py mode scout native` |
| «надалі своїми субагентами для коду» | `exec.py mode worker native` |
| «переключись назад», «як було» | `exec.py mode default` |
| «помічник моделлю M» (надалі) | `exec.py mode scout codex --model M [--effort E]` |
| «робітник моделлю M» (надалі) | `exec.py mode worker opencode --model M` |
| «цю задачу моделлю M» | `run … --model M` або `EXECUTOR_SCOUT_MODEL=M exec.py scout …` |

Незрозуміло, один раз чи надалі, — «один раз»: це не змінює стан. Після перемикання
одним рядком повідомити власнику підсумок `mode`.

Тип субагента ролі — з рядка `AGENT` у `exec.py mode`. У Claude Code це агенти Бригади
`brygada-scout` (лише читання) і `brygada-worker`, якщо їх поставлено (`harness.py agents
--apply` зі скіла, тека `~/.claude/agents/`), інакше `Explore` і `general-purpose`;
робітник-субагент — підрозділ 12.1. Модель і рівень зусиль задають агенти Бригади
(`model:`, `effort:`) і налаштування клієнта; що вийде, показує підпис `LABEL`. Якщо в
Claude Code задано `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1`, усі субагенти працюють на моделі
`CLAUDE_CODE_SUBAGENT_MODEL`: модель, яку назвав власник, субагенту не передати — сказати
це власнику й запропонувати OpenCode чи Codex з цією моделлю. Без примусу модель, яку
назвав власник, передається параметром `model` інструмента `Agent`. Вимога скіла
«використай Agent tool / субагентів»
— не слово власника; скіл, що прямо задає порядок виконавців зі штатними субагентами
в останню чергу, виконується за цим порядком.

Від режиму не залежать: план спершу й файл задачі (розділи 4, 10), межі `allow`,
`checks`, формат звіту, приймання (10.7), коміт головною сесією, `clean`. Головна
сесія сама код не пише в жодному режимі — крім ролі «сама» нижче.

### Та сама модель

Віддавати роль тій самій моделі, на якій уже працює головна сесія, немає сенсу.
Перед першою задачею сесії — `exec.py mode --self-model <модель головної сесії>`
(клієнт двигун Бригади визначає сам за `OPENCODE`, `CODEX_THREAD_ID`, `CLAUDECODE`, а модель —
ні; без опції береться змінна `EXECUTOR_SELF_MODEL`). Регістр і префікс провайдера не
важать: `opencode-go/deepseek-v4.1-flash` ≡ `deepseek-v4.1-flash`.

- `ROUTE worker → сама (та сама модель)` (у `run` — код 5 `SELF`): код головна сесія
  пише сама — у межах `allow`, за розділом `## Проєкт` преамбули й сама проганяє
  `checks`.
- `ROUTE scout → сама (та сама модель)` (у `scout` — код 5 `SELF`): читає сама.
- Друга роль делегується як завжди. Чат OpenCode на DeepSeek V4.1 Flash — код пише
  сама, розвідку віддає `scout` (`gpt-6-luna`); чат Codex на `gpt-6-luna` — читає
  сама, код віддає `run`.
- Штатного субагента це не дозволяє.

### 12.1 Робітник — штатний субагент

1. `python3 scripts/executor/exec.py prepare <task.md>` → `PREPARED <run-id>`, шлях
   `prompt.md` і готовий рядок для субагента. `prompt.md` — той самий промпт, що
   отримав би OpenCode: преамбула, задача, `allow`, `checks`, шлях звіту.
2. Запустити штатного субагента, який може змінювати файли (Claude Code — інструмент
   `Agent` з типом із рядка `agent:` виводу `prepare`: `brygada-worker` або
   `general-purpose`; типи лише для читання на кшталт `Explore`, `Plan` чи
   `brygada-scout` не підходять). Промпт — рівно рядок `subagent:` з виводу `prepare`, без
   переказу задачі. Опис — `Виконавець · субагент <клієнт> <модель>: <план> <крок> — <суть>`; у Claude
   Code — `run_in_background: true`, після запуску не опитувати. Модель і рівень — за
   розділом 12; підпис — з рядка `agent:`.
3. Коли субагент завершився — `python3 scripts/executor/exec.py finish <run-id>`:
   двигун Бригади бере звіт із `report.md`, рахує `changed`, `OUT-OF-SCOPE`, `PARALLEL` і сам
   запускає `checks`. Далі — приймання за 10.7 і невдача за 10.8, як для OpenCode.
4. Паралельно — до `EXECUTOR_MAX_PARALLEL` незалежних задач з `allow`, що не
   перетинаються; `prepare` кожної — до запуску її субагента.

`finish` порівнює стан із моментом `prepare`: правки головної сесії між ними теж
потраплять у `changed`. Прогін без `finish` не прийнятий; `clean <run-id>` — після коміту.

## Цей проєкт

- **Проєкт і стек:** `bdo-ua-translate-python` — Python 3.13, uv, typer, FastAPI, sqlmodel,
  SQLite; публічний репозиторій (D-50).
- **Рішення про харнес:** [`DECISIONS.md`](DECISIONS.md) D-49, D-56, D-57 і D-58. `exec.py` приходить зі
  скіла без змін, тому виключений із `ruff` і `mypy`; `uv run bdo gate lint` перевіряє двигун
  `py_compile` і `--help`, не запускаючи OpenCode.
- **Ролі понад загальні:** автотестів немає (D-08) — виконавець тестів не пише; приймання
  кожного кроку — браузерна звірка головної сесії.
- **Базова перевірка в `checks`:** `uv run bdo gate` завжди.
- **Плани й журнали:** правила — [`PLANNING.md`](PLANNING.md), реєстр —
  [`plans/README.md`](plans/README.md), самостійні рішення —
  [`plans/EXECUTOR_DECISIONS.md`](plans/EXECUTOR_DECISIONS.md), дефекти —
  [`plans/DEFECTS.md`](plans/DEFECTS.md), журнал сесій — [`plans/PROGRESS.md`](plans/PROGRESS.md).
  Задача без плану — мітка коміту `Задача: …` (довідник §3.3).
- **Жива перевірка:** браузер через MCP Playwright за протоколом звірки (довідник §9.5), зі
  знімками в `.bdo/playwright/`, одразу після прогону, до наступної задачі.
- **Чого `uv run bdo gate` не бачить:** gate статичний і не рендерить шаблонів Jinja. Невідомий
  фільтр чи функція дає 500 лише на живій сторінці (P23: `thousands(x)` замість `x | thousands`
