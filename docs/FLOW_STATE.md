# Стан флоу: як конвеєр працює зараз

Цей документ описує ФАКТИЧНИЙ стан, а не намір. Плани живуть у
[`plans/`](plans/README.md), історія рішень попередньої архітектури · в
[`archive/FLOW_STATE_OPENCODE.md`](archive/FLOW_STATE_OPENCODE.md).

Початок: 2026-09-04, перехід на скриптовий конвеєр із локальними моделями.

Канонічний перелік команд · [`../cli/command-registry.json`](../cli/command-registry.json);
згенерований довідник · [`COMMANDS.md`](COMMANDS.md). Ручних копій дерева команд
у документації немає.

## 1. Хто чим керує

| Шар | Файл | Відповідає за |
|---|---|---|
| Інтерфейс | `bin/tui.sh` | меню режимів, вибір патча й категорії, екрани стану |
| Драйвер | `cli/run/run-loop.sh` | виконання конверта `run drive`, перехід між пачками |
| Рушій | `cli/run/run-drive.sh` | ЩО робити далі: стан пачки, ретраї, карантин |
| Машина станів | `lib/Pipeline/StateMachine.php` | які переходи дозволені |
| Клієнт моделі | `cli/model/client.php` | один виклик ролі під strict-схемою |
| Реєстр ролей | `config/roles.json` | модель, схема й температура кожної ролі |
| Промпти | `roles/<роль>.md` | що саме роль робить із payload |

Головне правило архітектури: **порядок кроків тримає код**. Модель не вирішує,
що робити далі, і не бачить стану пачки · вона отримує один payload і повертає
одну відповідь під схемою.

## 2. Життя однієї пачки

```
selected → awaiting_terminology → prepared → awaiting_worker
        → candidate_valid → deterministic_valid → awaiting_qa
        → qa_valid → healing → awaiting_judge → ready_to_commit
        → committing → committed → verified
```

Кожен перехід дозволяє `StateMachine::TRANSITIONS`. Драйвер не вигадує кроків:
він виконує рівно те, що назвав рушій, і зупиняється на невідомому `kind`.

Конверт рушія:

| `kind` | Що робить драйвер |
|---|---|
| `child` | кличе `cli/model/client.php` з роллю, payload і шляхом відповіді |
| `continue` | іде на наступний крок, причина в лог |
| `retry` | пауза з backoff; після `BDO_LOOP_SPIN_LIMIT` без руху стану · зупинка |
| `continue_run` | відкриває наступну пачку САМ, з перевірених полів `goal` |
| `complete` / `goal_complete` | завершує прогін |
| `blocked` | зупинка з причиною |

## 3. Контракт виклику моделі

`POST /api/chat` до Ollama з:

- `format` · JSON-схема ролі (constrained decoding, огорожі ```json не буває);
- `think: false` · ЯВНО. «Не сказано» для думальної моделі означає ДУМАТИ;
- `options.num_ctx` із `config/roles.json`;
- `stream: false`.

Кожна з цих відмов зупиняє крок і має власну причину:

| Причина | Що сталося |
|---|---|
| `model_unreachable` | endpoint не відповідає |
| `model_error` | Ollama повернула помилку |
| `truncated` | `done_reason != stop` · відповідь обрізало |
| `context_overflow` | вхід зайняв >90% реального вікна · початок могло викинути |
| `empty_content` | порожня відповідь; окремо названо випадок thinking |
| `not_json` | відповідь не розбирається як JSON |

Кожен виклик, успішний і невдалий, пише рядок у `state/model-calls.jsonl`.
Це джерело правди для `./bdo audit`.

## 4. Що робить кожна роль

| Роль | Вхід | Вихід |
|---|---|---|
| `translation-terminology` | невідомі терміни пачки | пропозиції відповідників |
| `translation-worker` | рядки пачки + глосарій + приклади | переклад кожного рядка |
| `translation-qa` | source + candidate | вирок PASS/REVIEW/REJECT на КОЖЕН рядок |
| `translation-repair` | рядки з вироком + причина | виправлений текст |
| `translation-judge` | спірні рядки | маршрут (шар / модерація), не текст |
| `translation-glossary` | черга термінів | опис або відповідник |
| `translation-smoke` | два рядки | доказ справності каналу |

Між моделлю й записом стоять механічні перевірки `lib/Quality/**`: гомогліфи,
русизми, чужа писемність, розмітка, плейсхолдери, межі довжини, глосарій.
Механічний дефект сильніший за вирок моделі.

## 5. Межі, які тримає код

- **Payload передається файлом.** Ніхто його не переказує.
- **Схема прибита.** Чужий ключ або чужий `identity_hash` неможливі.
- **Валідація повторюється перед записом**, уже після repair і судді.
- **Драйвер не виконує рядків із конверта.** Поле `command` ігнорується; виклик
  складається з перевірених полів `goal`.
- **Прогін не крутиться на місці**: стан без руху зупиняє драйвер із причиною.
- **Поверхні для довільної команди немає**: драйвер кличе лише `./bdo` і
  `cli/model/client.php`, а клієнт не має ні інструментів, ні shell.

## 6а. Якість чисто локального прогону · ВІДКРИТА ПРОБЛЕМА

Чотири пачки на `qwen3.6:35b-a3b-mtp-q4_K_M`, 200 рядків: 126 у шар, 1 у
модерацію, **73 у карантин** (від 30% до 50% на пачку).

| Пачка | У шар | Модерація | Карантин |
|---|---|---|---|
| `20260904_055351` | 35 | 0 | 15 |
| `20260904_060408` | 35 | 0 | 15 |
| `20260904_065800` | 31 | 1 | 18 |
| `20260904_070841` | 25 | 0 | 25 |

Причина встановлена вимірами, не здогадом:

1. рання валідація ЛОВИТЬ порушення (19 із 50 на пачці `065800`);
2. `heal-plan` шле їх у ремонт із наказовою вказівкою (17 рядків, 16 із
   «ужий «…» для»);
3. модель цю вказівку ВИКОНУЄ, якщо вона єдина · проба на 15 рядках дала 15/15;
4. на живих назвах не виконує: у 90 порушеннях 87 це `missing_translation`, і
   третина припадає на `Epheria Carrack: Balance` та `Epheria Carrack: Advance`
   (по 16 разів);
5. невиправлений рядок не приймає й канал модерації · сервер перевіряє глосарій
   тим самим правилом, тому рядок падає в карантин.

Перестановка вказівки на перше місце серед дефектів **не допомогла**: наступна
пачка дала 25 карантину з 50. Отже причина в тому, що модель переказує власну
назву, а не в доставці підказки.

Це **D53**. Поки він відкритий, локальний прогін коштує третини пачки.

## 7. Що ще не заміряно

- Чи виправляє repair порушення глосарія, коли отримує `details.glossary[].expected`
  прямою вказівкою · на пачці `20260904_055351` не виправив жодного з 15.
- Придатність локальної моделі до ролі судді на довгій дистанції.
- Чи інша локальна модель тримає глосарій краще: `gemma4:26b-a4b-it-mtp` за
  замірами 2026-08-28 гірша на QA, але як worker не перевірялась саме на
  дотриманні термінів.
