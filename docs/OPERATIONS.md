# Експлуатація

Як користуватися програмою, коли вона вже встановлена: де лежать дані, як
читати журнал, як керувати прогоном і що відбувається під час видалення.
Документ для власника й агента, який працює з уже запущеною програмою.

Схема стану й таблиці SQLite · [`ARCHITECTURE.md`](ARCHITECTURE.md).
Класи даних і правила публікації · [`SECURITY.md`](SECURITY.md).
Що робити, коли зламалося, · [`TROUBLESHOOTING.md`](TROUBLESHOOTING.md).

## Де що лежить

Тека даних · `.bdo/` у корені репозиторію. Її шлях задає змінна `data_dir`
(типово `.bdo`) у `settings.py`. Це поле `pydantic-settings`, тому
перекрити його можна й змінною оточення `DATA_DIR` — так і роблять пісочницю
з окремою текою даних. Змінна оточення має вищий пріоритет за `.env`, тож
поряд із `BDO_ENV_FILE` задавайте й `BDO_WEB_PORT`: інакше порт із шаблонного
`.env` перекриє пісочницю.

| Шлях | Що це |
|---|---|
| `.bdo/bdo.sqlite` | база SQLite: сесії, пачки, рядки, виклики, вироки, записи, черги. `queue_reasons` живе довше за сесію — див. «Видалення сесії» |
| `.bdo/bdo.sqlite-wal`, `.bdo/bdo.sqlite-shm` | службові файли SQLite у режимі WAL; з’являються, поки база відкрита |
| `.bdo/web.log` | журнал вебпроцесу; JSON-рядки |
| `.bdo/web.pid` | pid запущеного вебпроцесу; його читає `webctl.py` |
| `.bdo/web.started` | мітка часу останнього старту; від неї рахуються знімки звірки |
| `.bdo/web.restarting` | короткочасна мітка перезапуску сервера; зникає після нього |
| `.bdo/browser/` | знімки браузерної звірки, якщо браузерний канал може зберегти їх на диск (`*.png`) |

Тека `.bdo/` під `.gitignore` і містить приватні дані: не комітити, не
передавати віддаленим моделям, не показувати в звітах ([`SECURITY.md`](SECURITY.md)).

## Як читати журнал

`.bdo/web.log` пише вебпроцес. Записи самого застосунку · один JSON-обʼєкт на
рядок: `ts`, `level`, `logger`, `msg`, за потреби `exc`. Налаштування ·
`logging_setup.py`. Поряд із ними у файл потрапляють зовнішні рядки (httpx,
uvicorn) і цілі трейсбеки Python — вони не JSON, і їх у журналі **багато**:
файл співмішаний, тож «останні 20 рядків» можуть не містити жодного JSON.

Щоб читати лише записи застосунку, фільтруйте їх:

```bash
rg '^\{"ts"' .bdo/web.log | tail -n 20
```

Секрети в журнал не потрапляють: `RedactSecrets` редагує значення за шаблонами
(`x-api-key`, `authorization: bearer`, `api_key`/`token`/`secret`/`password`,
`sk-…`) **до** форматування рядка. Проте журнал лишається приватним файлом —
не вставляйте його в чат цілком.

Безпечний перегляд хвоста (читає лише, нічого не змінює):

```bash
tail -n 40 .bdo/web.log
```

Потрібні лише повідомлення без службових полів:

```bash
tail -n 200 .bdo/web.log | sed -n 's/.*"msg": "\(.*\)".*/\1/p'
```

Ще один спосіб · екран «стан» (`/status`) показує останні 20 рядків журналу й
перевірку редагування секретів.

## Як подивитися стан БД

`.bdo/bdo.sqlite` — звичайна SQLite. Читати можна лише **через запити
`SELECT`**, бажано з `sqlite3` у режимі лише читання:

```bash
sqlite3 "file:.bdo/bdo.sqlite?mode=ro" "SELECT status, count(*) FROM sessions GROUP BY status;"
```

```bash
sqlite3 "file:.bdo/bdo.sqlite?mode=ro" "SELECT id, state, reason FROM batches ORDER BY updated_at DESC LIMIT 10;"
```

Корисні таблиці: `sessions`, `batches`, `batch_rows`, `fetch_diagnostics`,
`calls`, `verdicts`, `transitions`, `writes`, `deferred`, `quarantine`,
`queue_reasons`. Повний
опис полів · [`ARCHITECTURE.md`](ARCHITECTURE.md).

Порахувати відкладені рядки за середовищем, режимом і причиною без показу
текстів та ідентифікаторів:

```sh
sqlite3 "file:.bdo/bdo.sqlite?mode=ro" "SELECT s.env, s.mode, d.reason, count(*) FROM deferred d JOIN batches b ON b.id = d.batch_id JOIN sessions s ON s.id = b.session_id GROUP BY s.env, s.mode, d.reason ORDER BY s.env, s.mode, d.reason;"
```

Щоб звірити порядок ручного повтору, виконайте обидва наступні запити через
той самий режим лише читання. Перший — перед натисканням кнопки; замініть
`<mode>` на режим джерела невдалої або порожньої сесії:

Приклади нижче використовують стандартний файл `.bdo/bdo.sqlite`. Для
ізольованого DEV-сервера замініть URI `file:.bdo/bdo.sqlite?mode=ro` на
`file:<DATA_DIR>/bdo.sqlite?mode=ro`, де `<DATA_DIR>` — каталог даних цього
сервера. Так запит читає саме базу середовища, яке перевіряється.

```sh
sqlite3 "file:.bdo/bdo.sqlite?mode=ro" "SELECT d.identity_hash FROM deferred d JOIN batches b ON b.id = d.batch_id JOIN sessions s ON s.id = b.session_id WHERE s.env = 'DEV' AND s.mode = '<mode>' AND d.reason IN ('truncated', 'not_json', 'schema_mismatch', 'answer_loop', 'thinking_loop', 'empty_content', 'stream_incomplete', 'timeout', 'context_overflow', 'missing_item') ORDER BY d.created_at, d.identity_hash;"
```

Другий — після прогону; замініть `<retry-session-id>` на ID нової сесії:

```sh
sqlite3 "file:.bdo/bdo.sqlite?mode=ro" "SELECT br.identity_hash FROM batch_rows br JOIN batches b ON b.id = br.batch_id WHERE b.session_id = '<retry-session-id>' ORDER BY b.seq, CAST(substr(br.alias, 2) AS INTEGER);"
```

Порівняйте списки локально й залиште ідентифікатори лише в терміналі. За
правилами [`SECURITY.md`](SECURITY.md), не копіюйте їх у звіти, скриншоти, чати
чи стороннім моделям. У нотатки плану запишіть тільки кількість і результат
звірки.

**Ручне редагування бази заборонено.** Канон правил (`AGENTS.md`) забороняє
правити `.bdo/` вручну: `UPDATE`, `DELETE`, `INSERT`, `ALTER`, зміна
`user_version` ламають стан пачки й журнал. Потрібні зміни робляться через
інтерфейс (видалення сесії, архівування карантину) або з дозволом власника.

Зверніть увагу на URI-префікс у наведених прикладах: `sqlite3 "file:...?mode=ro"`
відкриває базу **лише на читання**. Звичайний `sqlite3 .bdo/bdo.sqlite` відкриває
її на запис і створює службові `-wal`/`-shm` — для читання так не робіть.

## Прогін: пауза, стоп, відновлення

Кнопки на екрані «прогін» (`/run`):

| Кнопка | Дія | Наслідок |
|---|---|---|
| «пауза» (`btn-run_pause`) | `runner.pause()` | поточний крок доходить до кінця, пачка переходить у стан `paused`, сесія · `paused`; зберігається точка відновлення |
| «зупинити» (`btn-run_stop`) | `runner.stop()` | сесія завершується після поточної пачки; статус `stopped`, причина «зупинено власником» |
| «продовжити» (`btn-run_resume`) | `runner.resume(session_id)` | сесія продовжується з збереженої точки відновлення; кнопка зʼявляється лише коли сесію можна відновити |
| «повторити відкладені» (`btn-run_retry_deferred`) | доступна на невдалій сесії або завершеній сесії з порожньою вибіркою, якщо є придатні рядки; створює нову сесію з рядками активного середовища й того самого режиму джерела, що й вибрана сесія; показує кількість; бере тимчасові відмови моделі та `missing_item` (worker не повернув переклад). У режимі пропозицій використовує актуальний текст пропозиції | після успішного запису рядок втрачає мітку `deferred`; якщо API більше не має рядка (404), він отримує причину `row_not_found` і далі не пропонується для повтору |
| «перекласти все» (`start-all`) | на `/start` для активного патча без категорії передає `include_deferred`; прогін спершу бере придатні відкладені, а залишок пачки заповнює новими рядками; кількість пачок рахується за більшим із числа рядків без ШІ-шару та локальної черги повтору | нові й відкладені рядки проходять той самий конвеєр; після успішного запису мітка `deferred` зникає |

«Пауза» й «зупинити» показуються **лише під час активного прогону** · коли
сесія має статус `running` (`controls_enabled` у `run.html`). Коли прогону
немає, цих кнопок на екрані немає взагалі.

Наслідок для рядків: на паузі й після зупинки жоден рядок не губиться.
Рядки, що не встигли дійти до запису, лишаються відкладеними (таблиця
`deferred`). Звичайний прогін без перемикача «перекласти все» їх пропускає;
перемикач на активному патчі без категорії спершу добирає придатні відкладені,
а залишок пачки заповнює новими рядками. Точковий повтор для конкретної сесії робить кнопка
«повторити відкладені». Уже записане лишається записаним.

Пауза і стоп діють на поточну сесію; кнопки змінюють стан наступного кроку,
тож ефект видно після завершення кроку, а не миттєво.

## Карантин і черга: що робити з рядком

Екран «карантин і запис» (`/queue`) показує три списки:

| Список | Таблиця | Що це |
|---|---|---|
| Відкладені | `deferred` | рядок конвеєр лишив на повтор: збій мережі, тимчасова відмова, ліміт або worker не повернув окремий переклад (`missing_item`). Причина · в полі `reason` |
| Карантин | `quarantine` | рядок із проблемою, яку конвеєр не міг розвʼязати сам: відмова API без можливості повтору, невідомий статус запису |
| Локальна модерація | `batch_rows` з фільтром `route = 'moderation'` | рядки, які конвеєр відправив у чергу до людини: механічний дефект, відмова QA, рішення судді |

Різниця відкладеного й карантинного: відкладені — рядок **ще може** бути
перезапущений після усунення причини кнопкою повтору (у звичайних режимах
звичайний прогін їх не бере сам, у режимі пропозицій автоматично добираються
лише транспортні причини; ручний повтор бере дозволені причини й працює з
актуальним текстом пропозиції); карантинні
повернуться **самі** ніколи, їх треба розібрати вручну.

Кнопка «Архівувати карантин» (`btn-quarantine_clear`) позначає активні записи
карантину як `archived` — це **не видалення**: історія лишається в базі, просто
ховається зі списку ([`COMMITS.md`](COMMITS.md)).

Черга до людини на сайті (пропозиції API) і локальна модерація — різні
списки; пропозиції живуть на сервері, локальні причини — у базі
(`queue_reasons`). Але `queue_reasons` заповнюється **лише** для каналу
`proposal` · рядок із маршрутом `moderation` туди не потрапляє, тож причину
такого рядка шукайте в `batch_rows`.

У `batch_rows` лежать усі рядки пачки, а не лише черга: маршрут `route`
має значення `machine`, `manual`, `proposal`, `moderation`, `deferred` і
`quarantine`. Перед читанням відфільтруйте за потрібним.

## Видалення сесії

Кнопка «видалити сесію» на екрані «сесії роботи» (`/sessions`) видаляє
завершену сесію разом із локальними записами, привʼязаними до її пачок:
`calls`, `verdicts`, `transitions`, `batch_rows`, `writes`, `deferred`,
`fetch_diagnostics`, `quarantine`, `batches`, `term_cache`, `sessions`. Після
цього база стискається (`VACUUM`). Кнопки немає під час прогону — спершу
зупиніть сесію (D-47).

Що лишається на сервері: **усе**. Переклади, пропозиції, модерацію й глосарій
зберігає Agent API; видалення сесії локальних даних їх не змінює. Документованого
ендпоінта видалення перекладів API не має.

Локальний лічильник спроб (`row_attempts`) не має привʼязки до сесії, тож
лишається глобальним. Те саме · `queue_reasons` (причини черги до людини): вони
живуть довше за сесію й привʼязані до `identity_hash` та середовища, а не до
пачки.

## Видалення `.bdo/`

Видалення теки `.bdo/` стирає **всю** локальну історію: базу з сесіями, пачками,
викликами, вироками, записами й чергами, журнал `web.log` і знімки звірки.
Ключі з `.env` при цьому **лишаються** — `.env` лежить у корені репозиторію,
а не в `.bdo/`.

Канон правил (`AGENTS.md`) забороняє видаляти `.bdo/` вручну; винятків
немає, і звичайний дозвіл на іншу задачу її не знімає. Якщо власник хоче
саме цю дію, потрібен **окремий дозвіл саме на неї**
([`COMMITS.md`](COMMITS.md)). Перевірте, чи не лишилося важливого:

- сесії, які ще знадобляться для звірки або статистики;
- журнал `web.log`, якщо в ньому шукали причину збою;
- знімки звірки в `.bdo/browser/` або у чаті, якщо штатний браузер не може зберегти файл.

Після видалення програма створить `.bdo/` знову на першому старті, а база —
порожньою.

## Квота

Денна квота рядків приходить із ключа API: `GET /me` → `limits`
(`rows_per_day`, `rows_remaining_today`, `quota_resets_at`). Квота спільна на
акаунт і скидається до київської півночі.

Що робить програма, коли квота вичерпана:

1. `validate` або `write` повертає код `daily_row_quota_exceeded`.
2. Рядки, які не встигли записатися, йдуть у `deferred` з тією ж причиною —
   вони **не** в карантині й **не** втрачені.
3. Сесія зупиняється: статус `stopped`, причина `daily_row_quota_exceeded`;
   пачка переходить у `failed_terminal`.
4. Повтор — після опівночі за київським часом: квота скидається, відкладені
   рядки лишаються відкладеними, тож наступний прогін їх не візьме без ручного
   рішення (див. [`TROUBLESHOOTING.md`](TROUBLESHOOTING.md)).

## Версії

```bash
uv run bdo version
```

Друкує версію пакета (рядок 1 коміту). Вона має збігатися з `pyproject.toml`,
`src/bdo_translate/__init__.py` і `uv.lock`.

Версія запущеного сервера · ендпоінт здоров'я:

```bash
curl -s http://127.0.0.1:7660/health
```

Відповідь · `{"ok":true,"version":"<версія>","env":"DEV|PROD","busy":false}`.
`busy: true` · триває прогін.

Перезапуск сервера:

```bash
uv run bdo web restart
```

Код 3 · сервер зайнятий прогоном (`busy`), перезапуск відкладено: дочекайтеся
кінця прогону. Код 0 · сервер перезапущено, команда друкує нову адресу й
версію.

**Увага:** версія на сервері власника може бути старшою за HEAD репозиторію —
сервер запускається з копії коду, яка була в момент старту. Звіряйте
`/health` і `uv run bdo version`, перш ніж судити про нову поведінку.
