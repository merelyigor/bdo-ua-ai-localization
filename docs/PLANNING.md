# Система планування

Плани · єдине джерело задач для агента-розробника. Чат джерелом правди не є:
чого немає в `docs/plans/`, того для наступної сесії не існує.

## Файли

| Файл | Питання | Хто веде |
|---|---|---|
| `docs/plans/README.md` | реєстр активних планів і наступний номер | агент, тим самим комітом, що змінює статус |
| `docs/plans/P0N-<slug>.md` | виконуваний план фази: кроки з чеклістами | агент під час виконання |
| `docs/plans/DEFECTS.md` | що ламалось, клас, регресія | агент у момент діагнозу |
| `docs/plans/BACKLOG.md` | відкладені ідеї з причиною і ознакою готовності | агент у момент рішення власника |
| `docs/plans/PROGRESS.md` | журнал сесій: дата, план, кроки, gate, коміт; єдиний слід закритого плану в дереві | агент наприкінці кожної сесії й на закритті плану |

## Статуси плану

| Статус | Значення | Перехід |
|---|---|---|
| `draft` | написаний, власник не підтвердив | → `approved` словом власника |
| `approved` | можна брати в роботу | → `in-progress` з першим кроком |
| `in-progress` | є кроки `done`, DoD не виконаний | → `done` або `blocked` |
| `blocked` | стоп-умова; причина в `Notes` кроку | → `in-progress` після рішення власника |
| `done` | усі кроки `done`/`skipped`, Final verification зелена | файл видаляється (правило 5) |

## Статуси кроку

`pending` · `in-progress` · `done` · `blocked` · `skipped` (лише з причиною в
`Notes`). Чекбокс ставиться після дії І побаченого доказу; наперед · ніколи.

## Формат плану

Кожен план має заголовок-таблицю (ID, статус, дати, джерело), `Goal`,
`Definition of Done`, `Scope`, `Non-goals`, `Constraints`, `Context for the
executor` (робоча тека, ключові файли, канонічні команди), `Instructions for
the executor`, фази з кроками, `Final verification`, `Rollback`, `Progress
log`. Крок має `Status`, `Depends on`, `Files`, `Why`, `Do` (чекліст), `Verify`
(чекліст із очікуваним результатом), `Done when`, `If it fails`, `Notes`.
Еталон · активний план у `docs/plans/` або останній закритий з історії git.

## Правила виконання

1. Плани по черзі реєстру; закрила план · сесія бере наступний. Почати з
   першого кроку не `done`/`skipped`.
1а. Сесія, що веде план, · головна сесія: вона бере кроки, веде статуси,
   `Notes`, `Progress log`, `EXECUTOR_DECISIONS.md`, звіряє й комітить. Код
   кроку делегується за актуальним глобальним skill `brygada`; одна задача має
   вузький явний обсяг, прив'язаний до кроку плану. Нижче «виконавець» · сесія,
   що веде план.
2. Крок виконується за планом. Розбіжність плану з кодом, API чи бібліотекою
   вирішується за п. 2б; `blocked` · лише стоп-умова плану або необоротна дія.
2а. Приймання кроку · лише звірка у браузері через MCP Playwright за
   протоколом у заголовку плану; unit-тести не пишуться (D-08, D-33).
2б. Автономія: прогалину чи розбіжність виконавець вирішує сам за порядком
   джерел довідника §5.5 і пише рядок у `EXECUTOR_DECISIONS.md`; зупинка й
   питання в чаті лише перед необоротним (PROD, `.env`, секрети, видалення,
   push, віддалені моделі, зміни поза репо). Кожен план містить це правило
   пунктами 10 і 10а в «Instructions for the executor».
3. Кожне відхилення · датований рядок у `Notes` кроку; кожен закритий або
   заблокований крок · рядок у `Progress log` плану.
4. Checkpoint фази: `uv run bdo gate` зелений, ЗВІРКА фази зі знімками,
   commit поіменно, версія за D-32, рядок у `PROGRESS.md`.
4а. Повідомлення коміту · за довідником §3.3 (власник, 2026-09-27):
   `git commit -m "P0N: …"` у кроці плану задає перше речення абзацу; рядок
   `Версія: X.Y.Z` (PATCH +1 від HEAD, закриття плану · `0.N.0`), оновлення
   `pyproject.toml`, `__version__`, `uv.lock` і блок `Файли:` головна сесія
   додає сама під час коміту. Кроки планів поштучно не переписуються.
5. Закриття плану (власник, 2026-09-30): `Final verification` зелена,
   `Definition of Done` весь відмічений; тим самим комітом файл плану
   видаляється (`git rm`), його рядок прибирається з реєстру, а в
   `PROGRESS.md` лягає рядок-підсумок (кроки, версія, що тепер працює).
   Архіву закритих планів у дереві немає: повний текст · в історії git.
   Застарілий план, який уже не буде виконано, видаляється так само з
   рядком у `PROGRESS.md` і причиною. Відкладене · у `BACKLOG.md`, а не в
   недописаному плані.
6. Дефект, знайдений під час виконання · рядок у `DEFECTS.md` одразу; якщо він
   поза scope плану · ще й рядок у `BACKLOG.md`.
7. Новий план пише лише сильна модель або власник; делегований виконавець
   планів не створює й не редагує, а блокування або питання поза межами задачі
   повертає головній сесії.

## Як власник запускає сесію

Промпт для моделі-розробника (дослівно, з `README.md`):

```text
Прочитай AGENTS.md, docs/PLANNING.md і docs/plans/README.md. Візьми активний
план, прочитай його заголовок і «Instructions for the executor», почни з
першого кроку зі статусом не done. Працюй лише за планом. Наприкінці · звіт
за форматом AGENTS.md.
```
