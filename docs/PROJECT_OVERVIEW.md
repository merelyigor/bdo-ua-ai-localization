# Огляд проєкту

## Призначення

`bdo-ua-ai-localization` · публічний клієнтський toolkit для перекладу рядків
Black Desert Online українською. Він читає й записує дані через BDO UA Translate
Agent API, запускає локальні моделі Ollama і механічно перевіряє identity,
markup і якість до запису.

Toolkit не містить серверної БД, Laravel application, moderation UI або deploy.
Серверна реалізація живе в іншому проєкті й доступна звідси лише read-only через
шлях `TRANSLATE_PROJECT_ROOT`: тільки targeted читання контракту, без запуску
Docker, Artisan, SQL/БД, тестів або будь-яких змін. Операційні дані toolkit
отримує виключно через Agent API. Серверне доопрацювання передається окремому
агенту за [API_CHANGE_HANDOFF.md](API_CHANGE_HANDOFF.md).

## Єдиний вхід

`./bdo` без аргументів піднімає СТОРІНКУ в браузері (рішення власника
2026-09-05); `./bdo tui` дає вікно в терміналі, `./bdo help` · дерево команд.
Реалізація підкоманд живе в `lib/Cli/Command/**` і маршрутизується
`lib/Cli/Router.php`; у `cli/**` shell не лишилось узагалі · там тільки PHP поза
деревом команд (HTTP-клієнт, клієнт моделі, план аргументів для вікна,
синхронізація `.env`, сервер сторінки). Штатний шлях у документації · через `bdo`. Причина не
косметична: агент, який не знайшов штатну команду, писав власну й обходив гейт
identity.

## Архітектура: код керує, модель виконує

```
сторінка (web/**) ─┐
./bdo tui ────────┴─► lib/Run/Actions.php ─► RunLoopCommand ─► RunDriveCommand ─► StateMachine
  дві поверхні          кнопка → команда        драйвер            рушій           дозволені
                                                    │                               переходи
                                                    └──► cli/model/client.php ──► Ollama (роль + схема)
```

Обидві поверхні складають аргументи прогону ОДНИМ місцем (`Actions`), тому
розбіжність між ними не дублюється в окремих обробниках.

Головне рішення 2026-09-04: **порядок кроків тримає код, а не модель.** До
цього конвеєр вела модель-диригент у OpenCode. Та версія законсервована тегом
`v3.0.6-opencode` і гілкою `legacy/opencode`; обидва рефи лишаються як історія
(рішення власника 2026-09-04), а робочого коду тієї епохи в наборі немає.

## Шари

| Шар | Відповідальність |
|---|---|
| `web/**` + `cli/system/web-router.php` | основна поверхня: екрани прогону, черги, сесій, старту, моделей |
| `lib/Web/` | читання `state/**` для сторінки (`Snapshot`) і виконання дій (`Runner`) |
| `lib/Run/Actions.php` | кнопка → команда набору; одна для сторінки й для вікна |
| `./bdo tui` | вікно в терміналі: меню, екрани стану й журналу |
| `RunLoopCommand` | виконання конверта рушія, перехід між пачками |
| `cli/model/` | виклик локальної моделі, розгортання відповіді, журнал |
| `lib/Cli/Command/**` | реалізація підкоманд: API, пачка, підготовка, якість, лікування, запис |
| `lib/` PHP (решта) | identity, належність пачці, дефекти якості, безпечні payload, машина станів |
| `roles/*.md` + `config/roles.json` | що робить кожна роль і якою моделлю |
| Agent API | авторитетні рядки, глосарій, валідація, ревізії, модерація |

HTTP write, виклик моделі й життєвий цикл стану мають штатні entrypoints. Ad-hoc
`curl`, інший runner моделі або саморобний payload обходять перевірки й
заборонені.

## Ціль прогону

`BDO_ENV=PROD|DEV` у локальному `.env` жорстко задає середовище для читання й
запису разом. PROD бере `BDO_API_BASE_PROD` або production default; DEV бере
`BDO_API_BASE_DEV`. Застарілий `BDO_API_BASE` ігнорується.

`BDO_ENV` є і ціллю, і дозволом: окремого підтвердження на прод-запис агент не
запитує. Свідома дія власника · правка `.env`. Механічні запобіжники лишились:
`./bdo run start` фіксує ціль прогону, а `./bdo commit --write` звіряє з нею
кожну пачку й перевіряє квоту.

## Критичні інваріанти

- Identity: `source_language + key0 + record_id + key1`; API `identity_hash` не
  змінюється й не вигадується.
- PA markup, placeholders, newlines і `tokens.must_preserve` проходять
  детерміновану й серверну валідацію. Квадратні дужки зберігаються, а вміст
  усередині перекладається, коли теґа немає в `keep`.
- Manual, machine і proposal не взаємозамінні; ручні ревізії та історія
  модерації не перезаписуються.
- Належність пачці перевіряє manifest; курсор рухається після завершення пачки.
- Роль отримує payload ФАЙЛОМ і не має інструментів; відповідь обмежена схемою.
- Модель ролі задає `config/roles.json`; дотримання схеми доводить
  `./bdo runtime` реальним викликом того самого клієнта, що працює на пачці.
- Валідація тексту повторюється ПЕРЕД записом, уже після repair і судді.
- Windows працює нативним PHP (`bdo.bat`); WSL2 лишається запасним способом ·
  [WINDOWS_WSL2.md](WINDOWS_WSL2.md).

## Локальні дані

`.env`, `output/`, `state/` і журнали моделі не є публічними артефактами. Вони
не комітяться, не публікуються й не передаються зовнішнім моделям. Деталі ·
[SECURITY.md](SECURITY.md).

## Перевірки

Єдиний entrypoint · `./bdo gate <профіль>` (реалізація · `scripts/agent-check.sh`):

- `touched` · ДЕФОЛТ: лише перевірки, яких стосуються змінені шляхи (карта
  `touched_map` у тому ж скрипті);
- `preflight` · розкладка, середовище, правила, контракт `.env`;
- `docs` · дзеркала правил, норматив, плани, посилання в документах, secret scan;
- `shell` · Bash/ShellCheck/PHP syntax;
- `agents` · ролі конвеєра, драйвер, TUI і клієнт моделі;
- `runtime` · локальна модель через справжній виклик `cli/model/client.php`;
- `api` · read-only API smoke проти цілі з `.env`;
- `full` · усі детерміновані локальні gates без викликів моделі та API.
