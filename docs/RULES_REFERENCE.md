# Нормативний довідник агента-розробника

Детальний контракт. `AGENTS.md` маршрутизує сюди за §N. Довідник не повторює
рішення з [`DECISIONS.md`](DECISIONS.md), а пояснює, як їх застосовувати.

## §1 Пріоритет, факти, межі

- §1.1 Порядок пріоритету: інваріанти безпеки й даних → явна вказівка власника
  в поточній задачі → план → `AGENTS.md` → цей довідник → де-факто звичка коду.
- §1.2 Факт береться з коду, екрана в браузері, виводу команди, `docs/API.md` або первинної
  документації бібліотеки (офіційні docs, changelog, код). Памʼять моделі про
  бібліотеку фактом не є. Не знайшов · пиши «не підтверджено» і став гіпотезу.
- §1.3 Межа роботи · цей репозиторій. Локальної копії PHP-попередника
  (`$OLD`) більше немає (власник, 2026-10-09); перенесене з нього ·
  `reference/**` і `docs/LESSONS_FROM_PHP.md`. Копіювати PHP сюди заборонено:
  словники й правила переписуються на Python, а джерело називається в docstring
  (`Джерело: $OLD/lib/Quality/Russianisms.php, 2026-09-25`). Копіюються
  РІВНО два файли: `web/app.css` і `web/assets/bdo-background.webp` (AGENTS.md
  п. 3а). Скрипти `*.sh`, `bdo`, `bdo.bat`, `scripts/**`, `cli/**`, `tests/**`,
  PHP · ніколи, навіть тимчасово; це ловить `uv run bdo gate lint`.
- §1.4 Два шари агентів. Розробка (сильна сесія, помічник Codex, робітник
  OpenCode, штатні субагенти — за Бригадою (§13) або словом власника, їхні інструменти, ліміти) і конвеєр (ролі, локальні моделі, `roles.json`). Правила промптів ролей не
  застосовуються до агента-розробника і навпаки.
- §1.5 Оцінки часу · в сесіях агентної роботи, не в людських днях.

## §2 Секрети і класи даних

- §2.1 У tracked-файлах, комітах, промптах, відповідях, логах немає ключів,
  токенів, паролів, приватних URL, cookies, дампів, повних payload із живими
  даними, персональних даних.
- §2.2 `identity_hash`, `source_hash`, `call_id` · технічні ідентифікатори, не
  секрети; але `.bdo/` не публікується.
- §2.3 `.env` читає лише `settings.py`; жоден інший модуль не читає `os.environ`
  напряму (`uv run bdo gate lint` шукає `os.environ` і
  `getenv` у `src/` поза `settings.py`).
- §2.4 Логи редагуються фільтром `RedactSecrets` до запису; екран «Стан»
  має кнопку «Перевірити редагування», яка пише в лог рядок із фальшивим
  ключем і показує, що в `.bdo/web.log` він став `***`.

## §3 Git і необоротні дії

- §3.1 `git status --short` до старту й перед фіналом. Незакомічені шляхи, яких
  план не називає, класифікуються як чужі й не чіпаються.
- §3.2 `git add` лише поіменно. Заборонені `git add .`, `-A`, `commit -a`,
  `--no-verify`, `push`, `push --force`, теги, `reset --hard`, `clean -fd`,
  `checkout -- <файл>` на чужих змінах.
- §3.3 Commit · після checkpoint фази плану або після кроку, який план явно
  позначає «commit». Формат повідомлення (власник, 2026-09-27, як у
  попередника):

  ```text
  Версія: 0.7.1

  P08: модуль статистики рахує час за роллю з таблиці calls. Перевірено:
  uv run bdo gate, код 0.

  Файли:
  pyproject.toml
  src/bdo_translate/__init__.py
  uv.lock
  src/bdo_translate/pipeline/stats.py
  ```

  1. Рядок 1 · рівно `Версія: X.Y.Z`, далі порожній рядок.
  2. Абзац українською: що змінилось і навіщо, що перевірено (команда, код
     виходу). Перше речення починається з мітки: `P0N: …`, `Плани: …`,
     `Правила: …`, для задачі без плану · `Задача: …`. `git commit -m "P0N: …"` у кроках планів означає саме це
     перше речення.
  3. Порожній рядок, `Файли:`, по одному шляху на рядок без порожніх рядків
     між ними · ті самі шляхи, що в `git commit -- <шляхи>`. Повідомлення
     пишеться у файл і комітиться `git commit -F <файл> -- <шляхи>`: кілька
     `-m` git розділяє порожніми рядками й ламає блок.
  4. Без markdown-розмітки й без атрибуції AI-інструмента (D-42).
  5. Версія (D-32): коміт закриття плану P0N · `0.N.0` (P10 · `1.0.0`, P11 ·
     `1.1.0`); кожен інший коміт · PATCH +1 від версії HEAD (після `0.7.0`
     робота над P08 · `0.7.1`, `0.7.2`, …, закриття P08 · `0.8.0`). PATCH не
     має стелі: правило попередника «PATCH 9 → MINOR +1» тут не діє, бо MINOR ·
     номер плану. Не зростає версія лише в amend, який не змінює файлів.
  6. Версія в коміті = версія продукту: `version` у `pyproject.toml`,
     `__version__` у `src/bdo_translate/__init__.py`, `uv.lock` після
     `uv sync`; три файли йдуть у коміт і в `Файли:`; `uv run bdo version`
     друкує число з рядка 1.
  7. Перед КОЖНИМ комітом · `git log -1 --format=%B` і `uv run bdo version`:
     паралельна сесія могла закомітити раніше, і наступна версія рахується
     від HEAD на момент коміту.
  8. Перевірку механічно стереже хук `commit-msg` (P10 крок 3.1).

  Коміти до 2026-09-27 мають старий формат `<план>: <що зроблено>`. Трейлери
  `Co-Authored-By` і особисту пошту з ранніх комітів прибрано переписуванням
  історії за рішенням власника (D-42); `git log --grep=Co-Authored-By` порожній.
  Нове переписування історії · лише окремим рішенням власника.
- §3.4 Видалення файлів, теки `.bdo/`, БД, знімків · лише за окремим дозволом
  власника, названим у поточній задачі. Кнопка «Архівувати карантин» на екрані
  «Карантин і запис» (дія `quarantine_clear`) дозволена: карантин не є чергою
  роботи, записи не видаляються, а позначаються `archived`.

## §4 Реалізація

- §4.1 Кожен модуль має docstring українською: що робить і чого НЕ робить.
- §4.2 Функції кроків конвеєра чисті щодо вводу: беруть `Repo`, `Settings`,
  транспорт як параметри; глобального стану немає. Це робить replay
  можливим без патчів.
- §4.3 Час · параметр `now: datetime` або `clock: Callable[[], datetime]`;
  `datetime.now()` усередині логіки заборонений (`uv run bdo gate lint`
  шукає його в `src/` поза `clock.py`).
- §4.4 Винятки: `ApiError`, `TransportError`, `StateError`, `ConfigError`
  успадковують `BdoError`. Ловити `Exception` дозволено лише в CLI/веб на межі
  з користувачем, з логом і машиночитаною причиною.
- §4.5 Нова залежність · лише рядком у `pyproject.toml` за дозволом власника і
  записом у `DECISIONS.md`.
- §4.6 `# type: ignore[код]` і `# noqa: КОД` · лише з коментарем чому. Загальні
  `# type: ignore` і `# noqa` без коду заборонені. `ruff` ловить лише зайвий
  `noqa` (`RUF100` у наборі `RUF`); `PGH003` не увімкнене, тож голий
  `# type: ignore` gate поки не ловить.

## §5 Документація і плани

- §5.1 `docs/*.md` описують фактичний стан; `docs/plans/**` · майбутню й
  поточну роботу. Закритий план видаляється тим самим комітом
  (власник, 2026-09-30); слід · рядок у `docs/plans/PROGRESS.md` і історія git.
- §5.2 Кожна зміна поведінки конвеєра тим самим комітом оновлює
  `docs/ARCHITECTURE.md`, якщо змінила карту модулів, стани або схему БД.
- §5.3 Дефект · рядок у `docs/plans/DEFECTS.md` у момент діагнозу, з класом і
  регресією. Ідея, яку власник відклав · рядок у `docs/plans/BACKLOG.md` з
  причиною і ознакою готовності.
- §5.4 Посилання в markdown ведуть на реальні файли (`uv run bdo gate docs`).
- §5.5 Автономія за планом (власник, 2026-09-26; замінює обережніші редакції
  2026-09-25 і 2026-09-26). Мета · план реалізується до кінця без зупинок (веде
  головна сесія за глобальним skill `brygada`, `AGENTS.md`); погане рішення виправляється потім, зупинка коштує дорожче.
  1. Прогалина, неоднозначність, розбіжність плану з кодом, реальною
     відповіддю API чи бібліотеки, невказаний тип, текст, імʼя, формат,
     значення · виконавець вирішує сам і продовжує.
  2. Порядок, як вирішувати: `docs/DECISIONS.md` → `docs/ARCHITECTURE.md` →
     `docs/API.md` і реальна відповідь API → `reference/**` → найпростіший
     варіант, який легко замінити (загальний тип
     замість вигаданої структури, `extra="allow"`, значення за замовчуванням,
     без нових абстракцій). Нова залежність · лише якщо без неї крок не
     виконати, і лише відома бібліотека з PyPI.
  3. Кожне рішення · рядок у `docs/plans/EXECUTOR_DECISIONS.md` (дата, план і
     крок, що вирішив, відкинуті варіанти, як відкотити) і рядок «вирішив сам»
     у `Notes` кроку. Звіт сесії перелічує ці рядки: власник і сильна модель
     переглядають їх і виправляють окремо.
  4. Стоп і питання в чаті ЛИШЕ перед необоротним або небезпечним: запис у
     PROD; зміна `BDO_ENV`; запис у `.env` поза білим списком D-44 і дозволеними
     діями екрана `/models`; секрети; видалення файлів чи даних, крім
     тимчасових `.bdo/` цього прогону; `git push`, force, теги, переписування
     історії; виклик віддаленої моделі, крім `go/*-free` (D-43);
     будь-яка зміна поза цим репозиторієм.
  5. Критерії приймання не послаблюються: звірка в Playwright, `uv run bdo
     gate` з кодом 0, заборона глушити помилки. Рішення «вимкнути перевірку,
     щоб пройти» не є дозволеним самостійним рішенням.
## §6 Identity, quality, state

- §6.1 Identity = `source_language + key0 + record_id + key1`, згорнута API в
  `identity_hash`. Не будується локально, не «виправляється», не дублюється,
  не губиться: `Manifest.assert_belongs` і `items` перед записом перевіряють
  повноту й належність пачці.
- §6.2 `keep`, placeholders, PA markup, `{BDO_NL}` копіюються байт у байт і в
  тій самій кількості; `quality/tokens.py` перевіряє. Квадратні дужки
  зберігаються, видимий вміст перекладається, якщо теґа немає в `keep`.
- §6.3 Роздільники переліків: оригінал, що закінчується на `;`, вимагає тієї
  самої кількості `;` і кінцевого `;` (`quality/separators.py`; урок D253).
- §6.4 Видимий український текст без російських літер `ыэъё`, без русизмів зі
  словника, без латинських гомогліфів у кириличних словах, без `—` (лише `-`
  або `·`), без чужої писемності, якої немає в оригіналі.
- §6.5 `manual`, `machine`, `proposal` · окремі шари; manual revisions,
  glossary, moderation не перезаписуються.
- §6.6 Механічний дефект сильніший за вирок моделі: рядок із дефектом не
  отримує `PASS`, навіть якщо QA так сказала. Суддя вирішує МАРШРУТ спірного
  рядка, не текст.
- §6.7 Стан пачки ізольований manifest-ом; курсор сесії рухається лише після
  `committed` або `failed_terminal`; dry-run курсор не рухає й нічого не пише в
  API.
- §6.8 Розмір пачки: механіку перевіряють у браузері на 5 рядках (мінімум API), поведінку
  моделі міряють на робочому розмірі (default 50). Число береться з коду
  (`RunGoal.rows_per_batch`), не дублюється в документах.
- §6.9 Лічильник спроб на `identity_hash` (`row_attempts`): після
  `heal_max_attempts` рядок іде в moderation/deferred і зникає з наступної
  вибірки сесії.

## §7 Agent API і production

- §7.1 Контракт · `docs/API.md` і `docs/API_WRITE_CONTRACT.md`. Розбіжність
  живого API з документом · дефект у `DEFECTS.md` і правка документа з датою
  звірки; не «підлаштувати код тихо».
- §7.2 Усі виклики йдуть через `api/client.py`; `curl`, власний `requests`,
  другий клієнт заборонені.
- §7.3 Перед кожним записом · `GET /me`: роль, `effective_abilities`,
  `writes.channels` (список обʼєктів, не мапа), квота. Немає права на канал ·
  запису немає, `layer` не підмінюється.
- §7.4 Запис лише після `POST /translations/validate` тим самим каналом
  (`layer`/`mode`/`auto_approve`). `status: repaired` з `repaired_text` ·
  безкоштовне лікування, застосовується кодом і повторно перевіряється
  механікою.
- §7.5 `Idempotency-Key` пачки стабільний; повтор запису безпечний.
- §7.6 Потрібна зміна API на сервері · агент пише ПРЯМО «потрібна правка API
  на серверному боці» і дає готовий текст запиту для серверної сесії в чаті.
  Серверний проєкт із цього репозиторію не відкривається.
- §7.7 PROD: `BDO_ENV=PROD`, увімкнений власником кнопкою з підтвердженням на «Старті» (D-51, D-53); коду PROD немає.
  Під час розробки `.env` тримає `DEV`; агент це не змінює.

## §8 Ролі, моделі, промпти

- §8.1 Активну модель для всіх ролей власник обирає на `/models` (D-43);
  `config/roles.json` задає схеми, температуру і стартове бажання `think` на
  роль. Екран `/models` зберігає бажання та рівень роздумів; фактичні
  можливості моделі визначають, що піде в запит (D-45). Після прогону джерело
  правди · таблиця `calls` (екрани «Виклики» й «Виклик»).
- §8.2 Промпт ролі самодостатній для активної моделі власника (D-43): короткі
  наказові речення, нумеровані правила, точна форма
  відповіді, явні stop-стани. Include, спільні файли, runtime-композиція
  заборонені; допустима лише build-time генерація з gate-перевіркою.
- §8.3 Промпт називає поле `id`, ніколи `identity_hash`; `uv run bdo gate lint`
  шукає `identity_hash` у всіх `roles/*.md` і червоніє, якщо знайшов.
- §8.4 JSON для моделі максимально простий: усе, що може вивести код (хеш,
  порядок, повтори, готовий переклад із памʼяті), модель не пише.
- §8.5 Рамка кожного промпту: офіційна українська локалізація Black Desert
  Online; знання гри · для сенсу, відповідник дає лише glossary/terms/examples;
  російську локалізацію не переносити.
- §8.6 Нову модель кваліфікують кнопкою smoke на екрані «Моделі» (реальний
  виклик `translation-smoke` під схемою) і серією «Повторити» на екрані
  «Виклик»; один sample доказом не є.
- §8.7 Автономність дорожча за виклики: ціль · не лишати людині
  доопрацювання; кількість викликів не є аргументом проти кола лікування в
  межах бюджету `heal_max_attempts`.
- §8.8 Зміна промпту перевіряється кнопкою «Повторити» на збережених викликах
  ДО живого прогону; звіт називає, що змінилось у відповідях.

## §9 Веб і дизайн

- §9.1 `bdo web serve` слухає `127.0.0.1:<BDO_WEB_PORT>`; `Host` лише
  `127.0.0.1`/`localhost`/`[::1]` з портом; `Origin`/`Sec-Fetch-Site` чужого
  сайту · 403 навіть на читання; дії · лише POST з локальним `Origin`.
- §9.2 `web/**` не містить другої бізнес-логіки: порядок і guards у `pipeline/`.
- §9.3 Дизайн-система: токени `var(--…)` із `:root` у `web/static/app.css`
  (скопійовані з `$OLD/web/app.css`, read-only), обидві теми, шкала 11/12/13,
  класи `button`, `.btn-primary`, `.btn-danger`, `.chip`. Новий колір чи розмір
  спершу стає токеном із причиною.
- §9.4 Екрани окремі, не вкладки (рішення власника 2026-09-05). UI-рішення
  агент приймає сам у бік простоти й зрозумілості для власника.
- §9.5 Візуальна звірка через MCP Playwright · ЄДИНИЙ канал приймання
  будь-якого кроку (D-33), не лише `web/**`. Протокол: `uv run bdo web start`
  друкує URL → `browser_navigate` на екран кроку → `browser_emulate_media`
  `colorScheme: dark` → `browser_snapshot` → дія кнопкою → `browser_wait_for`
  очікуваного тексту → `browser_take_screenshot` у `.bdo/playwright/<план>-<крок>-<n>.png`
  (3–5 знімків, пауза 1–2 с) → `browser_console_messages` без `error` →
  `browser_network_requests` без статусів ≥ 400 → `uv run bdo web stop` (код 0).
  Unit-тести, `curl`, DOM-звірка без знімків звірку не заміняють. Playwright
  недоступний · звірки немає, крок не `done`.
- §9.6 Тестовий прогін · лише `dry_run` на DEV; агент дивиться кожну пачку до
  кінця і звіряє екран із `calls` і manifest.
- §9.7 Сервер власника під час звірки macOS-застосунку: перед звіркою виконавець
  запускає `uv run bdo web status`. Якщо сервер уже працює і його підняв не
  виконавець, це записується в Notes; після звірки сервер лишається працювати,
  `uv run bdo web stop` не запускається. Знімки, console і network фіксуються
  звичайно.

## §10 Перевірки

- §10.1 `uv run bdo gate` · статичний gate за секунди; профілі `secrets`,
  `docs`, `lint`, `types`. Червоний gate · незавершена задача. Gate не є
  прийманням: приймання · §9.5.
- §10.2 Перевірка йде тим самим шляхом, що робота: кнопка на екрані викликає
  ту саму функцію, що й конвеєр, а не окрему «для перевірки».
- §10.3 Підсумок сесії · див. `AGENTS.md`.

## §11 Еволюція правил

- Власник просить змінити правило · правиться єдиний канон `AGENTS.md`
  (`CLAUDE.md` лишається рядком `@AGENTS.md`, його стереже `uv run bdo gate`), деталь іде сюди, рішення · у `DECISIONS.md`. Нове правило
  коротке і має видиму перевірку (gate або екран); без перевірки воно тут зайве.

## §12 Тихий збій і фіктивна перевірка

- Порожній вивід не є відповіддю; кожна команда повертає машиночитану причину.
- Перевірка, яка не може впасти, нічого не стереже: нову механічну перевірку
  показують у браузері на навмисно зламаному вході, і екран мусить показати дефект.
  Нове правило `bdo gate` чи git-хука так само запускають на навмисно
  зламаному файлі: gate мусить почервоніти, потім зламане прибирається.
- Стан, який код пише, хтось читає: поле без читача видаляється.
- Після двох однакових невдач · зупинка, діагноз, інший підхід.
