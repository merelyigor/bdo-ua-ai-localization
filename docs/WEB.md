# Вебінтерфейс і візуальна звірка

## Архітектура та вигляд

- `web/**` не містить другої бізнес-логіки: порядок конвеєра й guards реалізовані в `pipeline/`.
- Сервер слухає `127.0.0.1:<BDO_WEB_PORT>`. `Host` приймається лише `127.0.0.1`, `localhost` або `[::1]` із портом. Чужі `Origin` або `Sec-Fetch-Site` отримують 403, у тому числі для читання; дії дозволені лише POST із локальним `Origin`.
- Дизайн використовує токени `var(--…)` із `:root` у `web/static/app.css`, обидві теми, типографічну шкалу 11/12/13 і наявні класи `button`, `.btn-primary`, `.btn-danger`, `.chip`. CSS походить від `$OLD/web/app.css` і лишається read-only. Нові кольори й розміри спершу додаються як токени з поясненням.
- Екрани окремі, не вкладки (рішення власника 2026-09-05). UI-рішення приймаються в бік простоти й зрозумілості.

## Протокол звірки

Візуальна звірка — канал приймання кожного кроку (D-65), не лише змін вебкодом.
Перший канал — штатний браузер Codex: вкладка чату `iab`
(`cua.createBrowserTab("iab", url)`) або вкладки Chrome власника через Computer Use
(`cua_repl`) для залогінених екранів; довідка — skill `codex-in-app-browser`.
Playwright MCP беруть лише коли штатний канал цього не вміє, і тоді причину
називають у чаті.

1. Перевір `/health` і підтвердь, що екран показує `DEV` та очікувану версію
   кроку. Сервер власника працює у фоні на `127.0.0.1:7660` і може бути в `PROD`;
   не перемикай його середовище й не використовуй його для DEV-приймання.
   Якщо доступного DEV-сервера немає або власник уже використовує потрібний
   сервер, підніми **окремий** сервер у пісочниці з окремими `BDO_ENV_FILE`,
   `DATA_DIR` і `BDO_WEB_PORT`. `uv run bdo web start` проти сервера власника не
   запускають (канон — [`AGENTS.md`](../AGENTS.md)); у пісочниці його запускають
   лише з окремими шляхами.
   Окремий `DATA_DIR` тут не формальність: pid-файл `web.pid` лежить у
   `data_dir`, і його пише той самий `webctl.start`, що й значок `BDO.app`
   (`bdo app start`). Спільний `DATA_DIR` означає спільний pid-файл, а
   `bdo web stop` убиває процес саме з нього.
2. Відкрий екран кроку у вкладці `iab` і впевнись, що застосунок у темній темі: штатний канал не емулює схему примусово, тож світлий застосунок робить знімки нечинними.
3. Зніми стан екрана `getAXState()` і знайди в ньому елемент дії.
4. Виконай дію кнопкою й дочекайся очікуваного тексту. Онови `getAXState()` і перевір, що потрібний текст у ньому є.
5. Зроби 3–5 знімків `getScreenshot()` із паузою 1–2 секунди. Якщо інструмент дає зберегти файл, поклади його в `.bdo/browser/<план>-<крок>-<n>.png`. `cua_repl` наразі повертає знімок у чаті й не надає способу зберегти його на диск; у такому разі лиши знімок доказом у чаті.
6. Перевір видимі помилки екрана, наприклад `run-failure`, стан `/health` і
   консоль `tab.dev.logs({ levels: ["error"] })`. Штатний `cua_repl` дає
   `getAXState()`, `getScreenshot()` і журнал консолі, але не має окремого API
   для HTTP-статусів мережі. Статуси ≥ 400 перевір запасним Playwright MCP і
   назви в чаті цю причину.
7. Сервер власника не зупиняють: `uv run bdo web stop`, `uv run bdo app stop` і
   `kill` для нього заборонені (канон — [`AGENTS.md`](../AGENTS.md)), після
   перевірки він лишається працювати. Зупиняють лише окремий сервер у
   пісочниці, який підняв сам виконавець, і тільки з його `BDO_ENV_FILE` і
   `DATA_DIR`: `uv run bdo web stop` читає pid-файл саме з `DATA_DIR`, тож
   спільний `DATA_DIR` з сервером власника вбив би його процес. Код 0 від
   `bdo web stop` означає «зупинено і нараховано щонайменше 3 знімки після
   старту»; код 1 із написом «ЗВІРКИ НЕ БУЛО» означає, що знімків вистачило
   менше трьох.

Unit-тести, `curl`, DOM-звірка без знімків і самозвіт коду не замінюють протокол. Якщо недоступний і штатний канал, і Playwright — звірки немає і крок не закривається.

## Доказ кроку

Доказ кроку — це набір артефактів, за яким інша сесія перевіряє, що крок
виконано. Він узгоджений із [`CHECKLIST.md`](CHECKLIST.md).

У доказ входить:

- шляхи знімків (3–5 файлів у `.bdo/browser/` або самі знімки в чаті, якщо
  канал не дає записати файл);
- очікуваний і фактичний текст екрана після дії — записані в `Notes`
  відповідного кроку плану;
- консоль без записів рівня `error` через штатний
  `tab.dev.logs({ levels: ["error"] })`;
- мережа без неочікуваних статусів ≥ 400 (запасний Playwright MCP, якщо штатний
  `cua_repl` не надає статусів мережі; причину називають у чаті).

Не є доказом:

- знімок без звірки очікуваного тексту — файл без очікування нічого не
  підтверджує;
- `curl` до `/health` або іншого endpoint: це перевірка живості, а не екрана;
- DOM-звірка без знімків;
- самозвіт коду («повинно працювати»);
- зелений `uv run bdo gate` замість браузерної звірки: gate доводить
  статику, а не поведінку.

Коли звірки немає — недоступний і штатний канал, і Playwright, або екран
неможливо побачити: крок **не** переходить у `done` і **не** в `skipped`.
Причину записують у `Notes` кроку, крок лишається відкритим, а план не
закривається. Для кроку, що змінює лише документацію або плани, браузерної
поверхні немає: доказом є відповідний профіль `uv run bdo gate` із кодом 0
плюс diff, і це пишуть у `Notes` кроку.

Тестовий прогін — лише `dry_run` на DEV; кожну пачку переглянь до кінця й звір із таблицями `calls` та manifest. Запис на DEV дозволений лише в кроці плану з явним дозволом власника.

## Сервер власника

Власник запускає сервер значком `BDO.app`; він працює у фоні на порту `BDO_WEB_PORT` (типово 7660). Не запускай `bdo web start`, `bdo web stop`, `app stop` чи `kill` для сервера власника. Якщо `/health` показує старішу версію або звірці потрібен свіжий Python-код, дозволено `uv run bdo web restart`, але лише коли сервер не `busy`; дочекайся кінця прогону власника й повторно перевір `/health`. Окремий сервер допустимий лише в пісочниці зі своїми `BDO_ENV_FILE`, `DATA_DIR` і `BDO_WEB_PORT`, після чого зупиняється саме він — і зупинка мусить виконуватися з тими самими `BDO_ENV_FILE` і `DATA_DIR`, бо pid-файл сервера лежить у `DATA_DIR`.
