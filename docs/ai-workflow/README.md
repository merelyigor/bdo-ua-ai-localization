# AI-workflow набору перекладу BDO

## Навіщо це

Робота ведеться трьома ролями: **власник**, **архітектор** (сильна модель:
аналіз, межі, плани, промпти, рев'ю) і **агент-виконавець** (модель, яка добре
пише код, але не мусить сама вирішувати архітектуру). Цей каталог фіксує, хто
що вирішує, який вигляд має завдання й за якими доказами робота приймається.

Модель узята з робочого потоку хаба українізацій і адаптована під цей набір:
тут інші межі (локальні моделі, PROD-запис через Agent API, gate на bash).

Документи vendor-neutral: описують ролі й контракти, а не конкретні моделі.

## Канонічний потік

```text
ВЛАСНИК: мета й пріоритет
→ АРХІТЕКТОР: аналіз репозиторію, межі, ризики
→ (за потреби) READ-ONLY інспекція агентом
→ АРХІТЕКТОР: implementation prompt
→ АГЕНТ: код, тести, gate, коміт, звіт
→ АРХІТЕКТОР: рев'ю за фактичним diff і доказами
   ├─ дефект → corrective prompt → агент
   └─ прийнято → наступне завдання
```

## Чотири межі, специфічні для цього набору

1. **PROD-запис незворотний.** Пачка, яка дійшла до кроку commit, пише
   переклади в живий проєкт. Тому підтвердження вимагає КОД (`needs_confirm` у
   `lib/Run/Actions.php`), а не галочка в розмітці, і кожне завдання, що
   торкається кроку записування, перевіряється тестовим прогоном
   (`BDO_DRY_RUN=1`) ПЕРЕД бойовим.
2. **Порядок кроків тримає код, а не модель.** `cli/run/run-loop.sh` виконує
   конверт `./bdo run drive`. Завдання не має права переносити рішення «що
   робити далі» в промпт ролі: це вже коштувало 14 дефектів із 45.
3. **Перевірка йде тим самим шляхом, що й робота.** Порожній вивід не є
   відповіддю; тест на зручному розмірі не є доказом; правило без механічної
   перевірки не існує. Деталі · §12 довідника.
4. **Зміна в `web/**` закривається прогоном у браузері ВЛАСНИКА** (§16):
   `./bdo browser` → його вкладка `127.0.0.1` → знімок стану → клік саме там →
   3-5 знімків із паузою 1-2 с + консоль і мережа. Локальний тест цього не
   замінює.
