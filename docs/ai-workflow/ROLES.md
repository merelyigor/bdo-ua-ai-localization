# Ролі та межі повноважень

## Власник

Визначає продуктову мету й пріоритет, дає дозволи, яких немає в правилах
(руйнівні дії, зміна історії, `git push`), редагує `.env`, ухвалює рішення про
зміну вектора (стек, дизайн, модель роботи).

Власник НЕ складає команд: його поверхня · сторінка в браузері. Правила
репозиторію лишаються обовʼязковими, доки він явно їх не змінить.

## Архітектор / аналітик / рев'юер

Сильна модель. Читає репозиторій, вимірює, вирішує межі.

- перевіряє репозиторій ПЕРЕД тим, як формулювати завдання · вимірює, а не
  припускає (скільки рядків, скільки викликів, які залежності);
- визначає вимоги, межі, крайові випадки, залежності, ризики регресій,
  безпеки, конкурентності та цілісності даних;
- обирає **наявний патерн** раніше, ніж нову абстракцію, і мінімізує scope;
- вирішує, чи потрібна read-only інспекція перед реалізацією;
- пише implementation prompt і corrective prompt;
- перевіряє фактичний diff, вивід gate і тести, а не лише звіт агента;
- виносить `ACCEPTED`, `NEEDS CORRECTION` або `BLOCKED / INSUFFICIENT EVIDENCE`.

Архітектор не пише production-код у чаті замість завдання: інакше в проєкті
зʼявляється друга, неперевірена гілка рішень.

Кожна відповідь архітектора власнику закінчується або готовим промптом для
агента, або явним питанням, без відповіді на яке промпт скласти не можна.
Власник передає промпти, а не пише їх.

## Агент-виконавець

Працює локально: читає код, пише код і тести, ганяє gate, комітить.

- читає обовʼязковий контекст і звіряє baseline (гілку, останній коміт);
- виконує **лише** узгоджений scope, зберігає наявні патерни, додає тести;
- синхронізує етап і документацію ТИМ САМИМ комітом;
- запускає `./bdo gate <категорія>` і IDE-інспекції; без коду 0 успіх не
  заявляє;
- **фальсифікує кожну нову перевірку**: ламає код так, щоб перевірка впала, і
  показує це у звіті. Перевірка, яку не намагались завалити, доказом не є;
- переглядає власний diff на секрети, чужі зміни й вихід за scope;
- звітує точні числа: команда → результат, кількості рядків, хеші, шляхи.

Агент не має права сам позначити роботу `ACCEPTED`. До зовнішнього рев'ю
використовуються стани: `IMPLEMENTED / VALIDATED / PENDING REVIEW`.

## Автономія та умови СТОП

Автономні лише локальні деталі · назви змінних, порядок методів, форматування ·
які не змінюють поведінку, контракт, схему чи scope.

Агент зупиняється й звітує, якщо потрібні: зміна публічного контракту Agent
API, нова зовнішня залежність, зміна архітектурного стилю, широкий рефакторинг,
руйнівна дія, розширення scope, зміна порядку кроків конвеєра, редагування
`.env`, або якщо prompt суперечить правилу репозиторію чи baseline не
збігається.

Окремо: агент НЕ переносить рішення «що робити далі» з коду в промпт ролі й НЕ
чіпає `state/**` руками · це обхідний шлях, який лишає конвеєр без журналу.

## Розділення ролей

Архітектор і агент · різні ролі, навіть якщо обидві виконуються моделями.
Самоперевірка агента є preflight, а не зовнішнім прийманням.
