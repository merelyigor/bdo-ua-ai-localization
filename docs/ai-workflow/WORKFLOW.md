# Життєвий цикл завдання

## Простий потік (низький ризик, цілісна задача)

```text
АНАЛІЗ → PROMPT → РЕАЛІЗАЦІЯ → ТЕСТИ Й ДОКИ → GATE → КОМІТ → ЗВІТ → РЕВ'Ю
```

## Складний потік (ризик, нечіткість, дані, PROD-запис)

```text
РОЗУМІННЯ ЗАДАЧІ
→ READ-ONLY ІНСПЕКЦІЯ (агент нічого не змінює)
→ АНАЛІЗ І АРХІТЕКТУРА
→ ДЕКОМПОЗИЦІЯ ЗА РИЗИКОМ
→ PROMPT НА ПЕРШИЙ КРОК
→ РЕАЛІЗАЦІЯ → GATE → ТЕСТОВИЙ ПРОГІН → ЗВІТ
→ РЕВ'Ю → CORRECTIVE ЗА ПОТРЕБИ
→ ПРИЙМАННЯ
```

Read-only інспекція потрібна, коли поточний потік, архітектура або ризик
невідомі. Вона не змінює файлів і повертає: релевантні файли, поточний потік
даних, залежності, точки втручання, ризики й відкриті питання.

## Аналіз перед завданням

Архітектор називає: мету, вимоги, межі, крайові випадки, залежності й ризики
регресій, безпеку, цілісність даних, критерії приймання. Є код · спершу
досліджується він: відповідальності, потік даних, інтерфейси, конвенції,
наявні тести. Порядок рішень: наявний патерн → мінімальне розширення наявного
→ нова абстракція.

**Аналіз стоїть на вимірі, а не на здогаді.** «Скрипт великий» не є фактом;
`wc -l`, `rg -c`, число викликів і час кроку · є. Ця межа не формальна: рішення
про MLX-модель два дні виглядало правильним саме тому, що спиралось на вимір на
замалому payload (D82).

## Межі завдання

Кожне завдання має явні **IN SCOPE** і **OUT OF SCOPE**. Без прямої потреби
агент не робить: сторонній рефакторинг; зміни публічного контракту Agent API;
нові залежності; переписування робочих модулів; послаблення чи видалення
тестів; вимкнення інспекцій; приховування помилок; секрети в коді; TODO замість
реалізації.

Декомпозиція: крок має цілісну мету, обмежений набір файлів, конкретний
результат і перевірку. Коли архітектура визначена, а перевірка сильна, один
крок може містити реалізацію, тести, документацію, gate і коміт разом.

## Типи завдань

`інспекція` · `реалізація` · `виправлення` · `перенос` · `прогін` ·
`документація й процес`.

Завдання типу **перенос** (переписування наявної поведінки іншою мовою чи в
інший шар) має додаткову обовʼязкову частину звіту: доказ ІДЕНТИЧНОСТІ
поведінки · той самий вхід дає той самий вихід, побайтово або за названим
списком розбіжностей.

Завдання типу **прогін** має звітувати числа: рядків у пачці, у шар, до
людини, карантин, викликів моделі, час кроку.

## Що робить ВЛАСНИК між кроками

Роль власника описана в `ROLES.md`, але в самому циклі вона теж має місце, і
без нього потік зупиняється мовчки:

1. приймає або міняє пріоритет · яке завдання наступне;
2. **передає промпт** архітектора агенту · сам промптів не пише;
3. дає дозволи, яких немає в правилах: коміт, `git push`, руйнівна дія, зміна
   `.env`, зміна вектора;
4. виконує те, чого агент не має права робити сам · натискає в браузері дію,
   яку не почав, перевіряє на другій ОС, вмикає налаштування Chrome;
5. **передає звіт агента архітектору** · без цього рев'ю не починається.

Крок 5 легко забути, і тоді робота лежить у стані `PENDING REVIEW` невідомо
скільки. Якщо власник передав звіт, а архітектор не має доступу до
репозиторію · рев'ю НЕ починається на самому звіті: `REVIEW.md` ставить звіт
останнім у ієрархії доказів.

## ДВІ РОЛІ В ОДНОМУ РОБОЧОМУ ДЕРЕВІ

Архітектор редагує файли процесу, агент · код. Обидва працюють у ТОМУ САМОМУ
клоні, тому їхні незакомічені зміни лежать поруч. Це вже стрельнуло 2026-09-08:
архітектор мав три готові файли процесу, а в дереві вже лежала незакомічена
робота агента над підетапом 2.

Правила, які з цього випливають:

- **Комітить той, хто почав пізніше · останнім.** Поки в `git status` є чужі
  незакомічені файли, свій коміт відкладається. Причина не в акуратності:
  коміт зсуває HEAD, і baseline, названий у промпті, перестає збігатися.
- **Версію бере той, хто комітить.** Двоє не можуть узяти `6.1.8` одночасно.
  Промпт називає ОЧІКУВАНУ версію, але якщо HEAD зсунувся · агент бере
  наступну від фактичного HEAD і каже про це у звіті.
- **`git add` тільки поіменно.** `git add .` і `-A` заборонені завжди, але тут
  вони ще й затягнуть чужу незавершену роботу в чужий коміт.
- Архітектор не редагує файл активного етапу, поки агент має його в scope:
  статус підетапу ставиться ПІСЛЯ коміту агента.
- **Комітить завжди агент · і код, і файли процесу** (рішення власника
  2026-09-08). Архітектор не запускає `git commit` і `git commit --amend`
  навіть для власних файлів: він віддає промпт із переліком файлів і версією.
  Тому «двоє в одному дереві» перестало означати двох комітерів · комітер
  один, і черга з першого пункту вирішується сама.
- **Промпт на коміт файлів процесу** називає: точний перелік шляхів
  (`git add` поіменно), номер версії, формат за
  `.codex/prompts/commit-message-ua.txt`, заборону `--no-verify` і заборону
  `git push`. Коду в такому промпті немає взагалі, тож і перевірка одна:
  `./bdo gate docs` і чистий `git status` після коміту.

## Стани

- до рев'ю: `IMPLEMENTED / VALIDATED / PENDING REVIEW`;
- після успішного рев'ю: `ACCEPTED`;
- за наявності дефекту: `NEEDS CORRECTION`.

Наступне залежне завдання не починається, доки відкриті `BLOCKER` або
`IMPORTANT`. `OPTIONAL` не блокує рух.

**`ЗАБЛОКОВАНО`** · окремий стан, і він НЕ є провалом. Агент повертає його,
коли: baseline не збігається; промпт суперечить правилу репозиторію; потрібне
рішення власника; бракує доступу чи даних. Далі:

1. агент НЕ вгадує й НЕ обходить · зупиняється й називає, чого бракує;
2. архітектор вирішує, що це: дірка в промпті (пише новий), питання до
   власника (ставить його) або реальна межа (записує в беклог);
3. **два `ЗАБЛОКОВАНО` поспіль на одному підетапі означають, що промпт
   поганий, а не виконавець.** Тоді промпт переписується цілком, а не
   доповнюється.

**Межа corrective кіл: два.** Третій дефект того самого підетапу означає, що
scope завеликий або межі нечіткі · підетап ділиться, а не лагодиться далі.

## Перевірки, які визнаються доказом

| Категорія зміни | Команда | Що доводить |
|---|---|---|
| правила й документація | `./bdo gate docs` | дзеркала правил, посилання, реєстри |
| будь-який shell/PHP | `./bdo gate shell` | синтаксис, ShellCheck, тести поведінки |
| промпти й моделі | `./bdo gate agents` | промпти ролей, allowlist, routing |
| перед комітом | `./bdo gate full` | усе разом, код виходу 0 |
| контракт API | `./bdo api` | ключ активний, ендпоінти на місці |
| локальна модель | `./bdo runtime` | модель у `ollama list`, схема тримається |
| типи й інспекції | MCP `phpstorm lint_files` `min_severity: error` | 0 ERROR на змінених файлах |
| крок записування | `BDO_DRY_RUN=1` (кнопка «тестовий прогін») | усі етапи без запису в API |
| екран у браузері | `./bdo browser` + 3-5 знімків у вкладці власника | темп, консоль, мережа (§16.7) |

Заявляти «перевірки пройшли» без коду 0 заборонено. Якщо gate неможливо
запустити · називається точна причина, що саме не перевірено і який це ризик.

## Плани й контекст

- `docs/plans/stages/` · етапи: один файл на етап, із метою, scope і
  критеріями;
- `docs/plans/BACKLOG.md` · черга робіт і відкладені рішення з причиною;
- `docs/plans/DEFECTS.md` · що вже ламалося, з регресією на кожен рядок.

**Правило синхронності:** коміт, який змінює поведінку, тим самим комітом
оновлює етап і реєстр. Розсинхрон плану й коду вже коштував шести версій
розбіжності.

## Означення готовності завдання

Критерії приймання виконані; є доказ перевірки з кодом 0; кожна нова перевірка
ФАЛЬСИФІКОВАНА; diff у межах scope; етап і документація синхронізовані; немає
відкритих `BLOCKER` та `IMPORTANT`; звіт містить те, що НЕ зроблено, і чому.
