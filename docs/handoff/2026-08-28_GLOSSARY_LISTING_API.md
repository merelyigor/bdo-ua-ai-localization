# Передача: перелік глосарію для аудиту записів

- **Створено:** 2026-08-28
- **Формат:** [docs/API_CHANGE_HANDOFF.md](../API_CHANGE_HANDOFF.md)
- **Навіщо:** [docs/plans/GLOSSARY_SUSPECTS.md](../plans/GLOSSARY_SUSPECTS.md)

Скопіювати текст нижче цілком у сесію агента, який працює в серверному проєкті
BDO UA Translate API. Нічого дописувати не треба.

```text
Працюй у серверному проєкті BDO UA Translate API.

Мета: дати клієнтові можливість ПЕРЕЧИТАТИ глосарій сторінками, щоб перевіряти
записи цілим масивом, а не по одному знайденому в пачці.

Підтверджена прогалина (перевірено запитами до PROD 2026-08-28):
1. GET /agent/v1/glossary/terms без параметра q відповідає HTTP 400
   {"success":false,"error":"invalid_request","message":"Передайте q або q[].",
   "details":{"parameter":"q"}}. Тобто endpoint є лише пошуком за відомою
   назвою.
2. Інших способів отримати перелік термінів у Agent API немає: GET
   /glossary/concepts віддає поняття гри, GET /glossary/rows/{identityHash} ·
   лише терміни конкретного рядка.
3. Наслідок для якості. Помилковий запис глосарію коштує дорожче за
   відсутній: він є обовʼязковим (severity=mandatory) і псує КОЖЕН рядок, де
   трапився термін. У вибірці з 63 термінів, які випадково траплялись у
   прогонах, знайдено три такі записи: Week -> Місяць (тиждень названо
   місяцем), GO -> ВПЕ (абревіатура без розшифровки), Her -> Вона (займенник
   як обовʼязковий термін). Знайти їх заздалегідь неможливо: клієнт бачить
   термін лише тоді, коли той уже потрапив у пачку й уже вплинув на переклад.

Потрібний контракт (additive, чинний пошук не змінювати):

GET /agent/v1/glossary/terms/list
  ability: glossary:read (нову не заводити)
  query:
    limit          ціле 1..200, типово 100
    cursor         непрозорий рядок із попередньої відповіді; без нього ·
                   з початку
    include_total  0|1, типово 0 (повний підрахунок не має бути обовʼязковим)
    status         фільтр за статусом запису, множинний
    entity_type    фільтр, множинний
    severity       фільтр, множинний
    has_definition 0|1 · записи з описом або без нього
    updated_since  ISO-8601; для повторного аудиту лише змінених записів
    fields         core|full, типово core
  порядок: строго детермінований і стабільний між сторінками (term_id ASC),
           інакше пагінація дублює й губить записи
  відповідь 200:
    {"success":true,
     "data":{"terms":[
        {"term_id":1565443,"canonical_source":"Cheongsa Island",
         "ukrainian":"Острів Ліхтарів","ukrainian_layer":"machine",
         "status":"approved","severity":"mandatory","policy":"profile_default",
         "entity_type":"lore_term","category":"lore_term",
         "case_sensitive":false,"has_definition":false}
     ]},
     "meta":{"count":100,"has_more":true,"next_cursor":"...",
             "total_matching":null,"fields":"core"}}
  fields=full додає definition, definition_source, gist, wiki_url, forms,
  scopes; core лишає їх поза відповіддю заради ваги.
  Поле has_definition обовʼязкове саме як BOOLEAN, а не як «поле definition
  відсутнє»: клієнт розрізняє «опису немає» і «сервер про опис не сказав», і
  друге для нього означає «не чіпати запис».

Помилки: 400 на невалідні limit/cursor/updated_since з details.parameter;
401/403 без ability; порожній результат · це 200 з terms: [], а не 404.

Сумісність: зміна additive. GET /agent/v1/glossary/terms із q працює як
раніше, його поведінку й формат не чіпати.

Безпека: збережи auth, abilities, rate limits, validation та audit trail.
Перелік лише читає; жодних мутацій цей endpoint не робить. Запис нових
термінів і пропозиції лишаються там, де вони є зараз.

Продуктивність: сторінка не має робити повний COUNT, якщо include_total=0;
курсор має спиратися на індексований ключ, а не на OFFSET.

Перевірки: додай серверні regression-тести на success із пагінацією (дві
сторінки без дублів і без пропусків при одночасному записі), на фільтри
(status, entity_type, severity, has_definition, updated_since), на валідацію
(limit поза межами, зіпсований cursor, невалідний updated_since), на auth без
ability і на порожній результат.

Документація: онови канонічний серверний API contract · новий endpoint,
параметри, приклад відповіді, межі limit і правила курсора.

Результат для клієнтського агента: поверни точний контракт і приклад JSON без
секретів; не змінюй bdo-ua-ai-localization із серверної сесії.
```

## Що клієнт зробить після появи endpoint

- `./bdo suspects` перестане залежати від того, чи трапився термін у пачці:
  детектор пройде по всьому глосарію сторінками й одразу дасть повний звіт.
- Зʼявиться сенс у `updated_since`: повторний аудит лише змінених записів
  замість повного перечитування.
- Рядок «ОХОПЛЕННЯ · лише терміни, які вже траплялись у прогонах» зі звіту
  зникне разом із самою межею.
