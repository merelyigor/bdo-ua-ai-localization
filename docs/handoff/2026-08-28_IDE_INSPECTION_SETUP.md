# Передача в інші проєкти: інспекції IDE як обовʼязкова перевірка

- **Створено:** 2026-08-28
- **Навіщо:** формат перевірки, що знайшов помилки, яких не бачив жоден зелений
  gate. Текст нижче копіюється в агента будь-якого проєкту як є.

## Звідки взялося

У цьому проєкті `./bdo gate full` перевіряв синтаксис (`php -l`, `shellcheck`)
і поведінку (35 кроків тестів) і був зелений. При цьому в плагіні жили дві
помилки `TS2559`: тести імпортують `.ts` через `--experimental-strip-types`,
тобто типи просто знімаються без перевірки. Інспекції IDE знайшли їх за секунду.

Висновок, який варто перенести: **зелений тестовий gate не є доказом якості
коду**. Тести перевіряють те, що ви передбачили; інспекції · те, що ви
пропустили.

## Промпт (копіювати цілком)

```text
Заведи в цьому проєкті обовʼязкову перевірку коду інспекціями IDE.

1. Правило в головному файлі правил проєкту (AGENTS.md / CLAUDE.md або їхній
   аналог), дослівно за змістом:
   «Після будь-якої зміни коду прожени інспекції IDE по ЗМІНЕНИХ файлах і
   доповідай результат: агент · через MCP `phpstorm lint_files` з
   `min_severity: error`, людина або CI · через headless-інспектор. Рівень
   ERROR блокує коміт. Стильові WEAK WARNING виправляти не обовʼязково, але
   мовчати про них не можна · назви кількість.
   Тестовий gate цього НЕ замінює: він перевіряє синтаксис і поведінку, а не
   типи й інспекції рівня IDE.»

2. Команда для headless-прогону (`<твій-CLI> inspect [тека]`), яка:
   - шукає `inspect.sh` у стандартних місцях JetBrains;
   - запускає його з профілем проєкту й `-format json`;
   - парсить звіт і виходить кодом 1, якщо є хоч одна проблема severity ERROR;
   - НЕ мовчить, коли перевірка неможлива: друкує причину й виходить кодом 2.
     Найчастіша причина · «Only one instance of PhpStorm can be run at a time»:
     headless-інспектор не стартує, поки відкрита сама IDE. Перевірено, що
     обхід через окремі `idea.config.path`/`idea.system.path` не допомагає.
     Тому в щоденній роботі перевірку робить агент через MCP, а команда
     лишається для закритої IDE та CI.

3. Механічна перевірка самого правила у вашому gate: grep, що правило є в
   файлі правил і в чеклісті, що команда зареєстрована в дереві команд і що в
   ній є голосна відмова замість мовчазного пропуску. Правило без такої
   перевірки зникає при першому ж рефакторингу документації.

4. Порядок роботи агента після змін, саме в такій послідовності:
   а) свій тестовий gate;
   б) MCP `phpstorm lint_files` по змінених файлах, `min_severity: error`;
   в) якщо є ERROR · виправити й повторити (б);
   г) у звіті назвати: скільки ERROR (має бути 0) і скільки WEAK WARNING
      лишилось, із поясненням, чому вони прийнятні.

Обмеження, які треба назвати ЧЕСНО, а не обійти:
- MCP-інспекція доступна лише агентові в IDE-сесії; ваш shell-gate її викликати
  не може. Не робіть вигляд, що це один і той самий крок.
- Інспекції не бачать того, що не резолвиться: якщо `node_modules` чи vendor не
  встановлені, частина типів дасть хибні «unresolved». Спершу залежності,
  потім висновки.
- Порожній результат інспекції є відповіддю лише тоді, коли інспектор реально
  відпрацював. Якщо він не запустився · це не «чисто», це «не перевірено».
```

## Що дає на практиці

| Клас | Тестовий gate | Інспекції IDE |
|---|---|---|
| Синтаксис PHP/shell | так | так |
| Поведінка (регресії) | так | ні |
| Типи TypeScript | **ні** | так |
| Мертвий код, зайві приведення, PSR-12 | ні | так |
| Небезпечні конструкції (`json_decode` без прапорця) | ні | так |
