- **Статус:** active
- **Створено:** 2026-08-25
- **Реєстр:** [docs/plans/README.md](../README.md)

## Мета

Один і той самий toolkit працює на macOS, Linux і Windows 10/11, з однаковим
рядком команди для агента на всіх трьох.

## Виконано 2026-08-25 (шлях 2 · WSL-міст)

Діагностика етапу 1 пройдена на машині власника: `wsl bash -lc "php -v && jq
--version && sqlite3 --version"` показав PHP 8.3.6 і jq-1.7 усередині WSL, тож
міст доступний. Бракувало лише `sqlite3`.

## Рішення: три шляхи за зростанням ціни, а не один

Порт на PHP є найкращим КІНЦЕВИМ станом, але він НЕ є першим ходом. Дешевші
шляхи ніколи не вимірювались, тому їх треба спершу перевірити або спростувати.

| # | Шлях | Ціна | Стан доказу |
|---|---|---|---|
| 1 | OpenCode всередині WSL2 | 0 рядків коду | Працює сьогодні, задокументовано в [WINDOWS_WSL2.md](../../WINDOWS_WSL2.md) |
| 2 | **WSL-міст: native Windows OpenCode викликає скрипти через `wsl`** | 4 точкові зміни, порту немає | Очікування власника (2026-08-25); архітектурно можливий, але сьогодні заблокований guard-ом |
| 2b | Native Windows + Git Bash як shell OpenCode | ~0 рядків коду плюс правки шляхів MSYS | НІКОЛИ НЕ ПЕРЕВІРЯВСЯ; заборонений правилом без заміру |
| 3 | Порт оркестрації в `php bdo.php` | ~3500 рядків bash плюс 11 тестів | Потрібен лише якщо 1, 2 і 2b не підходять |

### Шлях 2 · WSL-міст (найімовірніший цільовий для Windows)

Власник тримає OpenCode як native Windows app поза WSL і очікує, що диригент
викликає `./bdo` ЧЕРЕЗ `wsl`. Це дешевше за порт і чистіше за Git Bash: усередині
WSL справжній Linux, тож немає ні підміни шляхів MSYS, ні браку `jq`, ні
відсутнього `shellcheck`, а `workdir` у Windows-формі `C:\...` транслюється в
`/mnt/c/...` автоматично самим `wsl.exe`.

Що саме треба зробити, і чому без цього не працює:

1. **Guard.** Whitelist зіставляє сирий рядок і вимагає, щоб він ПОЧИНАВСЯ з
   `./bdo` (`.opencode/plugin/translation-execution-guard.ts:36`). Рядок
   `wsl bash ./bdo env` буде відхилений, а три відмови вбивають сесію. Потрібна
   та сама нормалізація форми виклику, що описана нижче: зняти launcher-префікс
   (`wsl`, `wsl bash -c`, `./`, `php bdo.php`) ПЕРЕД зіставленням.
   Кращий варіант, якщо OpenCode це вміє: задати `wsl` як shell самого bash-tool ·
   тоді рядки команд лишаються `./bdo …` без жодної зміни guard, промптів і
   документації. Перевірити перед тим, як міняти guard.
2. **Кінці рядків.** Репозиторій на `C:\` вичитаний Windows-git-ом при
   `core.autocrlf=true` отримує CRLF у КОЖНОМУ `.sh`. Усередині WSL це дає
   `\r: command not found` і падіння на першому ж рядку. `.gitattributes`
   (етап 0) є передумовою, а не гігієною.
3. **Дані самого OpenCode лежать по інший бік межі.** `cli/audit/verify-run.sh:36`
   і `cli/audit/audit-dump.sh:16` читають `$HOME/.local/share/opencode/opencode.db`,
   а `cli/runtime/sync-opencode-models.sh:33` · `$HOME/.config/opencode/`. Під
   WSL `$HOME` це `/home/<user>`, тоді як native OpenCode пише в
   `C:\Users\<user>\AppData\...`. Тому `./bdo audit`, `./bdo audit-dump` і
   `./bdo models` зламаються, а `audit` є ЄДИНИМ джерелом правди про субагентів
   (`.opencode/critical-rules.md`). Потрібні змінні на кшталт
   `OPENCODE_DATA_DIR` / `OPENCODE_CONFIG_DIR` з дефолтом на `$HOME`.
4. **`sqlite3` усередині WSL.** Аудит вимагає його, але preflight
   `cli/system/check-platform.sh:21` перевіряє лише `bash php jq curl git`.
   Додати `sqlite3` до переліку, інакше збій вилізе аж на аудиті.

Ціна швидкості: репозиторій на `/mnt/c` повільний, і `check-platform.sh:12` уже
про це попереджає. Альтернатива · клон у WSL (`~/GitHub`), а Windows-OpenCode
відкриває його через `\\wsl$\…`; тоді bash працює з native `/home`.

### Шлях 2 заборонений без доказу

`.opencode/critical-rules.md:19` забороняє Git Bash. Заборону внесено одним
комітом `602d429` разом із самою інструкцією WSL2; ні в `docs/FLOW_STATE.md`, ні
в планах, ні в історії немає жодного заміру, який показав би, що Git Bash
пробували і він зламався. Це декларація, а не результат.

Git for Windows постачає `bash`, `curl`, `sed`, `awk`, `grep`, `perl`, `mktemp`,
`date` · тобто майже весь runtime набору. Бракує лише `php` (офіційний zip) і
`jq` (один портативний exe). Preflight `cli/system/check-platform.sh` вимагає
рівно `bash php jq curl git`, і всі п'ять там досяжні.

Відомі ризики шляху 2, які й треба виміряти, а не вгадати: підміна шляхів MSYS
при передачі аргументів у native `php.exe`, CRLF, і чи вміє OpenCode на Windows
взагалі викликати саме Git Bash як shell.

### Якщо доходить до шляху 3

Канонічний виклик стає `php bdo.php <команда>`. Це єдиний рядок, який однаково
існує в `zsh`, `bash`, `cmd.exe` і PowerShell. Уся оркестрація переїздить із
`cli/**/*.sh` у PHP-класи під `lib/Cli/`. `./bdo` і новий `bdo.cmd` лишаються
тонкими обгортками ДЛЯ ЛЮДИНИ; агент їх не використовує.

Єдина зовнішня залежність після міграції · PHP 8.3 (+ `git` для розробки,
`node` для тестів плагінів). Зникають `bash`, `jq`, `curl`, `perl`,
`shellcheck` як runtime-вимоги.

| Варіант | Чому відкинуто |

| Порт на TypeScript/Bun | `bun` не є окремим виконуваним файлом на машині власника (перевірено 2026-08-25: `which bun` порожній) · це рантайм усередині OpenCode. Плюс `lib/**` це 2266 рядків протестованої доменної логіки на PHP, яку довелось би переписати. |
| Вендорені PHP-бінарники в репо | 5 збірок (win-x64, mac-arm64, mac-x64, linux-x64, linux-arm64) по десятки МБ назавжди осідають в історії ПУБЛІЧНОГО репо, де force-push заборонено (`.opencode/critical-rules.md:3`). Ліміт GitHub 100 МБ на файл, плюс власник стає розповсюджувачем PHP і відповідає за його CVE. |
| Docker | Ще одна важка залежність, складні шляхи між контейнером і OpenCode, і той самий Linux усередині. |

Компроміс для «нічого не встановлювати» на шляху 3: код шукає інтерпретатор у

Репозиторій лишається чистим, а портативний варіант доступний тому, кому він

## Що фактично ламається на native Windows (інвентаризація 2026-08-25)

| Місце | Обсяг | Природа проблеми |
|---|---|---|

## Ключова архітектурна зміна: guard перестає залежати від форми виклику

Сьогодні whitelist зіставляє СИРИЙ рядок shell. Це поєднує політику безпеки з
формою запуску, тому будь-яка зміна входу автоматично блокується guard-ом.

Цільова поведінка: guard спочатку НОРМАЛІЗУЄ команду до канонічної форми
`bdo <args>`, приймаючи `./bdo …`, `bdo …`, `.\bdo …`, `bdo.cmd …`,
`php bdo.php …`, і лише потім зіставляє з whitelist. Регулярки стають
`/^bdo …$/`. Це знімає зчеплення назавжди й дозволяє мігрувати команди
поштучно, не ламаючи прогін.

## Етапи

### Етап 0 · гігієна репозиторію (потрібен за будь-якого рішення)

1. Додати `.gitattributes`: `* text=auto eol=lf`, `*.png binary`, явний `eol=lf`
   для `bdo`, `*.sh`, `*.md`, `*.json`, `*.ts`.
2. `docs/WINDOWS_WSL2.md` отримує розділ про CRLF і про те, що WSL2 лишається
   підтримуваним шляхом.

**DoD:** `git ls-files --eol` не показує `w/crlf` для tracked текстових файлів.

### Етап 1 · діагностика, яка обирає шлях (робити ПЕРШИМ, ціна · хвилини)

Симптом зі скріншота («команди завершуються без output») однаково пояснюється
трьома різними причинами, і кожна веде до іншого шляху. Порт ~3500 рядків не
оплачується, доки причина не названа. На Windows у native OpenCode виконати:

| Проба | Що доводить |
|---|---|
| `echo test` | Чи shell-tool OpenCode на Windows працює взагалі |
| `wsl echo test` | Чи доступний WSL-міст (шлях 2) |
| `wsl bash -lc "php -v && jq --version && sqlite3 --version"` | Чи повний runtime усередині WSL |
| `bash --version` | Чи є Git Bash на самому Windows (шлях 2b) |
| `./bdo platform` | Чи запускається наявний набір як є |

Розвилка за результатом:

- `echo test` мовчить -> shell-tool непрацездатний, жоден порт не допоможе;
  лишається шлях 1 (OpenCode всередині WSL), решта етапів закривається.
- `wsl echo test` відповідає -> будувати шлях 2 (WSL-міст), 4 точкові зміни,
  порт не потрібен. Це найімовірніший результат.
- WSL недоступний, але `bash --version` відповідає -> шлях 2b.
- Немає ні `wsl`, ні bash, але `php -v` відповідає -> шлях 3 підтверджено.

Якщо потрібен шлях 3, ЦЕЙ ЖЕ етап дає мінімальний probe: `bdo.php` рівно з
`platform` і `env`. `platform` перевіряє PHP >= 8.3 і розширення `curl`,
`mbstring`, `json`, `openssl`; `env` читає `.env` власним парсером без `source`.
Guard отримує нормалізацію форми виклику (розділ вище).

**DoD:** причина названа однією з трьох проб і записана сюди разом із виводом.
Без цього запису етапи 2-4 не починаються.

### Етап 2 · фундамент

`lib/Cli/` отримує: HTTP-клієнт із тією ж політикою повторів, що в
`cli/api/http-request.sh`; парсер `.env`; резолвер шляхів (`cli/system/paths.sh`);
атомарний запис стану, що працює на Windows.

**DoD:** `tests/http-retry.sh` переписано як PHP-тест і проходить на обох ОС.

### Етап 3 · read-only команди

`platform`, `env`, `paths`, `patch`, `patches`, `api`, `profile status`,
`audit`, `incidents`, `judge`, `moderation --limit`. Кожна команда переїздить
разом зі своїм рядком у whitelist, промптах, `docs/**` і тестах ОДНИМ комітом.

**DoD:** `php bdo.php patches` дає байт-у-байт той самий вивід, що `./bdo patches`.

### Етап 4 · рушій прогону

`mode status|start`, `run drive`, `fetch`, `payload *`, `items`, `validate`,
`heal`, `commit`, `write`, `gate`. Профіль gate `shell` замінюється на `php -l`
плюс перевірку промптів. `./bdo` стає обгорткою над `php bdo.php`, додається
`bdo.cmd`.

**DoD:** повна пачка з 15 рядків проходить від `mode start` до `verified` на
Windows без WSL; `php bdo.php gate full` зелений на macOS, Linux і Windows.

## Ризики

1. **Найбільша прихована ціна · не bash, а тести.** 11 shell-тестів треба
   переписати, інакше на Windows немає доказу, що прогін цілий.
2. **Часткова міграція небезпечна.** Поки whitelist не нормалізує форму виклику,
   будь-яка нова команда блокується guard-ом посеред прогону.
3. **PHP на Windows вимагає ручного `php.ini`.** Офіційний zip іде з вимкненими
   `curl` і `mbstring`; `platform` мусить називати точний рядок, який треба
   розкоментувати, а не казати «немає розширення».
4. **Прогін не можна зупиняти надовго.** Міграцію робити етапами, кожен з яких
   лишає систему робочою на macOS.
