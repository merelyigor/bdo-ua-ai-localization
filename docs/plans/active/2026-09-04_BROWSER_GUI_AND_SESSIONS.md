# Браузерний інтерфейс, сесії роботи й готовність до зовнішніх API

- **Статус:** active
- **Створено:** 2026-09-04
- **Реєстр:** [docs/plans/README.md](../README.md)

Зміна вектора: основним інтерфейсом власника стає GUI в браузері, а не TUI.
Моделі лишаються локальними (Ollama), але транспорт проєктується так, щоб
зовнішній API підключався конфігом, а не переписуванням. Docker не
використовується. Реалізація йде ТІЛЬКИ після затвердження макетів і цього
плану · рішення власника 2026-09-04.

## Що вже є і не переробляється

Конвеєр, драйвер, ролі, схеми, механічні перевірки, журнали й gates лишаються
без змін. GUI є ще однією ПОВЕРХНЕЮ над тим самим `./bdo`, а не другою
системою. Уже готове й придатне для GUI:

| Що | Де | Чому це важливо для GUI |
|---|---|---|
| потік токенів моделі | `cli/model/client.php` | пише чанки в `state/run-stream.log` · сторінка читає хвіст файла |
| зміст кроку | `cli/run/step-report.sh` | запит і відповідь ролі у формі самої ролі |
| журнал прогону | `state/run-transcript.log` | хронологія кроків, переживає прибирання пачки |
| журнал викликів | `state/model-calls.jsonl` | роль, вердикт, час, токени, `stream`, `think` |
| підсумок пачки | `state/batches/<id>/batch-summary.json` | у шар / до людини / карантин |
| українські підписи | `lib/Ui/Labels.php` | стани й ролі вже мають людські назви |
| межа підкоманд | `cli/system/watch.sh` | готовий зразок: дозволено рівно перелічене, решта · відмова з причиною |

## Зміряні обмеження, з якими проєктуємо

- **Push-потік МОЖЛИВИЙ, і це перевимір власного висновку.** Спершу заміряно:
  вбудований сервер PHP у типовому режимі однопотоковий · запит `/fast` чекав
  2.6 с, поки висів трисекундний `/slow`. Тому в першій редакції плану стояло
  «SSE неможливий, лише опитування». Перевимір із `PHP_CLI_SERVER_WORKERS=4`
  дав **0.02 с** для того самого `/fast` при тому самому висячому `/slow`.
  Тобто кілька процесів-воркерів знімають обмеження, і сторінка може тримати
  одне відкрите зʼєднання, як це робить будь-який чат.
  Ціна названа прямо: змінна документована як експериментальна й працює лише
  на POSIX (macOS, Linux, а на Windows · у WSL2, де конвеєр і живе). Одне
  SSE-зʼєднання займає один воркер, тому воркерів беремо 4-8, а сторінка
  тримає РІВНО одне зʼєднання на вкладку.
  Запасний шлях лишається в коді, а не в планах: якщо `EventSource` не
  підключився за 2 с, сторінка переходить на опитування кожні 200 мс. Модель
  віддає ~41 чанк/с (721 чанк за 17.5 с на живому вимірі), тобто крок
  опитування приносить ~8 чанків · на око це той самий друк.
- **Довга робота не живе в сервері.** Прогін запускає окремий процес
  (`./bdo loop`), сервер лише читає файли. Інакше перша ж пачка заблокувала б
  сторінку на десять хвилин.
- **Будь-яка сторінка в браузері може надіслати POST на `127.0.0.1`.** Це не
  теорія: локальний сервер без перевірки походження керується з чужої вкладки.
  Тому дії вимагають токена, який `./bdo web` друкує й вшиває в сторінку, плюс
  перевірки `Origin`/`Sec-Fetch-Site`. Читання теж за токеном · одна межа
  замість двох.
- **Windows без Docker · це WSL2, і це вже так.** Конвеєр складається з 49
  bash-скриптів; нативний Windows-PHP їх не виконає. Тому: macOS і Linux ·
  нативно, Windows · у WSL2 (`docs/WINDOWS_WSL2.md`), а браузер відкривається
  на самому Windows і бачить `127.0.0.1`, бо WSL2 пробрасує loopback. Повний
  нативний Windows потребує порту оркестрації в PHP · це окремий, уже
  відкладений рядок черги, і GUI від нього не залежить.
- **Прототип не є доказом.** Макет на вигаданих даних переконливий і тому
  небезпечний. Числа в макетах беруться з живих прогонів, а працездатність
  доводить тест (§13.6).

## Архітектура

```
браузер (Mac / Windows / Linux)
   │  GET  /                → сторінка (один файл, без CDN, офлайн)
   │  GET  /api/state       → стан прогону, вердикти, підсумки
   │  GET  /api/stream      → SSE: токени моделі в міру появи (запасний шлях · опитування)
   │  GET  /api/sessions    → історія сесій і пачок
   │  POST /api/action      → рівно перелічені дії, за токеном
   ▼
PHP_CLI_SERVER_WORKERS=4 php -S 127.0.0.1:<порт>  cli/system/web-router.php
   │
   ├── читає: state/current-session, state/run-transcript.log,
   │           state/run-stream.log, state/model-calls.jsonl,
   │           state/batches/<id>/{manifest,journal,batch-summary}.json,
   │           state/sessions/<id>/summary.json
   │
   └── дія → spawn окремим процесом: ./bdo mode start … | ./bdo loop … |
              ./bdo session new|close | ./bdo moderation --approve …
                    (аргументи валідуються В КОДІ, як у watch.sh)
   ▼
конвеєр без змін → Ollama локально (або зовнішній API після етапу 4)
```

### Як це запускається (вимога власника 2026-09-04)

Одна команда в терміналі, посилання надруковане, порт вільний · власник не
шукає порт і не редагує конфіг.

```
$ ./bdo web

  Інтерфейс:  http://127.0.0.1:7654/?t=9f3c…    ← посилання клікабельне
  Порт:       7654 (вільний)
  Ціль:       PROD · bdo-ua.com.ua/api/agent/v1
  Зупинити:   Ctrl-C

[21:30:33] GET /            200
[21:30:33] GET /api/state   200
```

Порт. Спершу пробуємо `7654` (або `BDO_WEB_PORT`, якщо задано). Якщо він
зайнятий · віддаємо вибір ядру через `php -S 127.0.0.1:0`, і PHP сам друкує
обраний порт рядком `Development Server (http://127.0.0.1:62458) started`;
скрипт бере число саме звідти. Це не сканування «а чи вільно тут»: між
перевіркою й запуском є щілина, у яку порт займає хтось інший, а `:0` віддає
рівно те, що вже прив'язано. Заміряно 2026-09-04 на PHP 8.5.4: `:0` друкує
обраний порт (62453), під `PHP_CLI_SERVER_WORKERS=4` усі п'ять рядків показують
ОДИН порт, а зайнятий порт дає `Failed to listen … (Address already in use)` і
код 1 · тобто відмова гучна, а не тихий фолбек. Якщо `BDO_WEB_PORT` задано
ЯВНО й зайнятий · падаємо з причиною, не переїжджаємо: власник просив саме
цей порт.

Токен. `./bdo web` генерує токен на запуск і вшиває його в надруковане
посилання. Сторінка при завантаженні перекладає токен у `sessionStorage` і
прибирає з адреси (`history.replaceState`), далі надсилає його заголовком.
Причина · межа з розділу «Зміряні обмеження»: будь-яка чужа вкладка може
постукати на `127.0.0.1`, тому і читання, і дії за токеном.

Життєвий цикл. Типово сервер тримається на передньому плані: Ctrl-C зупиняє,
і жодного забутого процесу не лишається. `--background` пише
`state/web.json` (порт, pid, токен, час; права 0600), і тоді працюють
`./bdo web --status` і `./bdo web --stop`. Браузер відкривається сам
(`open` · macOS, `xdg-open` · Linux, `explorer.exe` · WSL2), `--no-open`
цього не робить.

Прогін НЕ живе в сервері. Кнопка «почати прогін» породжує окремий процес
(`setsid ./bdo loop …`), тому: сторінку можна закрити й відкрити · робота
триває; сервер можна перезапустити · робота триває; а прогін, запущений із
терміналу вручну, видно в браузері так само, бо сервер лише ЧИТАЄ ті самі
файли `state/**`. Одне джерело правди для двох поверхонь.

### Сесія роботи

Сесія · це період роботи, який містить N пачок. Вимога власника: бачити всю
історію по кожній пачці, закривати сесію й починати нову, і щоб закриття
ПРИБИРАЛО файли попередньої.

Ключове рішення: **`state/` лишається живою робочою текою**, а сесія
матеріалізується при ЗАКРИТТІ. Інакше довелось би переписати шляхи в сорока
скриптах, і кожен із них · місце для нового тихого дефекту.

```
state/                          живе, як зараз (жоден скрипт не змінюється)
  current-session               ідентифікатор відкритої сесії
  sessions/
    20260904_1530_a1b2/
      summary.json              коли, ціль, пачок, у шар / до людини / карантин
      batches.jsonl             по рядку на пачку: id, рядки, розкладка, час
      transcript.log            хронологія кроків сесії
      model-calls.jsonl         виклики моделі сесії
```

`./bdo session new` · закриває поточну (якщо є) і починає чисту.
`./bdo session close` · збирає `summary.json` і `batches.jsonl`, ПЕРЕНОСИТЬ
журнали в теку сесії, потім чистить живі файли: `run-transcript.log`,
`run-stream.log`, `model-calls.jsonl`, теки завершених пачок.
`./bdo session list` · історія для GUI й для терміналу.

Що НЕ прибирається ніколи: `write-log.jsonl` (незнищенний слід записів у PROD),
`quarantine.jsonl.archived`, `glossary-suspects.json`, `term-notes-queue.json`.
Правда про переклад живе на сервері, а не в сесії.

### Готовність до зовнішніх API

Сьогодні `cli/model/client.php` говорить рівно з Ollama (`/api/chat`, NDJSON).
Щоб зовнішній API підключався конфігом, транспорт відділяється від логіки:

```
config/roles.json → "provider": "ollama" | "openai"
lib/Model/Transport/Ollama.php   NDJSON, поле think, /api/ps для вікна
lib/Model/Transport/OpenAi.php   SSE `data:`, reasoning_effort, без /api/ps
```

Інтерфейс один: `send(prompt, payload, schema, stream) → {content, thinking,
stats, done_reason}`. Обидва протоколи РЯДКОВІ, тому читач один, а розбір
рядка · за провайдером. Усі перевірки (`done_reason`, порожній вміст,
валідність, вікно, схема) лишаються де були · на зібраній відповіді.

Кожен етап окремо перевіряється й окремо комітиться. Наступний не починається,
доки попередній не має свого Definition of Done.

| 1 | **Сесії в коді** · ВИКОНАНО 2026-09-04. `./bdo session new|close|list|show`, `lib/Session/Ledger.php`, `state/sessions/**`, перенесення журналів, прибирання за `BDO_KEEP_DAYS=7` (і в `./bdo clean` тим самим класом) | `tests/session-lifecycle.sh` · зелений і фальсифікований на чотирьох зламах: тиха втрата квитанції, прибирання підсумку, живі журнали після закриття, недолік у лічильнику пачок |

## Рішення власника (усі три ухвалені 2026-09-04)

1. **Закриття сесії · тримати журнали 7 днів.** `summary.json` і
   `batches.jsonl` лишаються назавжди (дрібні), `transcript.log` і
   `stream.log` · за `BDO_KEEP_DAYS=7`, як решта дампів. Діалог закриття
   пропонує обидва варіанти, типовий · «тримати 7 днів».
2. **Порт · вільний, посилання надруковане.** Одна команда в терміналі.
   Деталі й заміри · розділ «Як це запускається». `BDO_WEB_PORT` лишається
   для фіксованого порту під закладку.
3. **GUI · основний інтерфейс; TUI лишається, але ЗВУЖЕНИЙ до монітора.**
   Власник поставив умову прямо: два повних функціонали тримати не будемо,
   бо за ними складніше слідкувати; лишаємо обидва лише якщо це без ризиків.
   Ризик не в показі, а в СКЛАДАННІ прогону: обидві поверхні читають ті самі
   `state/**` через ті самі `lib/Ui/Labels.php`, `lib/Ui/Clock.php` і
   `batch-summary.json`, тому розійтись у показаннях вони не можуть за
   побудовою. А ось меню старту (режим, патч, категорія, пачки) · це друга
   реалізація рішення, і саме вона дала б дві правди. Тому на етапі 5, коли
   GUI доведений на Mac, Linux і WSL2, `bin/tui.sh` втрачає меню старту й
   лишається ЛИШЕ монітором (стан, живий екран, вихід), а `./bdo watch`
   лишається способом показати довгу роботу без браузера. До етапу 5 TUI
   працює як зараз · інакше власник лишився б без інтерфейсу до першої
   робочої сторінки.
   Механічна межа замість домовленості: gate забороняє другий шлях складання
   прогону · аргументи `./bdo mode start` формує рівно одне місце.

## Definition of Done плану

Власник запускає пачку з браузера на своїй машині, бачить крок за кроком запит,
потік і відповідь кожної ролі, закриває сесію однією кнопкою (живі файли
чистяться, історія лишається), а `./bdo gate full` зелений · включно з новими
тестами на межі сервера, дій і транспортів.
