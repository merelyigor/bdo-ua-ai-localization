# Очищення документації проєкту

- **Статус:** active
- **Статус виконання:** не почато
- **Створено:** 2026-09-19
- **Реєстр:** [docs/plans/README.md](../README.md)

> Це одноразовий виконуваний план, а не довідка. Після виконання всіх
> етапів і зелених gates він видаляється тією ж зміною, а рядок у
> `docs/plans/README.md` прибирається. Git зберігає історію виконання.

Початковий замір: у `docs/` 77 файлів і близько 7,8 тис. рядків Markdown;
`README.md` має 670 рядків, `docs/AI_AGENT_RULES_REFERENCE.md` — 732,
дзеркала правил — приблизно по 260, а `docs/plans/DEFECTS.md` містить
196 записів, із яких 5 відкриті. Виконавець зобов’язаний перезняти ці числа
перед змінами: вони є базовою лінією, а не гарантованим поточним станом.

Ти працюєш у git-корені репозиторію `bdo-ua-ai-localization`. Перед діями перевір
факт через `git rev-parse --show-toplevel`; не вгадуй абсолютний шлях на іншій машині.

## 1. Мета

Очистити документацію проєкту від застарілих, дубльованих, завершених і надмірно деталізованих матеріалів так, щоб:

1. агент швидко знаходив актуальну архітектуру;
2. кожен факт мав одне канонічне джерело;
3. завершені дефекти та міграції не займали активний контекст;
4. відкриті проблеми й актуальний backlog не загубилися;
5. документація відповідала фактичному коду;
6. усі посилання і documentation gates залишилися робочими;
7. чужі незакомічені зміни не були змінені або закомічені.

Це очищення документації, а не рефакторинг коду. Не змінюй runtime-поведінку, GUI, workflow, prompts ролей, API або тести, крім вузьких documentation checks, якщо їх необхідно оновити через свідому зміну структури документації.

Цей план є разовим дозволом на видалення лише тих документів і записів, які після
інвентаризації отримали клас `DELETE_VERIFIED` і виконали всі умови цього плану.
Окремого підтвердження для кожного такого файла не потрібно. Цей дозвіл не поширюється
на код, тести, runtime-дані, відкриті або прийняті дефекти, активну роботу чи єдиний доказ
зовнішнього контракту.

## 2. Важливий контекст

На початок аудиту відомо:

- у `docs/` приблизно 77 файлів;
- у документації `docs/**/*.md` приблизно 7,8 тис. рядків;
- `README.md` має приблизно 670 рядків;
- `docs/AI_AGENT_RULES_REFERENCE.md` має приблизно 732 рядки;
- `AGENTS.md`, `CLAUDE.md` і `QWEN.md` мають приблизно по 260 рядків;
- `docs/plans/DEFECTS.md` містить приблизно 196 дефектів;
- із них приблизно 190 закриті, 5 відкриті й 1 прийнятий;
- `docs/verification/` містить історичні звіти попередніх версій;
- існують активні, backlog- і stage-плани;
- `docs/COMMANDS.md` генерується з `cli/command-registry.json`;
- дзеркала правил не можна редагувати незалежно одне від одного;
- до початку цієї задачі в робочому дереві могла бути чужа зміна `tests/web-call-view.sh`;
- локальна `main` могла випереджати `origin/main`;
- не включай чужі зміни у свій коміт і не пуш без окремого дозволу власника.

Усі ці факти перевір сам. Не покладайся на числа з промпта, якщо поточний стан інший.

## 3. Очікуваний результат

Після очищення структура документації має відповідати таким принципам:

### Активна документація

Активними лишаються тільки документи, які потрібні для поточної роботи:

- короткий публічний `README.md`;
- коротка карта правил для агента;
- актуальний огляд архітектури;
- актуальний стан workflow;
- API-контракти;
- security contract;
- checklist перевірок;
- згенерована документація команд;
- відкриті дефекти;
- актуальні backlog- і active-плани;
- інструкція користувача;
- потрібні платформні інструкції.

### Історична інформація

Історія не повинна дублювати git.

Закритий дефект можна прибрати з активного реєстру лише якщо:

1. виправлення існує в коді;
2. названа regression-перевірка реально існує;
3. перевірка входить у gate або запускається штатно;
4. на дефект немає активних посилань, які втратять сенс;
5. з дефекту не випливає актуальне архітектурне правило, якого більше ніде немає.

Якщо дефект містить довгостроковий принцип, перенеси лише короткий узагальнений принцип у відповідний канонічний документ. Не перенось повну історію інциденту.

### Заборонено

Не створюй новий великий архів із тими самими 190 закритими дефектами. Це лише перемістить сміття.

Не копіюй історичні тексти в нові документи «про всяк випадок». Git уже є історією.

Не видаляй документ лише через його розмір.

Не переписуй код або тести, щоб вони відповідали документації. Документація повинна відповідати фактичному коду.

Не запускай переклад пачок.

Не записуй нічого в PROD.

Не змінюй `.env`, `state/**`, `output/**`, модель або налаштування Ollama.

Не редагуй чужу незакомічену зміну `tests/web-call-view.sh`.

Не використовуй `git add .`, `git add -A` або `git commit -a`.

Не пуш без явного дозволу власника в цій задачі.

## 4. Definition of Done

Робота завершена, лише якщо виконано все:

1. Зібрано повний перелік документації.
2. Кожен документ класифіковано.
3. Визначено канонічного власника для кожного типу інформації.
4. Застарілі та дубльовані матеріали прибрано або скорочено.
5. Закриті дефекти не перевантажують активний реєстр.
6. Відкриті та прийняті дефекти збережені без втрати змісту.
7. Активні плани відповідають реальному стану коду.
8. Backlog не містить уже реалізованої роботи.
9. Генеровані документи не редагувалися вручну.
10. Усі внутрішні посилання працюють.
11. Documentation gates завершилися з кодом `0`.
12. `./bdo gate touched` завершився з кодом `0`.
13. `./bdo api` завершився з кодом `0`, якщо API доступне.
14. Фінальний diff не містить runtime-змін.
15. Чужі зміни не потрапили в коміт.
16. Створено один змістовний коміт.
17. Push не виконано без окремого дозволу.

## 5. Порядок роботи

Виконуй етапи суворо послідовно. Не переходь до наступного етапу, доки не перевірив попередній.

На початку етапу заміни його `- **Статус:** не почато` на `у роботі`.
Після виконання всіх дій і названої перевірки заміни статус на `завершено`.
Одночасно оновлюй верхнє поле `Статус виконання`: `не почато` → `у роботі` →
`завершено`. Статус етапу є журналом ходу роботи: не перескакуй його і не позначай
`завершено` авансом.

## Етап 1. Інвентаризація

- **Статус:** не почато

Збери перелік документації:

```bash
rg --files \
  -g '*.md' \
  -g 'AGENTS.md' \
  -g 'CLAUDE.md' \
  -g 'QWEN.md' \
  -g '.cursorrules' \
  -g '!vendor/**' \
  -g '!node_modules/**' \
  -g '!.opencode/node_modules/**'
```

Для кожного файла визнач:

- шлях;
- кількість рядків;
- призначення;
- цільового читача;
- чи описує він поточний стан;
- чи це план;
- чи це історичний доказ;
- чи він генерується;
- чи є на нього посилання;
- чи посилається він на інші документи;
- чи дублює він інший файл;
- чи суперечить коду;
- рекомендовану дію.

Використовуй класи:

| Клас | Значення |
|---|---|
| `KEEP_CANONICAL` | Канонічний актуальний документ |
| `KEEP_GENERATED` | Генерований документ; вручну не редагувати |
| `KEEP_ACTIVE` | Чинний active/backlog документ |
| `SHORTEN` | Потрібний, але перевантажений |
| `MERGE` | Зміст має перейти до іншого канонічного документа |
| `DELETE_VERIFIED` | Завершена або дубльована історія; можна видалити після перевірки |
| `REVIEW_OWNER` | Потрібне продуктове рішення власника |
| `BROKEN` | Суперечить коду, має мертві посилання або неправильний статус |

Не створюй постійний audit-файл у репозиторії. Тимчасову таблицю тримай у `/tmp`.

## Етап 3. Очищення реєстру дефектів

- **Статус:** не почато

Це окремий обов’язковий етап.

### 3.1. Перевір статуси

Для кожного запису в `docs/plans/DEFECTS.md`:

1. прочитай статус;
2. якщо `відкритий` — збережи;
3. якщо `прийнятий` — збережи разом із причиною;
4. якщо `закритий` — перевір названу regression-команду або тест;
5. перевір, що файл тесту існує;
6. перевір, що цей тест не був видалений або перейменований;
7. знайди всі посилання на ID дефекту:

```bash
rg -n '\bD[0-9]+\b' \
  --glob '!docs/plans/DEFECTS.md' \
  --glob '!vendor/**' \
  --glob '!node_modules/**'
```

### 3.2. Що лишити в активному реєстрі

`DEFECTS.md` після очищення має містити:

- правила реєстру;
- пояснення статусів;
- усі відкриті дефекти;
- усі прийняті дефекти;
- за потреби коротку таблицю недавно закритих дефектів, лише якщо вона потрібна для поточної стабілізації;
- посилання на канонічні архітектурні правила.

### 3.3. Що робити із закритими дефектами

Закритий дефект можна видалити з активного реєстру, якщо:

- regression існує;
- regression механічно виконується;
- код більше не залежить від опису дефекту;
- важливий принцип перенесений у канонічний документ;
- ID не потрібний актуальним планам.

Не створюй `DEFECTS_ARCHIVE.md` зі старими повними рядками.

Git зберігає історію. Тест зберігає захист. Канонічна документація зберігає правило.

### 3.4. Узагальнені принципи

Якщо багато дефектів мають один клас, сформулюй один короткий принцип.

Приклади класів:

- одне джерело правди;
- відсутність даних не дорівнює порожньому значенню;
- перевірка має проходити тим самим шляхом, що й робота;
- стан GUI не визначається за непрямими ознаками;
- модель не вирішує порядок workflow;
- write має бути idempotent;
- payload ролі відповідає prompt і schema;
- історичний artifact не є поточним станом.

Не додавай опис кожного випадку. Один принцип має займати 1–3 речення.

```text
docs/plans/active/
```

- перенеси реальний залишок одним конкретним пунктом у `BACKLOG.md` або новий короткий backlog-план;

Якщо план більше не відповідає напрямку проєкту:

- не переписуй його як нову задачу;
- познач для рішення власника;
- не видаляй без явного продуктового рішення, якщо там ще є невиконана робота.

## Етап 5. Перевірка історичних verification-документів

- **Статус:** не почато

Перевір:

```text
docs/verification/
docs/plans/stages/
legacy/
docs/handoff/
docs/prototypes/
```

Для кожного файла встанови:

- чи описує він поточний контракт;
- чи потрібний для відтворення;
- чи потрібний активному gate;
- чи є на нього посилання;
- чи це лише квитанція вже завершеної міграції.

Історичні verification-звіти не мають залишатися активною документацією лише тому, що колись були доказом.

Але не видаляй їх автоматично. Спочатку перевір:

```bash
rg -n 'verification/|plans/stages/|legacy/|handoff/|prototypes/' \
  --glob '!vendor/**' \
  --glob '!node_modules/**'
```

Якщо документація використовується gate або release verification, збережи потрібний мінімум.

Якщо серія документів має однакове призначення:

- залиш один актуальний індекс;
- видали завершені квитанції, якщо їх не читає автоматична перевірка;
- не об’єднуй десятки старих квитанцій в один новий великий файл.

- старі рішення, які вже закріплені кодом;
- великі приклади;
- факти, які часто змінюються;
- списки, які вже генеруються кодом.

`AGENTS.md` має бути картою, а не енциклопедією.

Не редагуй `CLAUDE.md`, `QWEN.md`, `.cursorrules` окремо. Спочатку знайди канон і штатний механізм синхронізації.

### `docs/AI_AGENT_RULES_REFERENCE.md`

Залиш тільки деталі, потрібні для виконання актуальних правил.

Кожна секція повинна відповідати на одне питання:

- коли її читати;
- що дозволено;
- що заборонено;
- якою командою перевірити.

Прибери повтори з `AGENTS.md`. Коротка карта посилається на повне правило, але не копіює його повністю.

### `docs/PROJECT_OVERVIEW.md`

Залиш:

- межі системи;
- шари;
- залежності;
- напрям потоку даних;
- ключові інваріанти;
- точки інтеграції.

Не дублюй детальну машину станів і всі runtime-помилки.

### `docs/FLOW_STATE.md`

Залиш поточний workflow.

Прибери:

- завершену історію міграцій;
- старі реалізації;
- довгі описи виправлених дефектів;
- benchmark, які не визначають поточну поведінку.

## Етап 7. Автоматична перевірка документації

- **Статус:** не почато

Перед видаленням будь-якого файла:

```bash
rg -nF 'імʼя-файла' .
rg -nF 'відносний/шлях/до-файла' .
```

Перевір Markdown links штатним gate.

Знайди потенційні дублікати:

```bash
rg -n 'головне правило|єдине джерело|порядок кроків|локальна модель|PROD|state/\*\*' \
  README.md AGENTS.md WORKFLOW.md docs
```

Це не команда на автоматичне видалення. Кожен збіг прочитай у контексті.

Перевір застарілі згадки:

```bash
rg -n \
  'OpenCode.*диригент|старий shell|run-drive\.sh|worker-payload\.sh|qa-payload\.sh|cli/[a-z/-]+\.sh' \
  README.md WORKFLOW.md AGENTS.md docs roles
```

Не видаляй згадку, якщо вона свідомо пояснює історію або заборону. Але історія не повинна виглядати як чинна інструкція.

- **Статус:** не почато

1. реєстри;
2. дефекти;

## Етап 9. Обов’язкова перевірка змісту

- **Статус:** не почато

Після редагування перевір:

### Канонічність

- список станів workflow існує в одному канонічному місці;
- список команд генерується з реєстру;
- параметри моделей беруться з конфігурації;
- актуальний список ролей не дублюється вручну в багатьох файлах;
- API-контракт не вигаданий із прикладів;
- відкриті дефекти не загублені;
- backlog не загублений;
- правила безпеки не послаблені.

### Посилання

Перевір усі відносні Markdown links.

### Секрети

Переконайся, що в документацію не потрапили:

- API keys;
- токени;
- приватні URL;
- значення локального `.env`;
- вміст `state/**`;
- персональні payload.

### Diff

Запусти:

```bash
git diff --check
git diff --stat
git diff -- README.md WORKFLOW.md AGENTS.md CLAUDE.md QWEN.md docs
git status --short
```

Прочитай весь власний diff. Не покладайся лише на `--stat`.

## Етап 10. Gates

- **Статус:** не почато

Запусти в такому порядку:

```bash
./bdo gate docs
./bdo gate touched
./bdo api
```

Якщо змінив механізм самого documentation gate, додатково запусти:

```bash
./bdo gate full
```

Не запускай `full`, якщо механізм gate не змінювався і правила проєкту цього не вимагають.

Якщо gate падає:

1. встанови точну причину;
2. визнач, чи це твоя зміна;
3. якщо твоя — виправ;
4. якщо pre-existing — назви це окремо;
5. не обходь перевірку;
6. не використовуй `--no-verify`.

Не повідомляй, що перевірка пройшла, якщо код виходу не `0`.

## Етап 11. Перевірка scope

- **Статус:** не почато

Перед комітом повторно виконай:


```bash

```

## 6. Формат фінальної відповіді

Фінальна відповідь повинна бути короткою й містити:

### Результат

- скільки документів було;
- скільки залишилось;
- скільки видалено;
- скільки скорочено;
- наскільки зменшився обсяг рядків;
- що тепер є канонічною точкою входу.

### Що очищено

- закриті дефекти;
- завершені плани;
- verification receipts;
- дублікати;
- застарілі інструкції;
- повтори правил.

Називай лише те, що реально змінено.

### Що свідомо залишено

- відкриті дефекти;
- прийняті ризики;
- активні плани;
- необхідні платформні документи;
- матеріали, які читають gates.

### Перевірки

Для кожної команди назви реальний exit code:

```text
./bdo gate docs — exit 0
./bdo gate touched — exit 0
./bdo api — exit 0
```

Якщо якась команда не виконана або впала, скажи це прямо.

### Git

- hash коміту;
- commit message;
- чи виконано push;
- які чужі зміни залишилися поза комітом.

## 7. Умови зупинки

Зупинись і попроси рішення власника, якщо:

- незрозуміло, чи документ описує чинне продуктове рішення;
- потрібно видалити відкритий або прийнятий дефект;
- потрібно скасувати незавершений backlog;
- документ є єдиним доказом зовнішнього API-контракту;
- cleanup вимагає зміни runtime-коду;
- потрібно змінити поведінку workflow;
- потрібно видалити файл, який читає gate;
- потрібно зробити push;
- знайдено конфлікт із чужими незакоміченими змінами.

В інших випадках виконуй роботу самостійно.

## 8. Режим виконання і закриття плану

Виконай весь план послідовно в одній сесії. Не зупиняйся після інвентаризації заради
окремого підтвердження `DELETE_VERIFIED`: разовий дозвіл у розділі 1 вже покриває цей
вузький клас. Зупинка потрібна лише за умов розділу 7.

Найбільший очікуваний ефект дають три дії: прибрати перевірені закриті дефекти з активного
контексту, прибрати завершені verification-квитанції та винести історичні пояснення з
`README.md` і правил. Це пріоритети, а не дозвіл механічно видалити всі закриті записи або весь
історичний Markdown без класифікації.

Після зелених gates, фінального перегляду diff і перевірки scope:

1. познач всі етапи завершеними;
2. заміни верхнє `Статус виконання` на `завершено`;
3. зафіксуй цей стан у власному diff;
4. видали `docs/plans/active/CRITICAL.md` і його рядок із `docs/plans/README.md` перед створенням
   фінального коміту;
5. повтори `./bdo gate docs` після видалення плану;
6. створи один цілісний коміт очищення.

Фінальний коміт не має містити цей виконаний план або його тимчасовий рядок у реєстрі.
