# Прототипи інтерфейсу

Тека для МАКЕТІВ браузерного інтерфейсу, а не для реалізації. Кожен файл
самостійний: один `.html`, жодних залежностей, жодного сервера · відкривається
подвійним кліком і працює офлайн.

```bash
open docs/prototypes/01-run-live.html      # macOS
xdg-open docs/prototypes/01-run-live.html  # Linux
start docs/prototypes\01-run-live.html     # Windows
```

## Правила теки

1. **Дані в прототипі несправжні, і це сказано на самій сторінці.** Макет на
   вигаданих числах виглядає переконливо й тому небезпечний: він створює
   враження працездатності там, де її ще немає. Прототип є документацією
   НАМІРУ, а не доказом · доказ дає тест (§13.6 нормативу).
2. **Числа беруться з живих прогонів.** Вигадані цифри роблять макет
   красивішим за реальність, і рішення за ним ухвалюється хибне. У кожному
   файлі названо, з якої пачки взято дані.
3. **Прототип не ходить в API і не читає `state/`.** Він самодостатній, тому
   його не можна випадково прийняти за робочий інструмент.
4. **Кнопка в макеті означає дію, яка ВЖЕ існує командою.** Малювати те, чого
   немає в `cli/command-registry.json`, означає проєктувати другу систему
   поруч із наявною.

## Актуальні знімки design system · 2026-09-15

PNG-знімки нижче новіші за HTML-прототипи 01–04. Вони є поточними візуальними
референсами для наступної роботи, але не замінюють behavioral contract: на
знімку можуть бути нові елементи, стани або композиція, яких ще немає в коді.
HTML-прототипи лишаються історичною документацією наміру й можуть бути не
актуальні на 100%. Для кожного знімка є окремий документ зі статусом
«реалізовано / частково / не реалізовано».

### Як читати статуси

- **реалізовано** · структура, стан і візуальна система відповідають знімку;
- **здебільшого відповідає** · поведінка й основна композиція є, але лишилися
  помітні відмінності у візуальному оформленні;
- **частково відповідає** · основний flow є, але частина композиції або станів
  ще не перенесена;
- **поведінково відповідає** · дані й дії працюють, але reference ще не є
  точним visual target.

Знімки містять дані й тексти з моменту створення. Їх не можна сприймати як
підтвердження актуального API, стану `state/**` або безпечності дії. Доказ
робочої поведінки дають live browser, DOM/AX inspection і тести.

## Що зведено з макетами 2026-09-06

Власник порівняв екрани з макетами й сказав, що макети подобаються більше.
Зведено ТРИ речі, яких бракувало по суті, а не за стилем:

- **вердикти на екрані прогону** (макет 01): рядки пачки з джерелом, перекладом
  і думкою QA, фільтри `усі / пройшло / на перегляд / відхилено`. До цього
  сторінка показувала, скільки секунд працювала роль, і жодного перекладеного
  рядка. Довгий вирок підрізається трьома рядками · на живій пачці QA написала
  3 169 символів на один рядок і сховала під собою весь перелік;
- **вибір патча таблицею** (макет 04): у випадайці не видно, ДЕ є робота.
  Тепер видно `без ШІ-шару` по всіх патчах одразу · саме за цим числом патч і
  вибирають;
- **шапка одним рядком і стрічка кроків хлібним слідом** (макет 01): шість
  коробок із однаковим словом «зроблено» з'їдали чверть екрана;
- **підсумок сесії картками** (макет 02).

Чим готове СВІДОМО відрізняється від макетів:

- **тема темна**, а макети світлі · вибір власника 2026-09-06;
- у черзі немає підписів «чому тут» і підказки глосарія: API пропозицій таких
  полів не віддає, а вигадана причина гірша за відсутню (це вже записано в
  `web/queue.html`);
- картка ролі не показує коротку витяжку її результату, як у макеті 01. Замість
  цього є `розгорнути роботу` і `на весь екран`, які показують СПРАВЖНІ файли
  запиту й відповіді. Причина не в лінощах: §14.8 нормативу забороняє другий
  рендер змісту кроку в JavaScript · його вже рендерить `./bdo step-report`, і два
  рендери розійшлися б на першій же зміні payload;
- кнопок `прийняти правку` / `до людини` на вердиктах немає: команди для правки
  рядка ПОСЕРЕД пачки не існує, а малювати кнопку без команди заборонено
  правилом 4 цієї теки.
